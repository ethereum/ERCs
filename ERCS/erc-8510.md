## Abstract

This proposal defines a receipt that a paid model endpoint signs for each call it charges: hashes of the request and
the response, the model, the tokens counted, the price in an [ERC-20](./eip-20.md) asset, the payer and the payment
that settled it. The receipt is a JSON object with a fixed member order, signed by the endpoint's key as an
[ERC-191](./eip-191.md) message.

The endpoint serves each UTC day's receipts as a day list, in a fixed order, with a Merkle root over their hashes. Within a
day after the day ends, it publishes that root in a log on chain. A payer holding a receipt can then show that the
endpoint counted the call that day, and a receipt the published root does not cover is evidence the endpoint left a
call out.

## Motivation

Agents buy model calls from endpoints they do not run, and pay per call or per token, often over HTTP payment schemes
such as x402. The payment settles on chain; what was bought does not. Each endpoint reports usage in its own format, if
at all, and nothing ties a charge to the request it answered.

A buyer needs three things after the fact: proof of what a given charge was for, a way to check that the endpoint's
account of a day matches the calls the buyer made, and a commitment the endpoint cannot revise later. Auditors and
lenders that size an agent's spending need the same records in one format across endpoints.

A signed receipt per call gives the first. A day list under a Merkle root gives the second without publishing anyone's
calls on chain. One record per day on chain gives the third at the cost of one transaction a day, whatever the volume.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT
RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Terms

- **Issuer**: a service that answers model calls for payment and signs receipts for them.
- **Signer**: the address of the key an issuer signs receipts with. One issuer MAY use several signers; each has its own
  day lists, records and base URL.
- **Payer**: the address whose payment settled a call.
- **Day**: a UTC calendar date, written `YYYY-MM-DD`. A receipt belongs to the day its `at` member names.
- **Day list**: one signer's receipts for one day, in day-list order: ascending `at`, and receipts with equal `at` in
  ascending receipt hash.
- **Day root**: the Merkle root over a day list.
- **Day record**: the statement of a closed day's root that the issuer publishes on chain.
- **Publisher**: an account that sends day records for a signer. It MAY differ from the signer.

### Receipt

A receipt is a JSON object with exactly the members below, plus `signature`. The table order is the canonical order.

| Member | Type | Meaning |
| --- | --- | --- |
| `v` | number | The version: `1`. |
| `request` | string | Keccak-256 of the request body bytes as the issuer received them, with any content-coding still applied. |
| `response` | string | Keccak-256 of the response body bytes the issuer produced for the call, also when it withheld them. |
| `model` | string | The issuer's identifier for the model the payer asked for. |
| `upstream` | string | The identifier of the model as the party that ran it names it. Equal to `model` when the issuer runs the model itself. |
| `tokensIn` | number | Input tokens counted for the call. |
| `tokensOut` | number | Output tokens counted for the call. |
| `price` | string | Everything charged for the call, in the asset's base units. |
| `fee` | string | The part of `price` that is a fixed charge per call. `"0"` when there is none. |
| `absorbed` | string | Cost of the call the issuer bore and did not charge, in the asset's base units. `"0"` when there is none. |
| `judged` | object or null | `null`, or the verdict when the issuer had the answer evaluated before returning it (below). |
| `asset` | string | The ERC-20 contract the payment was made in. |
| `network` | string | The chain the payment settled on, as a [CAIP-2](https://github.com/ChainAgnostic/CAIPs/blob/ebacdb90283ded501350bd0011db4362734f9c4b/CAIPs/caip-2.md) identifier such as `eip155:1`. |
| `payer` | string | The payer. |
| `nonce` | string | The payment's unique identifier for this payer under the payment scheme used: a decimal string for a numeric nonce, or 32 bytes as hex for a `bytes32` nonce. |
| `at` | string | When the receipt was signed: UTC, ISO 8601 with milliseconds and a `Z`, such as `2026-11-19T12:02:49.376Z`. |
| `signer` | string | The signer. |
| `signature` | string | The signature (below). Not part of the canonical form. |

`judged`, when not `null`, has exactly these members, in this order:

| Member | Type | Meaning |
| --- | --- | --- |
| `accepted` | boolean | Whether the evaluation accepted the answer. |
| `passProbability` | number | The evaluator's probability that the answer meets the bar, from 0 to 1, with at most 6 decimals. |
| `bar` | number | The probability the answer had to reach, from 0 to 1, with at most 6 decimals. |
| `decision` | string | An identifier of where the verdict is recorded, in a form the issuer documents. |

Every member MUST have the type its table gives. Hashes, `nonce` in hex form and `signature` MUST be lowercase hex with a
`0x` prefix. `asset`, `payer` and `signer` MUST be in [ERC-55](./eip-55.md) mixed-case form. `price`, `fee`, `absorbed`
and a decimal `nonce` MUST be decimal strings without leading zeros, below 2^256. `tokensIn` and `tokensOut` MUST be
whole numbers no greater than 2^53 - 1. `fee` MUST NOT exceed `price`. `model`, `upstream` and `decision` MUST be 1 to
256 printable ASCII characters (0x20 to 0x7E). A receipt MUST NOT have members other than those listed, and a verifier
MUST reject one that does.

An issuer MUST sign a receipt for every call it charges, and only for calls it charged. A call that is charged and
whose answer is withheld still gets a receipt. A payment that settles after the issuer stopped answering the call is a
charge too: the issuer MUST then sign a receipt for it or return the payment. An issuer MUST NOT sign two receipts with
the same `network`, `asset`, `payer` and `nonce`.

### Canonical form and signature

The canonical form of a receipt is its members other than `signature`, in the table order, with `judged`'s members in
their table order, serialized as [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) serializes values: no whitespace, strings escaped and numbers
written as RFC 8785 requires, so a probability of exactly 0 or 1 is written `0` or `1`. Member order is the table order,
not RFC 8785's sorted order. A verifier MUST reject a receipt whose JSON text repeats a member name in any object.

The receipt hash is Keccak-256 of the UTF-8 bytes of the canonical form.

`signature` is an ERC-191 signature, version `0x45`, by the signer over the 32 bytes of the receipt hash: the signer
signs `keccak256("\x19Ethereum Signed Message:\n32" || receiptHash)`. It is 65 bytes, `r || s || v`, with `s` no greater
than half the secp256k1 group order and `v` 27 or 28. A signer key MUST NOT make ERC-191 version `0x45` signatures over
32-byte messages for any other purpose.

A receipt is valid when every rule of the Receipt section holds, its signature has the form above, and the address
recovered from `signature` over that digest equals `signer`.

### Delivery

An issuer MUST give the payer the receipt with the response to the call it covers. Over HTTP, an issuer SHOULD return
it in the `Inference-Receipt` response header, as base64 of the receipt's JSON, on every response it charged for,
including one that withholds the answer.

### Day lists

An issuer MUST keep each signer's receipts per day and MUST serve each day's list at `<base>/v1/receipts/<YYYY-MM-DD>`,
where `<base>` is the base URL it states for that signer, as this JSON object. Each `<base>` serves exactly one signer.

| Member | Type | Meaning |
| --- | --- | --- |
| `day` | string | The day. |
| `signer` | string | The signer, ERC-55. |
| `count` | number | How many receipts `receipts` holds. |
| `root` | string or null | The day root over `receipts`, or `null` when there are none. |
| `unreadable` | number | Entries the issuer stored for the day that are not valid receipts of that day and signer. |
| `receipts` | array | The receipts, in day-list order. |

An entry is unreadable when it is not a valid receipt of that day and signer, including one the issuer cannot read
back. Unreadable entries MUST NOT be listed and are not under `root`. A non-zero `unreadable` tells readers the list is
not the whole day. Readers MUST reject a list whose receipts are not in day-list order, or that holds two receipts with
the same `network`, `asset`, `payer` and `nonce`.

An issuer MAY serve the list of a day that is not over. Its `root` changes as receipts are added and MUST NOT be
published. An issuer MUST serve each closed day's list for at least 365 days after the day, a day without receipts as a
list with `count` 0.

### Day root

The leaves are the receipt hashes, in day-list order. Each layer above is built from the one below, left to right: two
adjacent nodes `a` and `b` become `keccak256(min(a, b) || max(a, b))`, comparing them as 256-bit unsigned integers. A
node left without a partner at the end of a layer moves up unchanged. The day root is the single node at the top. The
root of a list with one receipt is that receipt's hash.

### Inclusion proofs

A proof for the receipt at index `i` is the list of sibling nodes from its leaf to the root, lowest first, skipping
layers where the node had no partner. A verifier MUST compute the leaf from the receipt's canonical form, then fold the
proof with the pair rule above and compare the result with the day root. This is the form OpenZeppelin's
`MerkleProof.verify` takes, so a contract can check a receipt against a published root. A contract or other verifier
checking inclusion MUST take the canonical receipt bytes as input, never a leaf, and MUST reject input of exactly 64
bytes.

### Day records

Within 24 hours after a day ends, an issuer MUST publish one day record for each signer that signed a receipt dated that
day. It MUST NOT publish a day's record before the day is over or while the day's `unreadable` is non-zero, and MUST NOT
sign a receipt dated a day it has published. It MAY publish a record with `count` 0 and a root of 32 zero bytes for a
day without receipts. The record is a JSON object with at least these members:

| Member | Type | Meaning |
| --- | --- | --- |
| `kind` | string | `"receipts"`. |
| `date` | string | The day. |
| `signer` | string | The signer, ERC-55. |
| `count` | number | The day list's `count`. |
| `root` | string | The day list's `root`, or 32 zero bytes when `count` is 0. |

For each signer, the issuer MUST state the chain (as a CAIP-2 identifier), the contract and the publisher accounts it
publishes records with, where its payers can read them, such as its agent registration file or the documentation of
its day lists. The publisher MUST send the record as the UTF-8 bytes of its JSON in the `data` of this event, emitted by
that contract with `by` set to the account that called it:

```solidity
event Inscribed(address indexed by, string kind, bytes data);
```

`kind` in the event MUST be `"receipts"`. An issuer SHOULD NOT publish a second record for the same signer and day.
Readers MUST consider only logs from the stated contract on the stated chain whose `by` is a stated publisher, MUST
ignore a log whose `data` is not a well-formed record for that signer and day, and MUST take the first remaining log by
block number and log index.

### Readers

To check a receipt it holds, a payer:

1. checks the receipt is valid;
2. reads the day list for the receipt's day and signer, checks every receipt in it is valid, of that day and of that
   signer, in day-list order and for distinct payments, and that `count` and `root` match the receipts listed;
3. finds the receipt in the list, or computes its proof and checks it against `root`;
4. finds the day record as the Day records section says, and checks its `count` and `root` against the list.

A valid receipt that no published root covers, or a list whose root differs from the published record, is the
issuer's to explain.

## Rationale

- **JSON with a fixed order, signed as ERC-191 bytes.** The signed bytes are the stored and served bytes, so a receipt
  needs no second encoding, and any language with a JSON library and Keccak can check one. The ERC-191 prefix keeps a
  receipt signature from ever being valid as a transaction signature. It does not separate receipts from other 32-byte
  messages, so the signer key is reserved for receipts. Typed structured data would add a domain of its own; receipts
  are signed and checked off chain today, and whether version 2 should move to it is an open question.
- **RFC 8785 values, table order.** RFC 8785 fixes how strings and numbers are written, which is where JSON
  serializers disagree. Its sorted member order was not taken, so that the order stays readable. Identifiers are kept
  to printable ASCII and probabilities to six decimals so that no serializer has a choice left to make.
- **A fixed order.** Ordering by `at` and then by hash lets anyone holding a day's receipts rebuild its list and root
  without knowing how the issuer stored them.
- **Sorted pairs, carried odd nodes.** Sorted pairs match OpenZeppelin's `MerkleProof`, so a contract can check a
  receipt against a root with a library most contracts already use. Hashing an odd node with itself would give a list
  and the same list with its last receipt repeated one root; carrying it up does not. Sorted pairs make a root blind to
  the order of two siblings; the day-list order fixes it.
- **Leaves without a second hash.** OpenZeppelin recommends hashing leaves twice, because the 64-byte preimage of an
  inner node hashes to that node and could otherwise pass as a leaf with a shorter proof. Here the leaf stays the
  receipt hash, the value payers already hold and quote, and the rule moves to the input instead: a canonical receipt is
  always longer than 64 bytes, and verifiers take receipt bytes, never a leaf.
- **Stated publishers, no record signature.** Any contract can emit the event and any account can call it, so the
  record's authority comes from the contract and accounts the issuer states. A signature over the record would let any
  log carry it, at the cost of a second signature format.
- **One list per UTC day.** Settlement, accounting and audits run by day, and a daily record bounds the on-chain cost
  to one log per signer per day.
- **One fixed member set.** `upstream`, `absorbed` and `judged` serve issuers that resell models other parties run, or
  have answers evaluated before they return them. They stay in version 1 with neutral values (`model`, `"0"`, `null`)
  for issuers that do neither, so every receipt has one canonical form and a hash that does not depend on which fields
  an issuer chose to use.

### Open questions

- Whether `upstream` should name the provider that ran the model separately from the model's name.
- Whether a version 2 should commit to the payment's settlement transaction, which the issuer learns only after
  settling, and name the payee and the payment scheme.
- Whether a version 2 should sign receipts as typed structured data with a domain of their own.

## Backwards Compatibility

This proposal introduces a new format and has no backwards compatibility issues.

## Reference Implementation

[`receipts.mjs`](../assets/erc-8510/receipts.mjs) implements the canonical form, the receipt hash,
the signature check, day lists, day roots, inclusion proofs and day records, with no dependencies.
[`cli.mjs`](../assets/erc-8510/cli.mjs) runs them on files, and
[`README.md`](../assets/erc-8510/README.md) says how.

BrainChain's inference gateway on Robinhood Chain issues these receipts for calls paid in an ERC-20 stablecoin over
x402, serves its day lists in this form and publishes each closed day's record on BrainChain. It returns the receipt
under its own header name, and its records carry two more members, `brainchain` and `at`, which "at least these
members" allows.

## Security Considerations

- **What a receipt proves.** A receipt proves what the issuer stated about a call: the hashes, the model, the counts and
  the charge. It does not prove that the named model produced the answer or that the token counts are right; an
  issuer that resells a model can only pass on what its upstream reported. The payment is checked against the payment
  scheme's own records, such as a token's record of used transfer authorizations or Permit2's nonce bitmap, from `network`, `asset`,
  `payer` and `nonce`; a receipt does not name the payee.
- **Self-dealing.** An issuer that pays itself through a payer it controls produces valid receipts. Receipts show what
  was charged, not that the payers are independent of the issuer.
- **Omission.** An issuer can leave a call out of a day list. The payer's signed receipt, dated and signed by the same
  key, shows it, and a missing record for a day the payer holds a receipt of shows it too. Payers SHOULD keep their
  receipts and SHOULD check them against published roots.
- **Revision.** An issuer can serve a different list later, but not change a record already on chain. Readers take the
  first record, so a second record does not replace it.
- **Unreadable entries.** An issuer can claim entries are unreadable to drop them from a list. The count is public, and
  a payer whose receipt is missing has the receipt.
- **Number formatting.** `passProbability` and `bar` are binary floating-point numbers. Implementations outside
  ECMAScript MUST write them as RFC 8785 requires, or the hash will differ; six decimals at most keeps every value
  exact in the shortest form.
- **Inner nodes as leaves.** The 64-byte preimage of an inner node hashes to that node, so a verifier that accepted a
  leaf, or 64 bytes as a receipt, would accept something that is not a receipt. The rule on verifier input closes this.
- **Key reuse.** A signature over a 32-byte value someone else chose can be presented as a receipt signature. The signer
  key MUST therefore sign nothing else of that form; a key that also settles payments signs transactions, which the
  ERC-191 prefix keeps apart.
- **Privacy.** Receipts carry hashes of request and response bodies, not the bodies. A short or guessable body can be
  found from its hash, identical requests share a hash, so a day list shows which payers sent the same body, and a
  deterministic answer to a known prompt can be confirmed. Payers that need otherwise SHOULD include something random in
  each request. Day lists also show models, token counts and verdicts, and which payers paid, how much and when.
- **Signature malleability.** For each signature a second valid `s` exists. Only the lower one is valid here, so each
  receipt has one signature; the signature is not part of the leaf or the record either way.
- **Key compromise.** Whoever holds a signer's key can sign receipts in its name, also dated in the past. Issuers SHOULD
  rotate to a new signer when a key may be exposed and say from which day the new signer applies. A receipt signed by a
  key since revoked is evidence only where a published root covers it.
