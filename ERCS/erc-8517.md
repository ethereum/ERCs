## Abstract

This standard defines how the post-quantum secrets of an Ethereum validator or builder are derived from a seed, usually a [BIP-39](https://github.com/bitcoin/bips/blob/43ce3a461dfb48e62ffa0cfc70f5f54d1eb5c577/bip-0039.mediawiki) mnemonic. It replaces [ERC-2333](./eip-2333.md) and [ERC-2334](./eip-2334.md) for these secrets.

A tree of keys is built from the seed with hardened-only HMAC-SHA512 derivation. The key of the node at path `m/5326/3600/<role>/<account>` is the *account seed* of one validator or builder. Validators and builders have separate roles, and therefore separate subtrees. Two seeds are expanded from an account seed with HKDF: the seed of the leanXMSS signing key, and the seed of the verifiable random function (VRF) tree. All the post-quantum keys of a validator are therefore recoverable from the mnemonic, its role and its account index.

## Motivation

[ERC-2333](./eip-2333.md) derives BLS12-381 secret keys, and [ERC-2334](./eip-2334.md) assigns them paths. Post-quantum consensus replaces BLS with leanXMSS, a stateful hash-based signature scheme, and with a hash-based VRF. Both are generated from 32-byte seeds rather than from scalars of a curve. Validators register a leanXMSS public key and a VRF root for each of their indices.

Without a standard derivation, each tool generates these seeds from fresh randomness. Every key then needs its own backup, and a validator cannot recover its post-quantum keys from the mnemonic it already holds. A standard derivation gives every tool the same keys from the same mnemonic. It also lets a stake owner who holds the mnemonic build the whole registration, including the proof of possession, for a validator run by another party.

The post-quantum secrets MUST NOT be derived from a BLS secret key. A BLS public key is published on chain, and a quantum adversary could recover the BLS secret key from it. Every secret derived from that BLS secret key falls with it. The derivation of this standard has no input in common with BLS keys apart from the root seed, and it only uses hash functions.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Notation

* `a || b` is the concatenation of the octet strings `a` and `b`.
* `I2OSP(n, l)` is the big-endian encoding of the non-negative integer `n` in `l` octets, as in RFC 8017.
* `HMAC-SHA512(key, data)` is HMAC (RFC 2104) with SHA-512.
* `HKDF-Expand(prk, info, l)` is the expand step of HKDF (RFC 5869) with SHA-256.
* `x[a:b]` is the octet string of the octets of `x` at positions `a` to `b - 1`.

### Constants

| Name | Value |
| - | - |
| `MASTER_KEY_DOMAIN` | `"Ethereum PQ seed"` (ASCII, 16 octets) |
| `PQ_PURPOSE` | `5326` |
| `COIN_TYPE` | `3600` |
| `HARDENED_OFFSET` | `2**31` |
| `ROLE_VALIDATOR` | `0` |
| `ROLE_BUILDER` | `1` |
| `XMSS_SEED_INFO` | `"leanXMSS key"` (ASCII, 12 octets) |
| `VRF_SEED_INFO` | `"VRF key"` (ASCII, 7 octets) |

### Seed

The `seed` is an octet string of 16 to 64 octets. It SHOULD be the 64-octet output of the BIP-39 `mnemonic_to_seed` function. A validator that already holds an [ERC-2333](./eip-2333.md) mnemonic SHOULD use the same mnemonic and passphrase. Its BLS and post-quantum keys then share one backup. It MAY instead use a different mnemonic (see [Separate mnemonics](#separate-mnemonics)).

### Nodes

A node of the tree is a pair `(key, chain_code)` of two 32-octet strings.

The master node of `seed` is:

```text
master(seed):
    I = HMAC-SHA512(MASTER_KEY_DOMAIN, seed)
    return (I[0:32], I[32:64])
```

The child of index `index` of the node `(key, chain_code)` is, for `0 <= index < HARDENED_OFFSET`:

```text
child((key, chain_code), index):
    I = HMAC-SHA512(chain_code, 0x00 || key || I2OSP(index + HARDENED_OFFSET, 4))
    return (I[0:32], I[32:64])
```

Every child is hardened: knowing a child node, its siblings or other nodes of the tree does not reveal its parent. An implementation MUST refuse an `index` outside `[0, HARDENED_OFFSET)`.

### Path

A path is written `m / i_1 / i_2 / ... / i_n`. `m` is the master node, and `i_k` is the index of the child taken at depth `k`. Every level is hardened. Paths are written without the `'` marker of BIP-32: the index `i` of a path is the child index `i + HARDENED_OFFSET`.

`role` is `ROLE_VALIDATOR` for a validator and `ROLE_BUILDER` for a builder. Other values of `role` are reserved for future roles. An implementation MUST refuse a `role` that it does not support.

The *account seed* of role `role` and account `account`, for `0 <= account < HARDENED_OFFSET`, is the `key` of the node at path `m / PQ_PURPOSE / COIN_TYPE / role / account`:

```text
node = master(seed)                       # m
node = child(node, PQ_PURPOSE)            # m / PQ_PURPOSE
node = child(node, COIN_TYPE)             # m / PQ_PURPOSE / COIN_TYPE
node = child(node, role)                  # m / PQ_PURPOSE / COIN_TYPE / role
(key, chain_code) = child(node, account)  # m / PQ_PURPOSE / COIN_TYPE / role / account
account_seed = key
```

The `chain_code` of that node is not used.

`account` plays the role of the account index `i` of [ERC-2334](./eip-2334.md): the `account`-th validator, or the `account`-th builder, of the seed. Each role has its own range of accounts, starting at `0`. A tool that derives both BLS and post-quantum keys for a validator from the same seed SHOULD use the same index for both.

### Seeds of the keys

The leanXMSS seed and the VRF seed of an account seed `account_seed` are:

```text
xmss_seed = HKDF-Expand(account_seed, XMSS_SEED_INFO, 32)
vrf_seed  = HKDF-Expand(account_seed, VRF_SEED_INFO, 32)
```

A builder has no VRF tree. A builder's tool MUST NOT require a VRF seed, and it MAY skip deriving it.

### Keystores

A keystore of these keys SHOULD encrypt the account seed, and SHOULD record the path from which it was derived. The path includes the role. Both the leanXMSS seed and the VRF seed are expanded from it. One keystore therefore holds the keys of one account.

## Rationale

### Hardened HMAC-SHA512 derivation

[ERC-2333](./eip-2333.md) derives every child through a Lamport public key, and outputs a scalar modulo the order of BLS12-381. The Lamport step was a commitment for a post-quantum backup of BLS keys. Post-quantum keys need no such backup, and the reduction modulo the order of a curve has no meaning for a 32-octet seed. Each level of ERC-2333 also costs more than 500 SHA-256 evaluations, which matters on hardware wallets and in zero-knowledge proofs of key derivation.

The derivation of this standard is the hardened derivation of SLIP-0010, used for Ed25519 keys and already implemented by hardware wallets and libraries. Ed25519 keys and leanXMSS seeds are both arbitrary 32-octet strings: no key is rejected and no derivation is retried. Only the domain of the master node differs. Each level costs two SHA-512 evaluations of HMAC.

The distinct `MASTER_KEY_DOMAIN` makes the tree of this standard disjoint from every SLIP-0010 tree of the same seed, whatever the path.

### One account seed per account

Each registration binds one leanXMSS public key and one VRF root, and both change together. Deriving both seeds from one node lets one keystore hold both, with one secret. HKDF with distinct `info` strings keeps the two seeds independent. Builders, which have no VRF, only derive the leanXMSS seed.

### Separate roles

A validator and a builder that shared a leanXMSS key would both sign at the same slots. The same leaves would then sign different messages, which allows forgeries (see [Reuse of leanXMSS leaves](#reuse-of-leanxmss-leaves)). Without a `role` level, a validator tool and a builder tool that both start at `account = 0` would derive the same key from the same seed. The `role` level puts each role in its own subtree. A validator and a builder of the same seed therefore never share a key, whatever their accounts.

### Path

* `PQ_PURPOSE` is `5326`, the word "lean" typed on a phone keypad (L = 5, E = 3, A = 2, N = 6). The purpose names Lean Ethereum, whose post-quantum signature scheme is leanXMSS, in the way the purpose `12381` of [ERC-2334](./eip-2334.md) names the curve BLS12-381. The value itself carries no security: the distinct `MASTER_KEY_DOMAIN` already separates this tree from every other tree of the same seed. It only leaves room for other families of post-quantum keys under the same master node.
* `COIN_TYPE` keeps the `3600` of [ERC-2334](./eip-2334.md): the keys are consensus keys of the same chain.
* `role` separates validators from builders (see [Separate roles](#separate-roles)). Reserved values leave room for future roles.
* The `use` level of [ERC-2334](./eip-2334.md) is dropped. Its only use was the split between withdrawal and signing keys. Post-quantum withdrawal credentials are execution addresses, and the two seeds of one account are split by HKDF.

### Separate mnemonics

Reusing the mnemonic of the BLS keys is a convenience, not a requirement. Nothing in this standard links the post-quantum keys of a validator to its BLS keys, and a stake owner MAY derive them from a different mnemonic, with any free `account` of the same role.

## Backwards Compatibility

This standard defines a new tree, disjoint from the trees of [ERC-2333](./eip-2333.md) and of BIP-32 and SLIP-0010 for other curves. It changes no existing key. A mnemonic created for [ERC-2333](./eip-2333.md) can be reused as is.

## Reference Implementation

```python
import hashlib
import hmac

MASTER_KEY_DOMAIN = b"Ethereum PQ seed"
PQ_PURPOSE = 5326
COIN_TYPE = 3600
HARDENED_OFFSET = 2**31
ROLE_VALIDATOR = 0
ROLE_BUILDER = 1
XMSS_SEED_INFO = b"leanXMSS key"
VRF_SEED_INFO = b"VRF key"


def mnemonic_to_seed(mnemonic: str, passphrase: str = "") -> bytes:
    return hashlib.pbkdf2_hmac("sha512", mnemonic.encode(), ("mnemonic" + passphrase).encode(), 2048)


def derive_master_node(seed: bytes) -> tuple[bytes, bytes]:
    assert 16 <= len(seed) <= 64
    i = hmac.new(MASTER_KEY_DOMAIN, seed, hashlib.sha512).digest()
    return i[:32], i[32:]


def derive_child_node(key: bytes, chain_code: bytes, index: int) -> tuple[bytes, bytes]:
    assert 0 <= index < HARDENED_OFFSET
    data = b"\x00" + key + (index + HARDENED_OFFSET).to_bytes(4, "big")
    i = hmac.new(chain_code, data, hashlib.sha512).digest()
    return i[:32], i[32:]


def derive_account_seed(seed: bytes, role: int, account: int) -> bytes:
    assert role in (ROLE_VALIDATOR, ROLE_BUILDER)
    key, chain_code = derive_master_node(seed)
    for index in (PQ_PURPOSE, COIN_TYPE, role, account):
        key, chain_code = derive_child_node(key, chain_code, index)
    return key


def hkdf_expand(prk: bytes, info: bytes, length: int) -> bytes:
    output, block, counter = b"", b"", 1
    while len(output) < length:
        block = hmac.new(prk, block + info + bytes([counter]), hashlib.sha256).digest()
        output += block
        counter += 1
    return output[:length]


def derive_xmss_seed(account_seed: bytes) -> bytes:
    return hkdf_expand(account_seed, XMSS_SEED_INFO, 32)


def derive_vrf_seed(account_seed: bytes) -> bytes:
    return hkdf_expand(account_seed, VRF_SEED_INFO, 32)
```

## Security Considerations

### Independence from BLS keys

The only input shared with [ERC-2333](./eip-2333.md) keys is the root seed. Recovering a BLS secret key, for example with a quantum computer, reveals nothing about the tree of this standard. Implementations MUST NOT derive post-quantum seeds from a BLS secret key, or from any value that a published BLS public key reveals to a quantum adversary.

### Quantum security of the derivation

The derivation only uses HMAC-SHA512, HKDF with SHA-256, and PBKDF2 with HMAC-SHA512 for the mnemonic. Grover's algorithm at most halves their security level in bits. 256-bit keys and chain codes keep about 128 bits of security against a quantum adversary.

### Reuse of leanXMSS leaves

leanXMSS is stateful: a key that signs two different messages at the same leaf allows forgeries. The seed does not record which leaves a key has signed at. Restoring a key from its seed is safe, but signing with it requires the signing history of the key. A tool that cannot obtain that history MUST NOT sign with the restored key.

### Reuse across chains

A leanXMSS key that signs on two chains signs different messages at the same leaves, which allows forgeries. A VRF tree used on two chains gives away the randomness of one chain on the other. The keys of an account seed MUST NOT be used on more than one chain. A validator that runs on several chains MUST use a different mnemonic or a different account on each.

### Seed compromise

The root seed and the master node give access to every key of every account. Account seeds SHOULD be the only secrets given to signing infrastructure. Knowing an account seed reveals no other node of the tree.
