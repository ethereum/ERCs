## Abstract

This standard defines a common lifecycle for the authorities that authorize an [EIP-8141](./eip-8141.md) frame-transaction account: how an authority is added, rotated, and revoked. An authority (a signing key, or more generally an authorization predicate such as a spending lock or a limit) is a leaf in a per-account committed tree whose root is published as an [EIP-8272](./eip-8272.md) recent root. A transaction carries a membership proof for the acting authority and names the root it proves against; the account verifies the proof in a frame that runs the account's own code and withholds approval on failure. Add is a leaf insertion, rotate is a leaf replacement, and revoke is a leaf removal, each realized as a new committed root. The model requires no protocol change: it is expressed entirely with primitives EIP-8141 and EIP-8272 already provide.

## Motivation

Native account-abstraction designs let a transaction reach a target while the account is named as the caller, without running the account's own entry-point code. Any rule an account enforces only inside that entry point is therefore not consulted on such a path. The account must re-express the rule where authorization is decided.

EIP-8141 gives an account a frame that runs the account's own code on every transaction and can withhold approval. EIP-8272 lets a transaction name a recent commitment-tree root and have clients check the reference against pre-state before any frame runs; its own Motivation names "wallet authorization roots" as an intended use. What is missing is a shared meaning for the operations wallets perform on such a root: add, rotate, revoke. Without one, every account model defines these independently and wallets must reconcile all of them.

This standard fixes that meaning once. It is deliberately model-agnostic: it constrains what add, rotate, and revoke mean over a committed authority root, not which authenticator or account layout an implementation uses, so different account-abstraction families can share one lifecycle.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

Terms `FrameTx`, `VERIFY`, `SENDER`, frame modes, `APPROVE`, `TXPARAM`, `FRAMEDATALOAD`, and `RECENTROOTREFLOAD` have the meanings defined in EIP-8141 and EIP-8272. This standard applies to accounts with code; a codeless default account (EIP-8141) runs protocol-default behavior and has no authorizing code to carry the check.

### Authority tree

An account MUST associate its authorities with a single committed tree. Each leaf is an `authorization`:

```text
authorization = (authority_id, predicate)
```

- `authority_id` is a 32-byte stable handle for an authority slot or role. It is chosen at add time and is independent of the key material, so rotating the underlying key does not change it.
- `predicate` is the account-defined data the account's code evaluates: for example a public key, an authenticator address, a threshold, a spend ceiling, or an unlock time.

The leaf encoding MUST be a deterministic function of `(authority_id, predicate)`. Implementations SHOULD use `leaf = keccak256(authority_id || predicate)` so that independent tooling can reconstruct and index a tree without account-specific knowledge.

The tree root MUST be published as an EIP-8272 recent root under a `source_id` the account controls and is the sole writer for. The `source_id` a Tier-1 account accepts (below) is fixed in the account's code at deployment.

### Lifecycle operations

An account changes its authorities only by publishing a new root:

- **add**: insert a leaf for a new `authorization`, publish the new root.
- **rotate**: replace an existing `authority_id`'s `predicate` (for example bind a new key to the same slot), publish the new root.
- **revoke**: remove a leaf, publish the new root.

An operation takes effect when the new root becomes referenceable, one slot after it is written (EIP-8272).

### Proof carriage and check

The transaction MUST carry the membership proof for the acting `authorization` in frame-declared data, read with `FRAMEDATALOAD`, and MUST name the root it proves against as an EIP-8272 recent-root reference, read with `RECENTROOTREFLOAD`. The tree shape and proof format are account-defined; the root proven against MUST be an EIP-8272-referenced root, not a value read from mutable storage.

The authorization check MUST run in a frame that executes the account's own code (a `VERIFY` frame targeting the account, or a `SENDER` frame that self-`APPROVE`s) and MUST gate that frame's `APPROVE` of execution. Placing the check in a dispatched frame that targets another contract does not satisfy this requirement, because that frame does not run the account's code.

The account's code MUST NOT `APPROVE` execution unless the carried proof verifies for the acting `authorization` against an accepted root. Two conformance tiers are defined; an account MUST implement at least one.

- **Tier 1 (root-bound, mempool-cheap).** The check reads only the transaction-declared recent-root reference and frame-declared data. It accepts any recent root under the account's fixed `source_id` and grants approval only if the proof verifies against it. It MUST NOT read mutable account or external storage. Revocation latency is bounded by the EIP-8272 recency window (`RECENT_ROOT_USABLE_WINDOW`): a dropped leaf's earlier root stays referenceable until it leaves the window.

- **Tier 2 (floor-bound, instant revocation).** In addition to Tier 1, the check reads one account-owned monotonic value (a rotation-floor slot) with a single storage read and rejects any reference whose slot is below the floor. Raising the floor on rotate or revoke makes the change effective at the next block, at the cost of the mempool-cheap admission tier. A single-authority account MAY instead read its current authorized root directly, which is the degenerate case of the same rule.

The account MUST fail closed: if no accepted authorization is proven, the account's code MUST NOT `APPROVE`, and the transaction is invalid.

### Isolation

Authorization MUST be keyed by the account: an authority proven for one account MUST NOT authorize another. Because each account proves against its own subtree under its own `source_id`, revoking an authority affects only that account and does not invalidate authorities held by other accounts.

## Rationale

The ideal external keystore is no external keystore: placing the authority datum in the account's own committed tree, keyed by the account, removes cross-account invalidation. One account's rotation cannot invalidate another's pending transactions, because there is no shared authority whose change fans out.

This also resolves the apparent choice between an account header and a keystore. A header selects the authorizing code; the tree supplies which authority is authorized as proven data. A single-authority account can stay on the header alone; multi-signature and session-key accounts keep the tree. Neither is required to adopt the other.

Making `authority_id` a stable handle independent of key material lets rotate change the bound key while preserving the account's reference to that authority slot, which is what a key rotation is. Add, rotate, and revoke are expressed as root transitions rather than as protocol operations so the same lifecycle applies whether the authority is a key, a lock, or a limit. This lets an account enforce an execution-time invariant, such as a lock or a ceiling, at authorization time, on the direct-dispatch path where its entry-point code does not run.

The two tiers make the revocation-latency trade-off explicit rather than hidden. Tier 1 keeps the check free of mutable reads, so it fits a bounded public mempool, at the cost of revocation latency up to the recency window. Tier 2 buys next-block revocation with one mutable read, moving admission to the tier that permits it. Both keep invalidation account-bounded.

### General principle

The split into two tiers is not arbitrary. The cost of an authorization check is set by how much mutable state it reads. Tier 1 reads nothing beyond its carried proof and a committed root, so it is admissible to a bounded public mempool. Tier 2 reads one account-owned monotonic value, so it moves to the admission tier that permits a mutable read. A check that would depend on live external state gains no tier here; it is outside the mempool-cheap path by construction.

The same rule applies to every input a check consumes, not only to the acting authority. Where a dependency can be committed ahead of time, an account SHOULD carry it as a proof rather than read it at authorization. A sponsor authority, for example, is proven as a leaf in the sponsor's own committed root and carried in frame-declared data, instead of read from the sponsor's live account. Carrying it keeps the check within Tier 1 and keeps invalidation account-bounded on the sponsor side as well. Only a dependency that is genuinely live and cannot be pre-committed stays outside the cheap path.

## Backwards Compatibility

This standard adds no transaction type, opcode, or consensus rule. It is a convention over EIP-8141 and EIP-8272 primitives. Accounts that do not adopt it are unaffected. An account that adopts it is authorized exactly as before on any path that runs its authorizing code.

## Security Considerations

- **Opt-in.** The protection exists only for accounts whose authorizing code performs the check. An account that does not is not protected on the direct-dispatch path. This is inherent to any account-defined authorization and is not specific to this standard.
- **Revocation latency (Tier 1).** Under Tier 1 a revoked authority stays provable until its last authorizing root leaves the EIP-8272 recency window. Accounts that require prompt revocation MUST use Tier 2.
- **Root-source liveness.** If the account's root source stops publishing, the authority set freezes at the last root and, once it ages out of the window, references fail closed. Accounts SHOULD provide a fallback authority path.
- **Cross-chain rotation is not atomic.** An authority rotated on one chain remains usable on another until that chain's root is updated. This is a property shared by any cross-chain shared-authority design and is not resolved here.
- **Keyed nonces do not bypass the check.** Under [EIP-8250](./eip-8250.md) each frame still runs the account's authorizing code, so choosing a different nonce domain does not skip authorization.
