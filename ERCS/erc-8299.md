## Abstract

This ERC defines a triple-hash commitment scheme and an [EIP-712](./eip-712.md) attestation profile for proving that the input an artificial intelligence (AI) model received is the input the user submitted, transformed only by a declared, public specification. It introduces three linked values — `raw_input_hash`, `sanitization_pipeline_hash`, and `input_hash` — that together form a verifiable chain of custody for AI inference inputs. A verifier holding the raw input can confirm input integrity from the committed hashes and the public sanitization specification, without trusting the agent, gateway, or execution environment. This standard occupies the input-provenance layer of the AI inference trust stack, complementing [ERC-8004](./eip-8004.md) (agent identity) and [ERC-8126](./eip-8126.md) (agent verification).

## Motivation

On-chain AI agent systems built on standards such as ERC-8004 and ERC-8126 can establish which agent is registered and whether it is considered trustworthy, and proof-verification layers can attest which model ran and what output was produced. No standard defines how to commit to the *input* before inference. This creates a trust gap: an agent may sanitize, rewrite, or substitute the user's input between request submission and model execution, leaving no evidence of the transformation.

ERC-8126 (AI Agent Verification) addresses the question "Is this agent trustworthy?" through risk scores and verification registries. It does not record what the agent actually processed in a specific invocation. WYRIWE (What You Read Is What You Execute) fills that gap.

Without a committed input record:

- A settlement contract cannot verify that the delivered output corresponds to the funded input.
- A proof verifier cannot confirm that the `inputHash` it receives matches what was originally requested.
- A commit-reveal dispute mechanism has no ground truth for what the model was actually asked to do.

WYRIWE closes this gap with a minimal, hash-based commitment that a compliant gateway produces at execution time and that any verifier can check independently.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### 1. Triple-Hash Construction

A WYRIWE-compliant execution MUST produce the following three values:

```
raw_input_hash             = keccak256(raw_user_input)
sanitization_pipeline_hash = keccak256(utf8(sanitization_spec_uri) || raw_input_hash)
input_hash                 = keccak256(sanitized_input)
```

Where:

- `raw_user_input` is the exact bytes of the user's input as received, before any transformation.
- `sanitization_spec_uri` is the full InterPlanetary File System (IPFS) Uniform Resource Identifier (URI) of the sanitization specification, including the `ipfs://` scheme prefix (for example `ipfs://Qmccvom6aRVgZ2dtFWvT6Wm3DmTvoAUHHotK7uQufnStVR`). `utf8(...)` is its UTF-8 encoding. The `ipfs://` prefix is part of the preimage.
- `raw_input_hash` in the second line is the 32-byte value from the first line.
- `sanitized_input` is the exact bytes fed to the model after applying the sanitization specification to `raw_user_input`.
- `||` denotes byte concatenation.

`sanitization_pipeline_hash` binds the specification to this specific raw input, so a pipeline commitment cannot be replayed against a different input.

### 2. Identity Transform

When no sanitization is applied, the identity-transform specification MUST be used, and the following MUST hold:

```
sanitization_spec_uri      = IDENTITY_SENTINEL_CID
sanitization_pipeline_hash = keccak256(utf8(IDENTITY_SENTINEL_CID) || raw_input_hash)
input_hash                 = raw_input_hash
```

where:

```
IDENTITY_SENTINEL_CID = "ipfs://Qmccvom6aRVgZ2dtFWvT6Wm3DmTvoAUHHotK7uQufnStVR"
```

`sanitization_pipeline_hash` MUST NOT be omitted or zero-valued in the identity case.

#### 2.1 Identity-Transform Specification

The content identified by `IDENTITY_SENTINEL_CID` is normative and frozen. It is the following 760 bytes: the UTF-8 encoding of the JSON text below, with two-space indentation and LF line endings exactly as shown, followed by one trailing LF.

```json
{
  "name": "identity-transform",
  "version": "1",
  "description": "The identity sanitization pipeline. No modification is applied to the input. The sanitized output is identical to the raw input byte-for-byte.",
  "transform": "none",
  "input": "raw_user_input (bytes, unmodified)",
  "output": "raw_user_input (bytes, identical to input)",
  "invariants": [
    "sanitized_input == raw_user_input",
    "input_hash == raw_input_hash",
    "sanitization_pipeline_hash == keccak256(IDENTITY_SENTINEL_CID_bytes || raw_input_hash)"
  ],
  "notes": "Use this CID when no sanitization is applied. The input_hash == raw_input_hash equality is a provable on-chain claim. Implementations MUST NOT substitute any other CID to represent the no-sanitization case."
}
```

The content identifier (CID) is a version-0 CID computed the way `ipfs add` computes it for a file of this size with default settings: the bytes are wrapped in a single UnixFS `File` node (no chunking, since the content is smaller than the default 262144-byte chunk) inside a DAG-PB node, the node is hashed with SHA2-256, and the multihash is encoded in base58btc. A verifier holding these 760 bytes MUST obtain `Qmccvom6aRVgZ2dtFWvT6Wm3DmTvoAUHHotK7uQufnStVR`. Implementations SHOULD pin this CID.

### 3. WyriweAttestation Struct

A WYRIWE attestation is an EIP-712 typed structured data record with the following fields:

```solidity
struct WyriweAttestation {
    bytes32 agentId;                    // ERC-8004 agent identity anchor
    address registry;                   // ERC-8004 identity registry address
    bytes32 modelHash;                  // commitment to the model that ran
    bytes32 rawInputHash;               // raw_input_hash
    bytes32 sanitizationPipelineHash;   // sanitization_pipeline_hash
    bytes32 inputHash;                  // input_hash
    bytes32 outputHash;                 // keccak256(model_output)
    bytes32 commitmentHash;             // see below
    uint256 timestamp;                  // Unix time in seconds at which the attestation was signed
}
```

All fields are REQUIRED and MUST be populated.

- `agentId` is the ERC-8004 registry identity anchor — the identifier the registry assigns — not a hash of any human-readable name. When the ERC-8004 identity is a `uint256` registry id, `agentId` is its left-padded encoding `bytes32(uint256(id))` (for example, registry id `860` becomes `0x000…035c`). Deriving an identity from a human-readable name is out of scope for this ERC; an implementation that does so MUST declare the derivation, and an Ethereum Name Service (ENS) name SHOULD be mapped to its [ERC-137](./eip-137.md) namehash, never to `keccak256(utf8(name))`. Where the execution environment does not implement ERC-8004, `agentId` and `registry` MAY be zero.
- `modelHash` is a 32-byte commitment to the model or its manifest. The attestor MUST document how it is computed.
- `outputHash` is `keccak256(model_output)`, where `model_output` is the exact bytes the model returned.
- `commitmentHash` is `keccak256(abi.encode(agentId, modelHash, inputHash, outputHash, timestamp))`, with the five values encoded as `bytes32, bytes32, bytes32, bytes32, uint256`. It lets a verifier that holds only these five values check them against the signed record.

The canonical EIP-712 type string is:

```
WyriweAttestation(bytes32 agentId,address registry,bytes32 modelHash,bytes32 rawInputHash,bytes32 sanitizationPipelineHash,bytes32 inputHash,bytes32 outputHash,bytes32 commitmentHash,uint256 timestamp)
```

Field order is normative. A type string with fields in any other order produces a different type hash and MUST NOT be used.

### 4. EIP-712 Domain and Signature

The EIP-712 domain for WYRIWE attestations is:

```
EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)

name              = "WyriweAttestation"
version           = "1"
chainId           = the chain ID of the chain on which `registry` is deployed
verifyingContract = registry
```

Binding the domain to `registry` means a signature made for one registry does not verify against another. `chainId` MUST be the chain ID of the registry's chain, including when the attestation is signed off-chain.

The attestation is signed with the EIP-712 signing method (`eth_signTypedData` in EIP-712) over the digest `keccak256("\x19\x01" || domainSeparator || hashStruct(WyriweAttestation))`. The signature is 65 bytes, `r || s || v`, with `v` ∈ {27, 28} and `s` in the lower half of the secp256k1 curve order. A signature produced with `eth_sign` or `personal_sign`, which prefix the message with `"\x19Ethereum Signed Message:\n"`, MUST NOT be used.

The address that produces the signature is the **attestor**.

### 5. Verification Procedure

A verifier evaluating a WYRIWE attestation MUST perform the following checks and report one of three results: **verified**, **refuted**, or **unverifiable**.

1. Recompute the EIP-712 digest from the attestation fields and the domain in Section 4, recover the signer, and check that it equals an attestor the verifier accepts for this `agentId` and `registry`. Recovering *some* address is not sufficient: every well-formed signature recovers to an address.
2. Recompute `commitmentHash` from `agentId`, `modelHash`, `inputHash`, `outputHash` and `timestamp`, and check it equals the attested value.
3. If the raw input is available: check `rawInputHash == keccak256(raw_user_input)`.
4. If the raw input is available: obtain `sanitization_spec_uri` (from the gateway response in Section 6, or `IDENTITY_SENTINEL_CID` for the identity case), check `sanitizationPipelineHash == keccak256(utf8(sanitization_spec_uri) || rawInputHash)`, apply the specification to `raw_user_input`, and check that `keccak256` of the result equals `inputHash`. For the identity case this reduces to `inputHash == rawInputHash`.

The result is **refuted** if any check that was performed fails. It is **verified** if all four checks pass. If checks 1 and 2 pass but the raw input or the specification is not available, the result is **unverifiable** for input provenance: the attestor's signature over the hashes is authentic, but the chain from raw input to model input has not been checked. A verifier MUST NOT report an attestation as verified when checks 3 or 4 were skipped.

A sanitization specification is identified by content; this ERC defines the identity specification (Section 2.1) and does not define a format for other specifications. A gateway that uses another specification MUST publish it at its `sanitization_spec_uri` in a form that states its transform exactly enough for an independent verifier to reproduce `sanitized_input` from `raw_user_input`.

### 6. Gateway Query Interface

A compliant gateway MUST expose:

```
GET /agent/verify/:inputHash
```

where `:inputHash` is the `inputHash` as hexadecimal, with or without a `0x` prefix, case-insensitive. On success the response MUST be HTTP 200 with a JavaScript Object Notation (JSON) body:

```json
{
  "inputHash": "0x…",
  "attestations": [
    {
      "attestation": {
        "agentId": "0x…", "registry": "0x…", "modelHash": "0x…",
        "rawInputHash": "0x…", "sanitizationPipelineHash": "0x…", "inputHash": "0x…",
        "outputHash": "0x…", "commitmentHash": "0x…", "timestamp": "1790000000"
      },
      "domain": { "name": "WyriweAttestation", "version": "1", "chainId": 1, "verifyingContract": "0x…" },
      "signature": "0x…",
      "attestor": "0x…",
      "sanitizationSpecUri": "ipfs://…"
    }
  ]
}
```

`bytes32` and `address` values MUST be `0x`-prefixed hexadecimal; `timestamp` MUST be a decimal string; `chainId` MUST be a JSON number. `attestations` MUST list every attestation the gateway holds for that `inputHash`, newest first. The gateway MUST respond with HTTP 404 when it holds none.

A gateway SHOULD keep the content at every `sanitizationSpecUri` it returns retrievable, for example by pinning it, for as long as it serves attestations that reference it.

### 7. ClaimType Discriminator

Compliant claim artifacts MUST carry a `claimType` field identifying the accountability model of the claim. This field is distinct from `proofSystem` and MUST NOT be conflated with it:

- `proofSystem` belongs to the `IProofVerifier` contract path and has contract context. It identifies the cryptographic mechanism that authenticated the artifact.
- `claimType` belongs inside the signed artifact and travels without that context. It identifies the accountability and dispute model.

An off-chain consumer holding only the raw signed struct MUST be able to determine the accountability model without a registry lookup.

```solidity
enum ClaimType {
    ReExecution,  // deterministic computation — objectively disputable
    Attestation,  // authorized signer certifies a result
    Judgment      // subjective assessment — accountable through track record / policy
}
```

The fields answer different questions:

- `proofSystem` answers: what cryptographic mechanism authenticated the artifact?
- `claimType` answers: what kind of accountability model backs the claim?

| `claimType` | `proofSystem` examples | Accountability | Dispute surface |
|---|---|---|---|
| `ReExecution` | `zk/sp1`, `zk/ezkl`, `op/ora` | Mathematical / economic | Objectively disputable |
| `Attestation` | `attestation/wyriwe`, `attestation/multisig` | Signer authorization / stake / reputation | Signer registry or policy |
| `Judgment` | `attestation/judgment` | Track record / reputation / policy-defined stake | Pre-outcome commitment and later outcome evidence |

A `WyriweAttestation` is an `Attestation`-class claim. A proof verifier for WYRIWE attestations SHOULD report `proofSystem() = "attestation/wyriwe"`.

### 8. Consumer Requirements

A settlement contract or other consumer that acts on WYRIWE attestations MUST enforce its own replay protection, for example by recording consumed `inputHash` or `commitmentHash` values. `timestamp` records when the attestation was signed and does not prevent replay.

## Rationale

### Why three hashes?

Two hashes (raw and final) prove that the input was transformed but not *which* transformation was applied. `sanitization_pipeline_hash` commits to both the specification and the raw input, making the transform auditable and reproducible by any third party.

### Why content-addressed specifications?

A content-addressed reference ensures the specification retrieved at verification time is the one applied at execution time. A mutable URL would let the specification be swapped after the fact, defeating the commitment.

### Why EIP-712, and why bind the domain to the registry?

EIP-712 signatures are verifiable on-chain and by existing wallet tooling, and the structured hash is deterministic. Using the ERC-8004 registry as `verifyingContract` scopes each signature to one registry on one chain without an extra field.

### Why include `agentId`, `registry` and `commitmentHash`?

Linking attestations to an ERC-8004 identity makes them attributable to a registered agent, not only to a signing key, which settlement systems such as [ERC-8183](./eip-8183.md) need. `commitmentHash` gives an on-chain verifier a single value that binds the agent, model, input, output and time, so it can be recorded or compared without the full struct.

### Why an identity specification instead of a null value?

A null or zero `sanitization_pipeline_hash` would make it ambiguous whether the field was omitted or a transform was applied but not committed. The identity specification makes the no-sanitization case explicit and verifiable on equal footing with sanitized cases.

### Why check the attestor, not just the signature?

`ecrecover` returns an address for every well-formed signature. A verifier that only checks that the recovered address is non-zero accepts attestations signed by anyone. Section 5 therefore requires comparing the recovered signer with an attestor the verifier accepts.

### Relationship to ERC-8126

ERC-8126 defines risk scores and verification registries that answer "Is this agent trustworthy?" WYRIWE answers "What did this agent actually process in this invocation?" The two compose: a settlement contract may require both that the agent is verified under ERC-8126 and that the input commitment matches the funded request.

### Composition with Adjacent Layers

This subsection is informative. It describes integration patterns that reuse WYRIWE's chain-of-custody shape at other layers. None of them is required of a WYRIWE implementation.

**Settlement snapshots.** A mesh of gateways that settles contribution counts can commit to a snapshot the same way: `snapshotRoot = keccak256(abi.encode(rows))` over rows of `(address contributor, uint256 score, uint256 timestamp)` sorted by contributor, and `commitmentHash = keccak256(abi.encode(snapshotRoot, periodId, nodeAddress))`, submitted in a commit phase and checked against the revealed rows in a reveal phase. A node can only reveal rows whose hash matches its commitment.

**Judgment.** The same question exists one layer up for judgment validators: nothing in an input commitment binds "action reviewed" to "action executed after the verdict". The shape maps slot for slot:

| WYRIWE | Judgment (example) |
|---|---|
| `rawInputHash` — what the user submitted | `rawProposalHash` — what the agent proposed |
| `sanitizationPipelineHash` — public spec transforming raw → permitted | `verdictHash` — the verdict, including any conditions, transforming proposed → permitted |
| `inputHash` — what the model actually received | `executedActionHash` — what was actually executed |
| identity specification — no-sanitization is a provable claim | unconditional approval — executed-as-reviewed is a provable claim |

Authenticating that a validator signed a verdict for an exact input is the subject of the optional `attestation/judgment` profile of the proof-verification interface being specified in ERC-8274. One way to bind the reviewed action to the executed one is an EIP-712 record such as:

```solidity
struct JudgmentExecutionAttestation {
    bytes32 agentId;             // identity of the executing agent
    address registry;            // ERC-8004 registry
    bytes32 validatorId;         // identity of the judgment validator (zero for an off-registry
                                 // validator identified inside the verdict artifact)
    bytes32 rawProposalHash;     // hash of the proposed-action artifact, before review
    bytes32 verdictHash;         // hash binding the verdict to rawProposalHash
    bytes32 executedActionHash;  // hash of the executed-action record
    uint256 verdictTimestamp;    // verdict issuance (commit)
    uint256 executedTimestamp;   // execution (reveal)
    string  recordPointer;       // locator of the accountability record
}
```

committed when the verdict is issued and revealed after execution, so the executor can only reveal an action whose hash matches what was judged. In one production deployment, the verdict hash is the SHA-256 of the canonical JSON of a published, self-describing list of preimage fields, which includes the field that pins the proposal; consumers recompute it against the field list declared on each proof rather than a fixed set, because the list grows over time. Keeping commitment evidence and outcome evidence separately addressable lets a dispute check the commitment without seeing the outcome. Relay-published verdicts can be overwritten on some relays, so the time a verdict was first published is best taken from an on-chain commitment where one exists.

## Backwards Compatibility

This ERC introduces a new standard and does not modify any existing interface.

Implementations deployed before this revision used other EIP-712 domain names (for example `ERC8004AttestationGateway`) or other pipeline-hash constructions. Signatures and hashes produced that way do not verify under this ERC; such attestations need to be re-issued to be conformant.

### Case 4: Forgery

```
claimed raw_user_input = "transfer 100 ETH to attacker"
```

presented with the Case 3 attestation. Check 3 fails: `keccak256(claimed raw_user_input)` does not equal the attested `rawInputHash`, so the result is **refuted**. If the forger instead signs a new attestation over the claimed input with their own key, check 1 fails because the recovered signer is not an accepted attestor, and the result is again **refuted**.

## Reference Implementation

A TypeScript gateway implementation produces `WyriweAttestation` records as specified in Sections 1–4 for the identity case and serves them to peer gateways. A Solidity `IProofVerifier` implementation reports `proofSystem() = "attestation/wyriwe"` and verifies an attestation on-chain from `metadata = abi.encode(agentId, registry, attestor)` and `proof = abi.encode(modelHash, rawInputHash, sanitizationPipelineHash, commitmentHash, timestamp, signature)`: it recomputes `commitmentHash` (check 2), and requires the signature, under the domain in Section 4, to recover to `attestor` (check 1). Checks 3 and 4 need the raw input and are performed off-chain. Case 3 above verifies against this implementation.

## Security Considerations

### Attestor key compromise

An attestation is only as trustworthy as the attestor's key. Consumers that use WYRIWE attestations for settlement or dispute resolution should keep an on-chain record of accepted attestors and support key rotation. A compromised attestor key allows forged attestations, but a forged attestation still cannot make a different raw input hash to the committed `rawInputHash`.

### Signature checks that accept anyone

A verifier that checks only that a signature recovers to a non-zero address accepts attestations signed by any key, which defeats the scheme. The recovered signer has to be compared with an accepted attestor (Section 5, check 1). High-`s` signatures are malleated copies and are excluded by Section 4.

### Hash collision resistance

WYRIWE relies on the collision resistance of keccak256. No practical collision attack is known. If keccak256 were broken, all three hashes would be affected equally; the triple-hash construction adds no collision surface of its own.

### Adversarial sanitization specification

WYRIWE proves faithful application of a declared transform, not that the transform is benign. A gateway can publish a specification designed to rewrite inputs maliciously — for example to replace a transfer amount or destination — and still commit to applying it faithfully. The scheme makes the transform auditable and attributable, but the semantic safety of a specification is the consumer's responsibility. Consumers that accept arbitrary specification URIs should restrict them to an allow-list, and end users should read the specification before relying on a result.

### Specification availability

`sanitization_pipeline_hash` commits to a URI, not to retrievable content. If the content at a specification URI becomes unavailable, check 4 cannot be completed and the result is unverifiable. Section 6 asks gateways to keep referenced specifications retrievable. The identity specification is reproduced in full in Section 2.1 for this reason.

### Input availability

WYRIWE commits to hashes of the input, not to the input. Parties that need to reproduce verification have to retain the raw input themselves; without it, the strongest available result is unverifiable (Section 5). This ERC does not define an input storage or retrieval mechanism.

### Cross-chain and cross-registry replay

The EIP-712 domain binds `chainId` and the registry address, so a signature made for one registry or chain does not verify against another. Replay within the same domain is prevented by the consumer (Section 8).
