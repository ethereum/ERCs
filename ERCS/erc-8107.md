## Abstract

This ERC defines a Trust Registry in which agents, identified by ENS names, sign trust
attestations about one another, and [ERC-8001](./eip-8001.md) coordinators admit
participants by verifying a trust path from a chosen gatekeeper. It follows the OpenPGP
web of trust model. It specifies the [EIP-712](./eip-712.md) attestation format and its
signing authority, denial, the path verification algorithm, how ENS names map to
controllers and addresses, and identity gates for [ERC-8001](./eip-8001.md).

## Motivation

[ERC-8001](./eip-8001.md) defines primitives for multi-party agent coordination and
leaves reputation and trust to modules. This ERC is that module. Before coordinating,
agents need answers to:

1. **"Should I include this agent in my coordination?"** — Participant selection
2. **"Can I trust this agent's judgement about other agents?"** — Transitive trust
3. **"How do I update trust based on coordination outcomes?"** — Trust maintenance

### Why Web of Trust?

The web of trust, standardised for OpenPGP in [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html),
solves the bootstrap problem: establishing trust with unknown agents without a central
registrar.

| OpenPGP Concept | This Standard |
|---------------|---------------|
| Public key | ENS name |
| Key signing | Trust attestation |
| Owner trust levels | `TrustLevel` enum |
| Key validity | Agent validity for coordination |
| Certification path | Trust chain through agents |

This standard adopts OpenPGP's trust levels and certification paths but not its validity
calculation (see [Divergence from OpenPGP](#divergence-from-openpgp)).

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Trust Levels

Implementations MUST use the canonical enum:

```solidity
enum TrustLevel {
   Unknown,   // 0: No trust relationship established
   None,      // 1: Endorsement withdrawn
   Marginal,  // 2: Partial trust — accepted on an edge when minEdgeTrust <= Marginal
   Full       // 3: Complete trust — satisfies any minEdgeTrust
}
```

| Level | Meaning | Validation Contribution |
|-------|---------|------------------------|
| `Unknown` | Default state; no data about agent | Cannot contribute to validation |
| `None` | The trustor has withdrawn its endorsement | Voids an edge whose effective level it is. Does not affect paths that do not use that edge |
| `Marginal` | Agent generally trustworthy | Contributes to validation when `minEdgeTrust <= Marginal` |
| `Full` | Agent's judgement equals own verification | Always contributes to validation |

`Marginal` and `Full` are reached only by a valid attestation with a higher nonce, and
`None` only by `revokeTrust` or `revokeTrustBatch`. `Unknown` is the default and cannot be
reassigned: a relationship, once created, is never removed from storage. Withdrawal is not
permanent: a later attestation with a higher nonce restores trust from `None`.

### Denial

The registry represents three distinct intentions of a trustor `A` towards a trustee `B`
in a scope `s`:

| Intention | Meaning | Operation |
|-----------|---------|-----------|
| Endorsement | `A` trusts `B` | `setTrust`, `setTrustBatch` (level `Marginal` or `Full`) |
| Withdrawal | `A` no longer endorses `B` itself | `revokeTrust`, `revokeTrustBatch` (level `None`) |
| Denial | `A` refuses to rely on `B`, even when other agents endorse `B` | `setDenial`, cleared by `clearDenial` |

Each trust record holds a boolean **denial flag** alongside its level, and the two are
independent:

* `setTrust`, `setTrustBatch`, `revokeTrust` and `revokeTrustBatch` MUST NOT change the
  denial flag
* `setDenial` and `clearDenial` MUST NOT change the level, the expiry, or any other
  stored part of the record

Denial is not subject to scope fallback. Writing `Deny(A, B, s)` for the flag stored at
scope `s`, the **effective denial** in scope `s` is:

```text
EffectiveDeny(A, B, s) = Deny(A, B, bytes32(0)) ∨ Deny(A, B, s)
```

A scoped flag that is `false` never overrides a universal flag that is `true`. Path
verification applies effective denial to every edge and, from the validator, to every
later node on the path (see [`verifyPath`](#verifypath)).

Clearing a denial reveals the stored endorsement exactly as it stands: `Full` or
`Marginal` applies again, `None` and `Unknown` still void the edge, and a scoped denial
still applies after a universal one is cleared. An attestation submitted while a denial
is in force updates the stored endorsement but does not clear the denial.

### ENS Integration

The Trust Registry uses ENS namehashes ([ERC-137](./eip-137.md)) as agent identifiers. It
requires an ENS registry; on Ethereum mainnet, the canonical deployment. Implementations
also take the network's NameWrapper address, or the zero address where no NameWrapper is
deployed.

The registry reads three external contracts:

```solidity
interface IENS {
   function owner(bytes32 node) external view returns (address);
   function resolver(bytes32 node) external view returns (address);
   function isApprovedForAll(address owner, address operator) external view returns (bool);
}

/// @dev NameWrapper is an ERC-1155; the token holder is the real name controller
interface INameWrapper {
   function ownerOf(uint256 id) external view returns (address);
   function isApprovedForAll(address owner, address operator) external view returns (bool);
}

interface IAddrResolver {
   function addr(bytes32 node) external view returns (address payable);
}
```

#### Name Controller Resolution

For a wrapped name, `ens.owner(node)` returns the NameWrapper contract, not the party
that controls the name (see [Why Unwrap NameWrapper Names?](#why-unwrap-namewrapper-names)).
Implementations MUST resolve the controller as follows:

```solidity
function controllerOf(bytes32 node) internal view returns (address) {
   address owner = ens.owner(node);
   if (owner == address(0)) return address(0);

   // Wrapped name: the ERC-1155 holder is the real controller
   if (nameWrapper != address(0) && owner == nameWrapper) {
      try INameWrapper(nameWrapper).ownerOf(uint256(node)) returns (address wrapped) {
         return wrapped; // see Wrapped Name Lifecycle
      } catch {
         return address(0);
      }
   }

   return owner;
}
```

Wherever this standard refers to "the ENS name owner", it means `controllerOf(node)`.
Authority follows ownership as the registry and the NameWrapper report it: `controllerOf`
does not consult `canModifyName`, fuses, or the `.eth` registrar's expiry.

The NameWrapper keeps a set of *fuses* for each wrapped name: permission flags that, once
burned, cannot be unburned until the name's NameWrapper expiry passes. Burning
`PARENT_CANNOT_CONTROL` on a subname *emancipates* it, so its parent can no longer replace
or unwrap it.

Implementations MUST pin the `nameWrapper` address at deployment, and MUST NOT allow it
to be changed afterwards (see [Why Pin the NameWrapper?](#why-pin-the-namewrapper)).
Implementations deployed on networks with no NameWrapper deployment MUST set
`nameWrapper` to the zero address, which disables unwrapping.

#### Wrapped Name Lifecycle

The NameWrapper's `ownerOf` reports a holder until the name's NameWrapper expiry has
passed. After that all fuses reset, and `ownerOf` returns the zero address only if
`PARENT_CANNOT_CONTROL` was burned:

| Name | Before NameWrapper expiry | After NameWrapper expiry |
|------|---------------------------|--------------------------|
| Wrapped `.eth` second-level name | holder, including during the 90-day grace period | zero address |
| Emancipated subname (`PARENT_CANNOT_CONTROL` burned) | holder | zero address |
| Unemancipated wrapped subname | holder | holder; fuses reset |

An unwrapped name has no NameWrapper expiry: `controllerOf` returns its registry owner
before and after the registrar expiry (see [Expired Unwrapped Names](#expired-unwrapped-names)).

For a wrapped `.eth` second-level name, the NameWrapper expiry is the registrar expiry
plus the 90-day grace period when the name is wrapped, and a renewal through
`NameWrapper.renew` normally sets it again. A renewal through the BaseRegistrar's `renew`
extends only the registrar expiry, so the holder loses control when the old NameWrapper
expiry passes, although the name is still registered and no one else can register it. A
later renewal through the NameWrapper restores the same holder. Neither kind of renewal
emits a NameWrapper event, so whether a wrapped name has a controller is read from state
(`controllerOf`, or the NameWrapper expiry from `getData`). Where this standard refers to
the end of a wrapped name's grace period, it means its NameWrapper expiry.

During the 90 days before its NameWrapper expiry, the NameWrapper refuses every
management operation on a wrapped `.eth` second-level name (`canModifyName` returns
false), but `ownerOf` still returns the holder, who keeps every power this standard
grants. Emancipated subnames have no grace period. An unemancipated subname never loses
its holder through expiry, and its parent can reassign it at any time (see
[Parent-Controlled Subnames](#parent-controlled-subnames)).

##### Re-registration

An unrenewed name passes to its next registrant with every record it set. The next
registrant inherits every attestation naming the name as trustee and can endorse from it
at once, so a path from an earlier trustor through the name reaches anyone the new
registrant endorses. An expiry on the name's own endorsements does not bound such a path;
only the attestation pointing to the name does.

The contract accepts every attestation that passes `setTrust`, whatever the state of its
names' registrations. The recommendations below guide signers and coordinators, and do
not change what the contract accepts or what the path-validation functions return.

Trustors:

* A trustor that is a `.eth` second-level name and signs or sets an endorsement after its
  registrar expiry SHOULD give it an `expiry` no later than the end of its grace period,
  and SHOULD issue it again after renewing.
* A trustor endorsing a `.eth` second-level name SHOULD give the attestation an `expiry`
  no later than the end of the trustee's grace period, and SHOULD issue it again after the
  trustee renews. An attestation signed before the trustee's registrar expiry, with the
  90-day maximum recommended under [Identity Continuity](#identity-continuity), already
  meets this.
* A trustor endorsing an emancipated subname SHOULD give the attestation an `expiry` no
  later than the subname's NameWrapper expiry, after which the parent can create the
  subname again for another holder.
* A trustor SHOULD watch its trustees' registrations as well as their expiries.

The **continuity check** decides whether the names an attestation involves have been
registered again since it was stored. For each attestation a path uses, take its
`TrustSet` event: the latest `TrustSet` for the record the path uses, that is the
trustor, trustee and scope that [scope fallback](#scope-fallback-semantics) selects for the
validation scope, not the latest record for the pair in any scope. The attestation ends
at the first of the following that comes after that event, for its trustor or its
trustee:

* For a `.eth` second-level name, or a name below one, a BaseRegistrar `NameRegistered`
  event for the second-level name's label
* For a name below a `.eth` second-level name, a NameWrapper `NameWrapped` event for that
  name or for any ancestor of it below the second-level name

`NameRenewed` never ends an attestation, however many renewals follow, and a later
`nameExpires` alone does not show a renewal, because a registration after the grace period
also produces one. A registration by the same holder also ends the attestation, which the
trustor then issues again. The NameWrapper emits `NameWrapped` whenever a name becomes
wrapped, including when a parent creates an emancipated subname again after its
NameWrapper expiry, or a holder unwraps its subname and wraps it again. It does not emit it
when a parent reassigns a subname that still has a holder, which is a change of control.
The check concerns registration, not control: a transfer within one registration emits
neither event (see [Monitoring Control Changes](#monitoring-control-changes)). Events are
ordered by block number, transaction index and log index, not by block timestamp, because
events in the same block share a timestamp. Both events are indexed, by labelhash and by
node, so the check needs the name, checked against the node.

The **liveness check** applies to a wrapped trustor: does the name have a controller now?
The coordinator reads `controllerOf(node)` (in practice the NameWrapper's `ownerOf`) or
the NameWrapper expiry (`getData(node)`). A `NameRenewed` event is not evidence of
liveness, since a renewal that bypasses the NameWrapper emits it without extending the
NameWrapper expiry.

Coordinators:

* A coordinator SHOULD apply the continuity check to every attestation on the paths it
  relies on whose trustor or trustee is a `.eth` second-level name or a name below one,
  whenever the attestation was issued, and SHOULD treat an attestation the check has ended
  as ineligible. A coordinator that cannot establish the name, or every relevant event from
  the `TrustSet` event to the block at which it decides, SHOULD NOT rely on the attestation.
* A coordinator SHOULD apply the liveness check, when it makes its decision, to every
  wrapped trustor on the path, whenever its endorsement was issued, and SHOULD NOT rely on
  an endorsement while its trustor has no controller.
* A coordinator SHOULD validate such paths with `enforceExpiry` set. A coordinator that
  relies on an endorsement issued after its trustor's registrar expiry SHOULD also monitor
  the trustor's control, its registrar expiry and, for a wrapped trustor, its NameWrapper
  expiry, and re-evaluate its gates when control changes.

#### Agent Address Resolution

[ERC-8001](./eip-8001.md) identifies participants by address, while this registry
identifies agents by ENS namehash. The binding between the two is the node's forward
address record ([ERC-137](./eip-137.md)):

```solidity
/// @dev Gas forwarded to a node's resolver, chosen at deployment
uint256 internal immutable resolveGas;

function resolveAgent(bytes32 node) public view returns (address) {
   address resolver = ens.resolver(node);
   if (resolver == address(0)) return address(0);

   // Low-level, gas-capped, bounded-copy call: a hostile resolver can neither make
   // resolution revert nor consume more than resolveGas
   bytes memory data = abi.encodeWithSelector(IAddrResolver.addr.selector, node);
   uint256 gasBound = resolveGas;
   bool ok;
   uint256 word;
   uint256 size;
   assembly ("memory-safe") {
      ok := staticcall(gasBound, resolver, add(data, 0x20), mload(data), 0, 0x20)
      size := returndatasize()
      word := mload(0)
   }
   if (!ok || size < 0x20 || word >> 160 != 0) return address(0);
   return address(uint160(word));
}
```

An address `a` is bound to node `n` if and only if `resolveAgent(n) == a` and
`a != address(0)`. Callers supply the node as the last element of a `TrustPath`, and the
registry confirms that it resolves to the participant. This standard does not use reverse
resolution.

ENS does not clear the `addr` record when a name expires or is re-registered, so it can
keep naming a previous holder's address. `validateParticipantAddress` therefore also
requires the node to have a controller, which covers a wrapped name nobody controls but
not a re-registered one (see [Resolver Trust](#resolver-trust)).

`resolveAgent` MUST NOT revert because of the resolver's behaviour. It MUST return the
zero address when the node has no resolver, or when the call to `addr` reverts, runs out
of gas, returns fewer than 32 bytes, or returns a first word with any of its upper 96
bits set. Return data beyond the first 32 bytes MUST be ignored. Implementations MUST
bound the gas forwarded to the resolver. The bound is chosen by the implementation; the
reference implementation takes it as a constructor argument, and its tests use 50,000
(see [Why Does Resolution Cap Gas and Never Revert?](#why-does-resolution-cap-gas-and-never-revert)).
Callers that validate many participants in one call SHOULD budget for that bound on each
participant.

This standard does not support resolution through CCIP-Read ([ERC-3668](./eip-3668.md))
during on-chain validation: an off-chain resolver's `addr` reverts, and `resolveAgent`
returns the zero address. Agents that need to pass on-chain identity gates MUST publish an
on-chain `addr` record, served by a resolver that answers `addr` within the gas bound.

#### Identity Continuity

The ENS name, not the key behind it, is the identity. When control of a name changes, the
new controller inherits every attestation naming it as trustee, gains authority over every
attestation and denial in which it is the trustor, and takes over any gatekeeper or anchor
role the name has in a gate. The gate configuration does not change. Attestations the
old controller signed but did not submit fail after the transfer, and become submittable
again if control returns to the signer while their nonces are unused.

* Coordinators SHOULD monitor control changes for the gatekeeper and anchor nodes of their
  gates, and SHOULD re-evaluate the affected gates when one occurs (see
  [Gatekeeper and Anchor Names](#gatekeeper-and-anchor-names)).
* Attestations covering high-stakes scopes SHOULD carry short expiries (RECOMMENDED: 90
  days maximum), so that a transfer cannot carry inherited trust forward indefinitely.
* Agents SHOULD monitor control changes on ENS names they trust, and re-evaluate trust
  when a trusted name changes hands. No single event reports every change of control (see
  [Monitoring Control Changes](#monitoring-control-changes)). After any relevant event,
  monitors are RECOMMENDED to re-check the name's `controllerOf`, its fuses and its expiry
  (for a wrapped name, its NameWrapper expiry from `getData` as well as its registrar
  expiry), rather than relying on any single event stream. Expiry emits no event, so a
  wrapped name also needs re-checking when its NameWrapper expiry passes.
* Agents SHOULD use wrapped `.eth` second-level names or emancipated subnames, whose
  authority ends when their NameWrapper expiry passes. Gatekeepers SHOULD prefer such
  names for gatekeeper and anchor nodes. An unwrapped name keeps its authority after it
  expires, and an unemancipated wrapped subname keeps it indefinitely.
* Coordinators SHOULD check whether a name is wrapped when they verify a path or gate,
  rather than rely on its status when an endorsement was issued. Unless `CANNOT_UNWRAP`
  is burned the holder can unwrap the name, and a name that lapses while wrapped may be
  registered again unwrapped. Fuses can also stop a name changing hands, at a long-term
  cost (see [Name Locking with Fuses](#name-locking-with-fuses)).
* Trustors SHOULD treat a subname whose parent can reassign it as no more trustworthy
  than its parent, and SHOULD prefer subnames with `PARENT_CANNOT_CONTROL` burned. This
  standard does not inspect fuses, so trustors and gatekeepers check them off-chain.

#### ENSv2 Migration

A name that migrates to ENSv2 can no longer act through this standard, while the
endorsements and denials it stored stay in force (see
[ENSv2 Compatibility and Migration](#ensv2-compatibility-and-migration)).

* Before migrating, agents SHOULD withdraw endorsements they may later need to withdraw,
  and set or clear denials so that the frozen state is the one they intend, and
  gatekeepers SHOULD reconfigure dependent gates.
* Protocols that issue agent subnames SHOULD NOT migrate the parent name while those
  subnames are in use with this standard.
* Coordinators SHOULD monitor migration of gatekeeper, anchor and participant names, and
  re-evaluate the affected gates. Applications using address-based validation SHOULD
  account for the loss or retention of legacy resolver records. For high-assurance
  coordination, time-limited attestations and explicit gate reconfiguration are
  RECOMMENDED.

### Signature Authority

Trust attestations MUST be signed by an address with signing authority for the ENS name.
Signing authority is limited to the name controller (`controllerOf(node)`) or, for a
contract controller, any signer the contract validates via [ERC-1271](./eip-1271.md).

"Approved operator" means an address for which `isApprovedForAll` returns true on
whichever contract holds the name, per `canSubmitRevocation`. A per-token approval
(`approve` on the NameWrapper or the `.eth` registrar) grants no authority under this
standard. An operator approval belongs to the holder that granted it, so it no longer
applies once the name changes hands.

| Operation | Controller | Approved operator | Any address |
|-----------|:----------:|:-----------------:|:-----------:|
| `setTrust`, `setTrustBatch` | signs | no | MAY submit a valid signature |
| `revokeTrust`, `revokeTrustBatch` | MAY call | MAY call | no |
| `setDenial`, `clearDenial` | MAY call | **MUST NOT** | no |
| `invalidateNonces` | MAY call | **MUST NOT** | no |
| `setIdentityGate`, `removeIdentityGate` | keyed by `msg.sender`; no ENS authority involved | | |

Approved operators MAY withdraw, because a withdrawal affects only the trustor's own
endorsement of one trustee, in the scopes named. They MUST NOT call `setDenial`,
`clearDenial` or `invalidateNonces` (see [Why Is Denial Controller-Only?](#why-is-denial-controller-only)
and [Why Is `invalidateNonces` Controller-Only?](#why-is-invalidatenonces-controller-only)).

These restrictions are only as strong as the ENS ownership model beneath them. An
operator approved through `isApprovedForAll` can change a name's registry owner, or
transfer its NameWrapper token unless `CANNOT_TRANSFER` is burned, and a per-token
approval on the `.eth` registrar can transfer or `reclaim` an unwrapped name. Such a party
can make itself the controller, or migrate the name to ENSv2. Trustors SHOULD grant
`isApprovedForAll`, and per-token approvals on the `.eth` registrar, only to parties they
would trust with control of the name. A per-token approval on the NameWrapper cannot
transfer the name, but lets its holder extend the expiry of the name's subnames, which
prolongs an emancipated subname holder's authority; if `CANNOT_APPROVE` is burned, it
also survives a transfer of the name.

Implementations MUST attempt ECDSA recovery before [ERC-1271](./eip-1271.md), and MUST
reject malleable (high-s) signatures. An EOA with an [EIP-7702](./eip-7702.md)
delegation has code, but its key still signs for it (see
[Why ECDSA Before ERC-1271?](#why-ecdsa-before-erc-1271)).

An [ERC-1271](./eip-1271.md) call that reverts, returns fewer than 32 bytes, or returns a
first word other than the magic value `0x1626ba7e` left-aligned with zero padding MUST be
treated as a failed signature, so `setTrust` reverts with `InvalidSignature` rather than
with the controller's revert data or an empty revert. The party that submits
a contract controller's attestations SHOULD simulate the submission before relaying it,
since the controller can consume all gas forwarded to `isValidSignature`.

```solidity
/// @dev Verify signature - signing authority is the name controller only
function verifySignature(
   bytes32 node,
   bytes32 digest,
   bytes calldata signature
) internal view returns (bool) {
   address controller = controllerOf(node);
   if (controller == address(0)) return false;

   // ECDSA first: covers plain EOAs and EIP-7702 delegated EOAs
   if (signature.length == 65) {
      bytes32 r = bytes32(signature[0:32]);
      bytes32 s = bytes32(signature[32:64]);
      uint8 v = uint8(signature[64]);
      // Reject malleable (high-s) signatures
      if (uint256(s) <= 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0) {
         address recovered = ecrecover(digest, v, r, s);
         if (recovered != address(0) && recovered == controller) return true;
      }
   }

   // ERC-1271 fallback for any controller with code. A low-level call, so that a
   // controller returning nothing fails as InvalidSignature, not with an empty revert
   if (controller.code.length == 0) return false;
   (bool ok, bytes memory ret) = controller.staticcall(
      abi.encodeWithSelector(bytes4(0x1626ba7e), digest, signature)
   );
   return ok && ret.length >= 32 && bytes32(ret) == bytes32(bytes4(0x1626ba7e));
}

/// @dev Check if caller can submit a revokeTrust transaction
function canSubmitRevocation(bytes32 node, address caller) internal view returns (bool) {
   address controller = controllerOf(node);
   if (controller == address(0)) return false;
   if (caller == controller) return true;

   // Approvals live on whichever contract actually holds the name
   if (nameWrapper != address(0) && ens.owner(node) == nameWrapper) {
      return INameWrapper(nameWrapper).isApprovedForAll(controller, caller);
   }

   return ens.isApprovedForAll(controller, caller);
}
```

### EIP-712 Domain

Implementations MUST use the following [EIP-712](./eip-712.md) domain:

```text
EIP712Domain(
   name: "TrustRegistry",
   version: "1",
   chainId: block.chainid,
   verifyingContract: address(this)
)
```

Implementations SHOULD expose the domain via [ERC-5267](./eip-5267.md).

### Primary Types

```solidity
struct TrustAttestation {
   bytes32 trustorNode;       // ENS namehash of trustor
   bytes32 trusteeNode;       // ENS namehash of trustee
   TrustLevel level;          // Trust level assigned
   bytes32 scope;             // Scope restriction; bytes32(0) = universal
   uint64 expiry;             // Unix timestamp; 0 = no expiry
   uint64 nonce;              // Per-trustor monotonic nonce
}

struct ValidationParams {
   uint8 maxPathLength;       // Maximum trust chain depth (1-10)
   TrustLevel minEdgeTrust;   // Minimum trust level required on each edge
   bytes32 scope;             // Scope to verify against; bytes32(0) = universal
   bool enforceExpiry;        // Check expiry on all chain elements
   bytes32[] requiredAnchors; // Path MUST traverse at least one anchor; empty = no requirement
}

struct TrustPath {
   bytes32[] nodes;           // [validator, ...intermediaries..., target]
}
```

Path length is the number of edges in the path. A direct trust relationship has path
length 1, and a path `[A, B, C]` has length 2.

#### Default Validation Parameters

When not specified, implementations SHOULD use:

```solidity
ValidationParams({
   maxPathLength: 5,
   minEdgeTrust: TrustLevel.Marginal,
   scope: bytes32(0),
   enforceExpiry: true,
   requiredAnchors: new bytes32[](0)
})
```

#### Validation Parameters Constraints

Implementations MUST reject `ValidationParams` where any of the following hold, checked
in this order:

| Condition | Error |
|-----------|-------|
| `maxPathLength == 0` or `maxPathLength > 10` | `InvalidMaxPathLength` |
| `minEdgeTrust == TrustLevel.Unknown` or `minEdgeTrust == TrustLevel.None` | `InvalidMinEdgeTrust` |
| `requiredAnchors.length > 10` | `TooManyRequiredAnchors` |

Both `verifyPath` and `setIdentityGate` MUST apply these constraints, through a shared
routine, before the parameters are used. The Gate Constraints below are not part of that
routine.

#### Gate Constraints

`setIdentityGate` MUST also reject the following parameters, which no path can satisfy:

| Condition | Error |
|-----------|-------|
| `requiredAnchors.length > 0` and `maxPathLength < 2` | `UnsatisfiableAnchors` |

Only intermediary nodes satisfy an anchor (see [`verifyPath`](#verifypath)), and a path of
one edge has none. `verifyPath` MUST NOT apply this check: given these parameters
directly, it returns `false`, as it does for any path that misses its anchors. Other
unsatisfiable configurations, such as a gate whose only anchor is its own gatekeeper, are
accepted and reject every participant.

### Typed Data Hashes

```solidity
bytes32 constant TRUST_ATTESTATION_TYPEHASH = keccak256(
   "TrustAttestation(bytes32 trustorNode,bytes32 trusteeNode,uint8 level,bytes32 scope,uint64 expiry,uint64 nonce)"
);

function _structHash(TrustAttestation calldata att) internal pure returns (bytes32) {
   return keccak256(abi.encode(
      TRUST_ATTESTATION_TYPEHASH,
      att.trustorNode,
      att.trusteeNode,
      uint8(att.level),
      att.scope,
      att.expiry,
      att.nonce
   ));
}
```

The signed digest is the [EIP-712](./eip-712.md) typed data hash of `_structHash(att)`
under the domain above.

### Interface

Implementations MUST expose the following interface:

### Interface Detection

Implementations MUST implement [ERC-165](./eip-165.md) and MUST return `true` from
`supportsInterface` for:

| Interface | Identifier |
|-----------|------------|
| `IERC165` | `0x01ffc9a7` |
| `ITrustRegistry` | `0x94f0ee34` |

`ITrustRegistry`'s identifier is the XOR of the selectors of its seventeen functions,
excluding the inherited `supportsInterface`.

### Semantics

Each function below lists its revert conditions in order. Implementations MUST evaluate
them in the order listed and MUST revert with the error given for the first condition that
applies.

#### `setTrust`

`setTrust` MUST revert if any of the following hold:

1. `attestation.trustorNode == attestation.trusteeNode`: `SelfTrustProhibited`
2. `attestation.level` is `Unknown` or `None` (withdrawal is expressed by revocation, not
   attestation): `InvalidAttestationLevel`
3. `attestation.expiry != 0 && attestation.expiry <= block.timestamp`:
   `AttestationExpired`
4. `ens.owner(attestation.trustorNode)` is the zero address: `ENSNameNotFound`
5. `attestation.nonce <= getNonce(attestation.trustorNode)`: `NonceTooLow`
6. `attestation.nonce` exceeds `getNonce(attestation.trustorNode) + 2**32`, with the same
   overflow-safe bound as `invalidateNonces`: `NonceJumpTooLarge(attestation.nonce, bound)`
7. The signature does not verify per [Signature Authority](#signature-authority),
   including when `controllerOf` returns the zero address, as it does for a wrapped
   `.eth` name past its NameWrapper expiry: `InvalidSignature`

Otherwise:

* The trust level and expiry MUST be stored, keyed by `(trustorNode, trusteeNode, scope)`
* The denial flag for that key MUST NOT change
* `getNonce(trustorNode)` MUST return the attestation's nonce
* `TrustSet` MUST be emitted

An attestation is accepted while the trustee is denied. It updates the stored
endorsement, which takes effect only when the denial is cleared.

#### `setTrustBatch`

`setTrustBatch` MUST revert if any of the following hold:

1. `attestations.length != signatures.length`: `BatchLengthMismatch`
2. `attestations` is empty: `EmptyBatch`
3. Any attestation has a different `trustorNode` than the first: `BatchTrustorMismatch`
4. Nonces within the batch are not strictly increasing: `BatchNonceNotIncreasing`
5. Any attestation, taken in order, meets a `setTrust` revert condition: that condition's
   error

Otherwise each attestation MUST be applied as `setTrust` would apply it.

#### `revokeTrust`

`revokeTrust` withdraws the trustor's endorsement. It MUST revert with `NotAuthorized` if
the caller is not the name controller or an approved operator for `trustorNode`.
Otherwise:

* Trust level MUST be set to `None`
* The stored expiry MUST be set to `0`, so `getTrust` returns `(None, 0)` for every
  revoked record
* The denial flag MUST NOT change
* `TrustRevoked` MUST be emitted
* The relationship MUST remain in storage (not deleted) to preserve the withdrawal

A prior trust relationship is not required. A trustor MAY withdraw in a scope it never
granted, which blocks the universal fallback in that scope. Callers that want to
distinguish withdrawing an existing endorsement from such a preemptive withdrawal MUST read
`getTrust` first; the registry does not make that distinction.

A withdrawal at `bytes32(0)` voids the trustor's edge to the trustee in every scope; one in
any other scope affects that scope only. Only the named record is written, and the
override is applied during path verification (see
[Scope Fallback Semantics](#scope-fallback-semantics)).

Withdrawal removes an edge and nothing else: paths through other agents that still
endorse the trustee remain valid, including paths the trustor evaluates as validator,
whatever the reason code. A trustor that refuses to rely on the trustee at all MUST use
`setDenial`. Withdrawal does not invalidate attestations the trustor has signed but not
yet submitted (see [`invalidateNonces`](#invalidatenonces)).

#### `revokeTrustBatch`

`revokeTrustBatch` applies `revokeTrust` to several scopes for the same
`(trustorNode, trusteeNode)` pair. It MUST revert if any of the following hold:

1. The caller is not the name controller or an approved operator for `trustorNode`:
   `NotAuthorized`
2. `scopes` is empty: `EmptyScopeList`

Otherwise each listed scope MUST be updated as `revokeTrust` would update it, with one
`TrustRevoked` event per scope. Implementations MUST NOT enumerate scopes on-chain;
callers derive the list from `TrustSet` logs.

#### `setDenial`

`setDenial` denies `trusteeNode` within the trustor's decisions in `scope`. It MUST revert
if any of the following hold:

1. The caller is not the name controller for `trustorNode`, including when `controllerOf`
   is the zero address: `NotAuthorized`
2. `trustorNode == trusteeNode`: `SelfTrustProhibited`

If the stored flag is `false`:

* The stored flag for `(trustorNode, trusteeNode, scope)` MUST be set to `true`
* The trust level, expiry and every other stored part of the record MUST NOT change
* `DenialSet` MUST be emitted with `denied = true`

If the stored flag is already `true`, `setDenial` MUST succeed without changing storage
and MUST NOT emit `DenialSet`. `setDenial` takes no nonce, so other activity on the
trustor's name never blocks it. A trustor MAY deny an agent it never endorsed. A
universal denial applies in every scope, and no scoped flag can lift it. Denial has no
expiry; it holds until the controller clears it.

#### `clearDenial`

`clearDenial` clears the trustor's denial of `trusteeNode` in `scope`, on condition that
no attestation by the trustor has been stored since the caller reviewed it. It MUST revert
if any of the following hold:

1. The caller is not the name controller for `trustorNode`: `NotAuthorized`
2. `trustorNode == trusteeNode`: `SelfTrustProhibited`
3. `getNonce(trustorNode) != expectedNonce`: `NonceChanged(expectedNonce, current)`

The nonce check applies whether or not the flag is set. Every stored attestation raises
the trustor's nonce, as does `invalidateNonces`, so an unchanged nonce means no
endorsement by the trustor has been written since the caller read it. Withdrawals do not
raise the nonce, but can only reduce trust.

If the stored flag is `true`:

* The stored flag for `(trustorNode, trusteeNode, scope)` MUST be set to `false`
* The trust level, expiry and every other stored part of the record MUST NOT change
* `DenialSet` MUST be emitted with `denied = false`

If the stored flag is already `false`, `clearDenial` MUST succeed without changing
storage and MUST NOT emit `DenialSet`.

The nonce check cannot stop an attestation that was signed above the current nonce and
lands *after* the clear; it applies as soon as it is stored. A caller SHOULD therefore
clear in this order:

1. If the trustor may have signed attestations that are not yet stored, call
   `invalidateNonces` with a floor above every nonce the trustor has signed
2. After that call has executed, read `getNonce(trustorNode)`, review the stored
   endorsements, and pass the nonce read to `clearDenial`

An attestation the trustor signs after step 1 is fresh authorisation by the controller.
A caller that must not let unreviewed attestations take effect right after reinstatement
SHOULD pause or serialise the trustor's signing from step 1 until the clear has executed.
If `clearDenial` reverts with `NonceChanged`, the caller SHOULD review again before
retrying with the new nonce.

#### `getDenial`

`getDenial` MUST return the denial flag stored for exactly `(trustorNode, trusteeNode,
scope)`, and MUST NOT return the effective denial. Like `getTrust`, it returns stored
data. Callers derive the effective denial from two reads:

```text
effectiveDenial(A, B, s) = getDenial(A, B, bytes32(0)) || getDenial(A, B, s)
```

#### `invalidateNonces`

An attestation signed at nonce `N` remains submittable until the trustor's nonce reaches
`N`, whatever has been revoked since. `invalidateNonces` lets a trustor raise that floor.
It MUST revert if any of the following hold:

1. The caller is not the name controller for `trustorNode`: `NotAuthorized`
2. `newNonce <= getNonce(trustorNode)`: `NonceTooLow`
3. `newNonce > getNonce(trustorNode) + 2**32`, evaluated without overflow: when that sum
   exceeds `type(uint64).max`, the bound is `type(uint64).max`:
   `NonceJumpTooLarge(newNonce, bound)`

Otherwise:

* `getNonce(trustorNode)` MUST return `newNonce`
* `NoncesInvalidated` MUST be emitted

Every attestation signed with a nonce at or below `newNonce` becomes permanently
unusable, whichever trustee or scope it names.

Trustors SHOULD issue nonces sequentially (`getNonce(trustorNode) + 1`) so that the
highest outstanding nonce is always known.

To quarantine a compromised or misbehaving counterparty, a trustor SHOULD:

1. **Set denial** at universal scope. The counterparty then fails every edge from the
   trustor and every path the trustor evaluates as validator, even while other agents
   still vouch for it. Gates whose gatekeeper is any other agent are unaffected.
2. **Invalidate outstanding nonces**, with a floor above every nonce the trustor has
   signed. This voids the trustor's outstanding attestations for every trustee and scope.
3. **Investigate and recover**: once step 2 has executed, read the trustor's nonce,
   review the stored endorsements, withdraw those that should not return, then call
   `clearDenial` with the nonce read if the counterparty is reinstated.

The denial does not depend on step 2, but recovery does: clearing the denial reveals
whatever endorsement is stored at that time. Every step requires the name controller (see
[Key Compromise](#key-compromise)).

#### `verifyPath`

`verifyPath` validates a pre-computed trust path and returns a single verdict. It MUST
return `false` unless every requirement is satisfied, including the `requiredAnchors`
constraint.

`verifyPath` MUST reject `ValidationParams` that violate the
[Validation Parameters Constraints](#validation-parameters-constraints) before using them,
through the same routine `setIdentityGate` uses. Without this, `minEdgeTrust ==
TrustLevel.Unknown` would make every edge comparison pass. `validateParticipantWithPath`
and `validateParticipantAddress` read parameters from a stored gate, which were validated
when `setIdentityGate` stored them, so those functions MAY skip revalidation; they MUST
NOT accept parameters from any other source.

The external functions wrap internal helpers that take `memory` arguments: `_verifyPath`,
`_getTrust` (the stored record, as `getTrust` returns it) and `_getIdentityGate` (the
stored gate, as `getIdentityGate` returns it).

```solidity
function verifyPath(
   TrustPath calldata path,
   ValidationParams calldata params
) external view returns (bool valid) {
   return _verifyPath(path, params, true);
}

function _verifyPath(
   TrustPath memory path,
   ValidationParams memory params,
   bool validateParams
) internal view returns (bool) {
   if (validateParams) requireValidParams(params);

   // Path must have at least 2 nodes (validator and target)
   if (path.nodes.length < 2) return false;

   // Path length constraint (edges = nodes - 1)
   if (path.nodes.length - 1 > params.maxPathLength) return false;

   // Nodes MUST be distinct
   for (uint256 i = 0; i < path.nodes.length; i++) {
      for (uint256 j = i + 1; j < path.nodes.length; j++) {
         if (path.nodes[i] == path.nodes[j]) return false;
      }
   }

   // The validator's denial overrides any indirect endorsement.
   // k = 1 is already covered by the first edge check.
   bytes32 validator = path.nodes[0];
   for (uint256 k = 2; k < path.nodes.length; ++k) {
      (, , bool validatorDenies) = _edgeTrust(validator, path.nodes[k], params.scope);
      if (validatorDenies) return false;
   }

   bool foundAnchor = params.requiredAnchors.length == 0;

   for (uint256 i = 0; i < path.nodes.length - 1; i++) {
      (TrustLevel level, uint64 expiry, bool denied) =
         _edgeTrust(path.nodes[i], path.nodes[i + 1], params.scope);

      // Denial voids the edge whatever its endorsement
      if (denied) return false;

      if (level < params.minEdgeTrust) return false;
      if (level == TrustLevel.None) return false;

      if (params.enforceExpiry && expiry != 0 && expiry <= block.timestamp) {
         return false;
      }

      // Anchor check (intermediate nodes only, not first or last)
      if (!foundAnchor && i > 0) {
         for (uint256 j = 0; j < params.requiredAnchors.length; j++) {
            if (path.nodes[i] == params.requiredAnchors[j]) {
               foundAnchor = true;
               break;
            }
         }
      }
   }

   return foundAnchor;
}
```

**Node uniqueness:** A path MUST NOT contain the same node twice. Repeated nodes inflate
path length without adding trust. A path has at most 11 nodes, so the scan is at most 55
comparisons (see [Why At Most Ten Edges?](#why-at-most-ten-edges)).

**Edge denial:** `verifyPath` MUST return `false` if, for any edge `nodes[i] → nodes[i+1]`,
`EffectiveDeny(nodes[i], nodes[i+1], params.scope)` holds (see [Denial](#denial)), whatever
endorsement the edge stores, whether or not `enforceExpiry` is set, and whatever
`minEdgeTrust` is.

**Validator denial:** `verifyPath` MUST return `false` if, for any node `nodes[k]` with
`k >= 2`, `EffectiveDeny(nodes[0], nodes[k], params.scope)` holds. For `k = 1` the edge
denial check already applies. The check applies only to the denials of `nodes[0]`; a
denial held by any other node on the path voids the path only through that node's own
outgoing edge. It reads denial only: the validator's trust levels for later nodes do not
void the path.

**Anchors:** Only intermediary nodes (indices `1` through `nodes.length - 2`) can satisfy
`requiredAnchors`, so a direct edge `[A, B]` can never satisfy a non-empty
`requiredAnchors` (see [Gate Constraints](#gate-constraints)). Callers that want anchors
to be advisory MUST pass an empty `requiredAnchors` array rather than inspecting a partial
result.

Off-chain indexers that compute paths SHOULD apply every rule of this algorithm during
search, evaluated from the validator's perspective, so that the paths they return verify.

##### Scope Fallback Semantics

"Universal" means the record stored at `bytes32(0)`. When `params.scope` is `bytes32(0)`,
the universal record applies. Otherwise, implementations MUST determine each edge's trust
as follows:

1. If the universal level is `None`, the edge is `None`: universal withdrawal voids the
   edge in every scope
2. Otherwise, if a record is stored at `params.scope` (its level is not `Unknown`), that
   record applies, whether or not it has expired
3. Otherwise, the universal record applies

An expired scoped record therefore never falls back to universal trust: with
`enforceExpiry` set, the edge fails.

A universal attestation that replaces a universal `None` lets every positive scoped
record for the pair apply again, including scoped grants made long before the withdrawal.
A trustor re-endorsing at universal scope SHOULD first review, or withdraw, the scoped
grants it does not want to return.

Denial does not use these fallback rules. `_edgeTrust` returns the effective denial
alongside the level and expiry, read from the same records:

```solidity
function _edgeTrust(bytes32 from, bytes32 to, bytes32 scope)
   internal view returns (TrustLevel level, uint64 expiry, bool denied)
{
   TrustRecord storage u = _trust[from][to][bytes32(0)];

   // Universal denial holds in every scope, so no scoped record can lift it
   if (scope == bytes32(0) || u.denied) return (u.level, u.expiry, u.denied);

   TrustRecord storage s = _trust[from][to][scope];

   // 1. Universal None voids the endorsement in every scope
   if (u.level == TrustLevel.None) return (TrustLevel.None, u.expiry, s.denied);

   // 2. Any stored scoped record is authoritative, expired or not
   if (s.level != TrustLevel.Unknown) return (s.level, s.expiry, s.denied);

   // 3. Otherwise universal applies
   return (u.level, u.expiry, s.denied);
}
```

`TrustRecord` and `_trust` are the reference implementation's storage, which packs the
level, expiry and denial flag of each record into one slot. Implementations MAY store
records differently, provided `_edgeTrust` returns the same values.

#### `setIdentityGate`

Gates are stored under the key `(msg.sender, coordinationType)`, so a caller can only
create, replace, or remove gates in its own namespace.

`setIdentityGate` MUST revert if `params` violates the
[Validation Parameters Constraints](#validation-parameters-constraints), checked first and
in table order, or the [Gate Constraints](#gate-constraints), checked after them.

`setIdentityGate` MUST NOT require the caller to control `gatekeeperNode`. Naming a
gatekeeper only reads that agent's public attestations.

Otherwise:

* The gate MUST be stored at `(msg.sender, coordinationType)` and marked enabled
* `IdentityGateSet` MUST be emitted

#### `removeIdentityGate`

`removeIdentityGate` MUST revert with `GateNotFound` if no enabled gate exists at
`(msg.sender, coordinationType)`. Otherwise:

* The gate MUST be disabled
* `IdentityGateRemoved` MUST be emitted

#### `validateParticipantWithPath`

This function gates [ERC-8001](./eip-8001.md) participation for a participant identified
by ENS node. It MUST revert with `GateNotFound` when no gate is enabled at
`(coordinator, coordinationType)`, before any other check (see
[Why Do Unconfigured Gates Revert?](#why-do-unconfigured-gates-revert)).

It MUST return `false` if any of the following hold, and otherwise the result of
`_verifyPath` with the gate's parameters:

* `path.nodes.length < 2`
* `path.nodes[0] != gatekeeperNode`
* `path.nodes[path.nodes.length - 1] != participantNode`
* `verifyPath(path, params)` returns `false`

Requiring the path to end at `participantNode` binds the result to the agent being gated.

#### `validateParticipantAddress`

This is the hook an [ERC-8001](./eip-8001.md) coordinator calls for each entry in an
intent's `participants` array, with one pre-computed path per participant. It MUST revert
with `GateNotFound` when no gate is enabled at `(coordinator, coordinationType)`, before
any other check.

It MUST return `false` if any of the following hold, and otherwise the result of
`_verifyPath` with the gate's parameters:

* `participant == address(0)`
* `path.nodes.length < 2`
* `path.nodes[0] != gatekeeperNode`
* `resolveAgent(path.nodes[path.nodes.length - 1]) != participant`
* `controllerOf(path.nodes[path.nodes.length - 1]) == address(0)`
* `verifyPath(path, params)` returns `false`

The `participant == address(0)` check stops a node with no `addr` record matching a zero
address. The controller check rejects a name nobody controls, such as a wrapped name past
its NameWrapper expiry, whose `addr` record ENS has not cleared. It reads `controllerOf`
only, so it does not reject an expired unwrapped name, a name in its grace period, or a
migrated name whose legacy resolver is kept. `validateParticipantWithPath` does not
consult control.

#### Re-evaluation at Execution

Both functions report the registry's state when they are evaluated. A denial, withdrawal,
expiry or change of control affects later evaluations only. A coordinator whose execution
relies on its participants still passing the gate SHOULD evaluate the gate again in the
transaction that executes, for example in `executeCoordination`, with the paths supplied
in its `executionData`.

That evaluation cannot apply the continuity check under
[Re-registration](#re-registration), which reads events no transaction can see. A
coordinator that relies on the check SHOULD perform it off-chain on the paths it will
supply, and SHOULD NOT treat the on-chain result as covering it. A check run to block B
leaves a window: a registration after block B, including one earlier in the executing
block, ends attestations that the on-chain evaluation still accepts.

For a `.eth` second-level name on its paths, a coordinator can close that window with the
expiry E that the BaseRegistrar's `nameExpires` returns for the name at block B. In the
executing transaction it requires either that `block.timestamp` is no later than E plus
the BaseRegistrar's `GRACE_PERIOD`, or that `nameExpires` still returns E. The
BaseRegistrar registers a name only after its expiry plus the grace period has passed, and
no operation lowers the expiry, so either condition shows that no registration has
occurred since block B. This standard defines no comparable check for a name below a
second-level name being wrapped again.

The liveness check reads state, so a coordinator can repeat it in the executing
transaction by reading the NameWrapper's `ownerOf` for each wrapped trustor on the path,
and not executing while any of them returns the zero address. The on-chain evaluation does
not do this: `validateParticipantAddress` requires a controller for the last node only.

### Errors

Implementations MUST use these errors for the revert conditions this standard assigns
them to:

```solidity
error SelfTrustProhibited();
error InvalidAttestationLevel(TrustLevel level);
error NonceTooLow(uint64 provided, uint64 required);
error AttestationExpired(uint64 expiry, uint64 currentTime);
error InvalidSignature();
error NotAuthorized(bytes32 node, address actor);
error ENSNameNotFound(bytes32 node);
error GateNotFound(bytes32 coordinationType);
error InvalidMaxPathLength(uint8 provided);
error InvalidMinEdgeTrust(TrustLevel provided);
error TooManyRequiredAnchors(uint256 provided);
error UnsatisfiableAnchors(uint8 maxPathLength);
error BatchLengthMismatch();
error EmptyBatch();
error BatchTrustorMismatch();
error BatchNonceNotIncreasing();
error EmptyScopeList();
error NonceJumpTooLarge(uint64 provided, uint64 max);
error NonceChanged(uint64 expected, uint64 current);
```

`NonceTooLow.required` is `getNonce(trustorNode) + 1`, saturating at
`type(uint64).max`. Once a trustor's floor reaches `type(uint64).max` no nonce is
accepted, and both `setTrust` and `invalidateNonces` revert with
`NonceTooLow(provided, type(uint64).max)` rather than an arithmetic panic.

### Recommended Reason Codes

For `TrustRevoked` and `DenialSet` events, the following reason codes are RECOMMENDED:

| Reason Code | Value | Meaning |
|-------------|-------|---------|
| Unspecified | `bytes32(0)` | No specific reason |
| Misbehaviour | `keccak256("MISBEHAVIOR")` | Agent acted improperly |
| Compromised | `keccak256("COMPROMISED")` | Key or account compromised |
| Inactive | `keccak256("INACTIVE")` | Agent no longer active |
| Transfer | `keccak256("TRANSFER")` | ENS name transferred |

Reason codes are informational and do not change the effect of an operation: a
withdrawal recorded as `COMPROMISED` does not deny the agent. Where exclusion is
intended, it MUST be expressed with `setDenial`. `clearDenial` MAY use `bytes32(0)`.

### Recommended Scopes

For interoperability, the following scope values are RECOMMENDED:

## Rationale

### Why ENS Instead of a New Identity System?

ENS is finalised ([ERC-137](./eip-137.md)), widely deployed, and already provides
identifiers that survive key rotation, ownership through `owner()` and
`isApprovedForAll()`, and subdomains for protocol-issued agent identities. Agent
registries that represent each agent as an [ERC-721](./eip-721.md) token can be consumed
through an adapter that issues an ENS subname per token, so `requires` lists only
finalised standards.

### Why Scope as Storage Key?

A trustor may trust the same trustee fully for DeFi and marginally for gaming. Making
scope part of the key `(trustorNode, trusteeNode, scope)` expresses this directly, with
universal trust as the fallback.

### Divergence from OpenPGP

OpenPGP keeps validity (does a key belong to its holder?) apart from owner trust (how far
are the holder's certifications relied on?). This standard keeps one quantity, the level
on an edge, which acts as owner trust for an intermediary and as validity for the target.
The binding between a name and its controller comes from ENS.

`verifyPath` also performs no marginal accumulation. OpenPGP accepts a key with one fully
trusted certification or several marginal ones. Here one path is checked and every edge
must reach `minEdgeTrust`, which gives one verdict per path at O(path length) cost with no
threshold parameters. An application that wants accumulation can verify several paths
and combine the verdicts.

### Why Four Trust Levels and a Separate Denial Flag?

The four levels follow OpenPGP. A trustor needs to withdraw an endorsement without
refusing the agent, and to refuse the agent without losing the endorsement it would
restore afterwards. If `None` meant both, there would be no neutral withdrawal, and an
approved operator, who may withdraw, could decide whose judgement the trustor accepts. A
fifth level would break the ordering that `minEdgeTrust` comparisons rely on. Denial is
therefore a flag that only the controller writes.

### Why Separate Signing Authority from Transaction Submission?

ENS operator approvals exist so operators can manage names. Letting them sign
attestations would break the binding between an attestation and the name's controller.
Anyone may relay a signed attestation, and approved operators may withdraw.

### Why ECDSA Before ERC-1271?

An [EIP-7702](./eip-7702.md) account is still controlled by its key, which can sign a new
delegation at any time, so a signature from that key already carries the account's full
authority. Trying ECDSA first accepts it; routing every controller with code straight to
[ERC-1271](./eip-1271.md) would reject it whenever the delegate does not implement
`isValidSignature`. The [ERC-1271](./eip-1271.md) fallback still lets a delegate validate
signatures of its own. The cost is that a delegate cannot stop its key from attesting; an
account that needs that restriction uses a contract controller with no key.

### Why Is Denial Controller-Only?

Denial decides whose judgement the trustor accepts, and clearing it readmits an agent the
controller excluded. Both carry the same authority as signing an attestation. A
controller that needs to delegate can use a contract controller.

### Why verifyPath Only (No On-Chain Search)?

On-chain graph traversal has unpredictable gas cost, and attackers can inflate adjacency
lists. Pre-computed paths keep verification O(path length) and leave search to off-chain
indexers.

### Why At Most Ten Edges?

A path of more than a few edges says little about its target, and the cap bounds the cost
of verification. In the reference implementation a ten-edge path costs about 146,500 gas
in a named scope and 92,200 at universal scope, with registry storage cold. The default
is five.

### Why Required Anchors?

Sybil attacks are the main threat to a web of trust. Required anchors force paths through
established nodes such as DAOs, protocols or auditors, as an enforced gate parameter.

### Why Are Gates Keyed by Caller Address?

An [ERC-8001](./eip-8001.md) `coordinationType` has no namespace, so unrelated
applications will choose the same value, and keying by it alone would let the first
registrant squat it. Keying by `(msg.sender, coordinationType)` gives each caller its own
namespace and needs no ENS name. Keying by the gatekeeper's node would conflate the party
that sets a policy with the party whose trust graph it reads.

### Why Do Unconfigured Gates Revert?

The integrator supplies both halves of the gate key, so a typo finds no gate. An open
default would admit everyone while looking like a working gate, and returning `false`
would blame the participant. Reverting with `GateNotFound` names the real problem.
Coordinators can read `getIdentityGate(...).enabled` first if they need to branch.

### Why Forward Resolution Instead of a Binding Registry?

The `addr` record is already the controller's statement of which address a name denotes,
so reusing it needs no registration step. Reverse records are self-asserted, and
verifying one on-chain requires a forward lookup plus string handling over untrusted
input. The trade-off is that a stale record can outlive a registration (see
[Resolver Trust](#resolver-trust)).

CCIP-Read resolution is client-side. Supporting it on-chain would need the caller to fetch
the gateway's response and the registry to pass it to the resolver's callback, and how a
callback authenticates that response differs between resolvers. That is left to a
separate module.

### Why Does Resolution Cap Gas and Never Revert?

A coordinator typically validates every participant in one call, and participants choose
their own resolvers. If resolution could revert or consume most of the remaining gas, one
participant could abort validation for all of them. Capping the forwarded gas and treating
every malformed answer as "no address" fails closed for that participant only. Deployed
resolvers answer in under 20,000 gas (every resolver sampled at mainnet block 26,173,410,
with state cold).

The bound is set by each implementation, not by this standard, because gas repricing can
change those figures. A caller-supplied bound was considered. It would add a parameter to
`resolveAgent` and `validateParticipantAddress`, and the same gate could then admit or
reject a participant depending on the bound each caller chose.

[ERC-1271](./eip-1271.md) checks are not capped. They run only when an attestation is
submitted, and a batch carries one trustor, so an expensive controller wastes only the
gas of whoever submits its attestations.

### Why a Single Per-Trustor Nonce?

A single monotonic nonce per trustor gives it one floor to raise after a compromise. An
unordered nonce bitmap has no floor, so every outstanding nonce would have to be burned
individually. Nonces per `(trustor, trustee, scope)` can be invalidated only one record at
a time. A per-trustee floor beside the global one would allow quarantining one
counterparty, but adds a storage read to `setTrust`, a second nonce for every signer and
a larger interface, for a narrow case whose cost today is re-signing the attestations still
in flight. Agents that need throughput can use `setTrustBatch`.

### Why Explicit Nonce Invalidation?

Revocation cannot undo an attestation that is signed but not yet submitted, and only the
trustor knows the highest nonce it has issued, so advancing the nonce by a fixed step in
`revokeTrust` would not reliably invalidate anything.

### Why Is `invalidateNonces` Controller-Only?

Raising the nonce floor permanently voids every outstanding attestation of the trustor.
ENS `isApprovedForAll` is a coarse approval often granted to marketplaces and management
tools, which were not granted that power.

### Why Is Universal Withdrawal Authoritative?

A trustor that withdraws at universal scope means it everywhere. If universal `None`
applied only where no scoped record existed, every earlier scoped grant would keep the
edge alive. The override costs one extra storage read per edge in a named scope. An
expired scoped record does not fall back to universal trust, since that would let a lapsed
narrow grant widen silently.

### Why Does a Validator's Denial Override Indirect Paths?

Suppose Alice trusts Bob, Bob trusts Carol, and Alice has denied Carol. Checking only
edges, `[Alice, Bob, Carol]` would verify, and Bob's endorsement would override Alice's
refusal inside Alice's own decision. Only the validator's denial counts: checking every
pair of nodes would cost O(n²) reads and let any agent on a path veto it. The check costs
about 6,000 gas per node from index 2 in a named scope, and 3,000 at universal scope, with
storage cold.

### Why Does Clearing a Denial Check the Trustor's Nonce?

Without a check, a relayer could front-run a reviewed clear with another valid
attestation, which the clear would then activate unreviewed. The trustor's nonce covers
every scope with one storage read. Folding the nonce floor into `clearDenial` would void
the trustor's outstanding attestations for every other trustee. Denying takes no nonce,
because it is the emergency operation and must not fail because an attestation landed
first.

### Why Batch Revocation Instead of Revoke-All?

A revoke-all would have to enumerate scopes on-chain or shadow records with an epoch that
`getTrust` would not report literally. Universal withdrawal already covers every scope.

### Why Unwrap NameWrapper Names?

The NameWrapper does not implement [ERC-1271](./eip-1271.md), so treating it as the
signing authority would leave every wrapped name unable to attest. Unwrapping through
`ownerOf` recovers the actual controller and inherits the NameWrapper's expiry behaviour.

### Why Does Authority Follow Ownership Rather Than Management Permission?

During a `.eth` name's grace period the NameWrapper refuses management operations but
still reports the holder. Requiring `canModifyName` would remove the name's authority,
including withdrawal, denial and nonce invalidation, for 90 days in which the name has not
changed hands. It would also cover only part of the risk, since unwrapped names keep their
registry owner after expiry.

Binding each record to the registration that issued it would let the registry reject
records from an earlier registration, but ENSv1 state cannot tell a renewal from a later
registration without the BaseRegistrar's events. It would also change the storage layout
and the interface, and work only for `.eth` second-level names. This standard leaves it to
an ENSv2-native successor.

### Why Pin the NameWrapper?

The `nameWrapper` slot decides who controls every wrapped name. Whoever could change it
could point it at a contract whose `ownerOf` returns addresses of their choosing. A
governance-updatable slot would only move that power to whoever holds the update right.
The cost falls on names that move to a successor wrapper: supporting one means deploying a
new registry, and trustors re-attest against its [EIP-712](./eip-712.md) domain.

## Backwards Compatibility

This ERC introduces new functionality and does not modify existing standards.

It uses only ENSv1 interfaces: `owner`, `resolver` and `isApprovedForAll` on the registry,
`addr` on the resolver ([ERC-137](./eip-137.md)), and `ownerOf` and `isApprovedForAll` on
the NameWrapper, and works with deployments that have no NameWrapper. Agents whose names
are served by an off-chain resolver can hold and issue trust, but cannot be validated by
address.

[ERC-8001](./eip-8001.md) coordinators can optionally integrate identity gates by calling
`validateParticipantAddress` once per participant. No change to [ERC-8001](./eip-8001.md)
is required. Signatures use [EIP-712](./eip-712.md), with [ERC-1271](./eip-1271.md) for
contract wallets.

Registries built from earlier drafts of this ERC are not compatible with this revision,
and some report the same interface identifier and [EIP-712](./eip-712.md) domain version.
A consumer that depends on this revision's behaviour identifies a registry by its
deployment address and verified source.

### ENSv2 Compatibility and Migration

This ERC does not specify native ENSv2 controller resolution, signing authority or address
resolution. This section is informative. It describes the ENSv2 migration process as
deployed on Sepolia, checked at block 11,906,480 (13 October 2026). ENSv2 is not deployed
on Ethereum mainnet, and its mainnet process may differ. The rules of this standard do not
depend on it: `controllerOf` returns whatever the ENSv1 registry and the pinned
NameWrapper report.

Under that process a migrated name's ENSv1 token is transferred to the ENSv2 Graveyard
contract, so `controllerOf` returns the Graveyard. The Graveyard does not implement
[ERC-1271](./eip-1271.md), so no one can manage trust for the name through this ERC.
Migration clears the ENSv1 resolver, except for a locked name with `CANNOT_SET_RESOLVER`
burned. An approved operator can migrate a name and choose its new ENSv2 owner.

Migration freezes the name's state in the registry. Stored paths through it stay valid,
subject to their levels, expiries and gate constraints, while its outgoing endorsements
and denials can no longer be changed, and those with `expiry == 0` persist indefinitely.
A migrated gatekeeper keeps admitting participants through stored paths, and can neither
exclude nor readmit agents. Attestations it signed but never submitted no longer verify.
Address-based validation fails where the resolver was cleared.

Subnames of a migrated parent keep their controller and resolver until anyone calls the
Graveyard's `clear` function, which hands unwrapped and unemancipated wrapped subnames to
the Graveyard and freezes them in the same way. On that deployment `clear` also applies to
`.eth` second-level names past their grace period that were never migrated, which ends a
lapsed holder's authority over an expired unwrapped name, and ENSv1 registration is
closed. Whether that happens on mainnet is not established.

Supporting names registered only in ENSv2 needs a successor registry. Trust state does
not carry over, because signatures are bound to the registry's [EIP-712](./eip-712.md)
domain (see [Why Pin the NameWrapper?](#why-pin-the-namewrapper)).

## Security Considerations

### Sybil Attacks and Graph Manipulation

An attacker can create many ENS names, establish mutual trust between them, and try to
place them on many trust paths. Mitigations:

* Require anchors (`requiredAnchors`), so paths traverse established community nodes
* Keep `maxPathLength` short and require `minEdgeTrust: Full` for high-value coordination
* In application logic, weight trust by name age or registration cost, add stake
  requirements, or require several independent paths, each checked with `verifyPath`

### Key Compromise

When a counterparty is compromised, the trustor's own controller is sound: it denies the
counterparty at universal scope and follows the quarantine procedure under
[`invalidateNonces`](#invalidatenonces). Withdrawal, even at universal scope with the
`COMPROMISED` reason code, removes only the withdrawing agent's own edge. Denial applies
to the node, not to the address it resolves to (see [Address Aliases](#address-aliases)).

When the trustor's own controller is compromised, denial is not sufficient: the attacker
holds the same controller and nonce space, so it can clear denials, withdraw endorsements
and sign new attestations. Rotating the controller stops new attestations but retracts
nothing. The remedy is denial by counterparties, which the attacker cannot clear because
each denial is stored under the counterparty's own name.

Neither an attestation nor an `invalidateNonces` call can raise the nonce floor by more
than 2^32. Without that bound, one call with nonce `type(uint64).max` would stop the name
from ever attesting again, and the lockout would pass to every future controller.

### Pre-Signed Attestations

An attestation carries no signing timestamp and is submittable by anyone holding the
signature until the trustor's nonce passes it. If Alice signs an attestation for
`bob.eth` at nonce 10 and then revokes trust in `bob.eth`, anyone holding the nonce-10
signature can restore it. Mitigations are sequential nonces, `invalidateNonces` above
every nonce signed, raising the floor before clearing a denial, and short `expiry` values.

### Gatekeeper and Anchor Names

A gate stores its gatekeeper and anchors as namehashes, so a change of control moves the
role to the new controller and nothing in the gate records it. A new controller of
`gatekeeperNode` can attest directly from it: where the gate requires no anchor, one
attestation admits any agent it chooses. A non-empty `requiredAnchors` forces that agent
through an anchor. Either way it can deny agents, or clear denials a previous controller
set. A new controller of an anchor inherits every attestation naming the anchor, and can
attest from it to any agent; only inbound attestations with an expiry bound that.

Mitigations are monitoring control of every gatekeeper and anchor node, non-empty
`requiredAnchors` where a change of gatekeeper control would be costly, expiries on
attestations leading to anchors, and, at a cost, locking these names with fuses.

### Monitoring Control Changes

No single event reports every change of control. Depending on how a name is held, a
change appears as:

* A registry `NewOwner` event from `setSubnodeOwner`, used by registration, reclaiming a
  `.eth` name and a parent reassigning a subname
* A registry `Transfer` event from `setOwner`
* For unwrapped `.eth` second-level names, a BaseRegistrar [ERC-721](./eip-721.md)
  transfer. The registry owner does not change until the new registrant reclaims the name
* For wrapped names, a NameWrapper [ERC-1155](./eip-1155.md) `TransferSingle` or
  `TransferBatch` event

A wrapped name also loses and regains control with no event when its NameWrapper expiry
passes or is restored (see [Wrapped Name Lifecycle](#wrapped-name-lifecycle)).

### Resolver Trust

The controller can change a node's `addr` record at any time, so a trusted name can be
repointed and gates keyed on it will admit the new address without any attestation
changing. Trusting a node means trusting its resolver.

The record can also be stale. After a re-registration it keeps naming the previous
holder's address until the new registrant changes it, and `validateParticipantAddress`
keeps admitting that address. Monitoring `AddrChanged` does not catch this. A
registration that sets the `addr` record in the same transaction leaves no stale window.
Mitigations are short expiries, and treating a node's `addr` record as unconfirmed after
a change of control until the new controller has set it.

### Address Aliases

Denial excludes a name, not the address it resolves to. If `agent.eth` and `backup.eth`
both resolve to `X` and both have eligible paths from a gatekeeper, `X` still passes
`validateParticipantAddress` through `backup.eth` after the gatekeeper denies
`agent.eth`, and the controller of any name with an eligible path can point it at `X`.
To exclude an address, apply an address-level policy alongside the gate, or identify
participants by node through `validateParticipantWithPath`.

### Expired Unwrapped Names

When an unwrapped `.eth` second-level name expires, `ens.owner(node)` keeps returning the
lapsed holder until the name is re-registered, so the lapsed holder keeps every authority
this standard grants and can still repoint the `addr` record. The registry cannot detect
this, because `.eth` expiry is recorded against the labelhash, which cannot be derived
from the namehash. On re-registration the new registrant inherits the name's trust at
once. Wrapped names and emancipated subnames lose authority once their NameWrapper expiry
passes.

### Parent-Controlled Subnames

An unwrapped parent, or a wrapped parent whose subname does not have
`PARENT_CANNOT_CONTROL` burned, can reassign the subname at any time, and whoever
registers the parent next can do the same. The new controller inherits the subname's
trust and roles without the holder's consent. `PARENT_CANNOT_CONTROL` protects an
emancipated subname only until its NameWrapper expiry. The continuity check under
[Re-registration](#re-registration) bounds both cases for coordinators that apply it.

### Name Locking with Fuses

`PARENT_CANNOT_CONTROL`, `CANNOT_UNWRAP` and `CANNOT_TRANSFER` together stop a wrapped
name being reassigned by its parent or transferred by its holder, until its NameWrapper
expiry resets every fuse. Locking is a long-term commitment: under ENS's migration process
as deployed on Sepolia, names with `CANNOT_TRANSFER` burned cannot migrate to ENSv2.

### Replay Protection

The [EIP-712](./eip-712.md) domain prevents cross-contract and cross-chain replay, and
monotonic nonces prevent replay within the registry. Nonces do not stop an attestation
being applied late (see [Pre-Signed Attestations](#pre-signed-attestations)).

### Off-Chain Path Computation

A malicious indexer can omit valid paths or return suboptimal ones, but cannot make an
invalid path verify. Users can run their own indexers or use several. Indexers need to
follow `DenialSet` as well as `TrustSet` and `TrustRevoked`.
