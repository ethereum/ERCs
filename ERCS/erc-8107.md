## Abstract

This ERC defines a **Trust Registry** that enables agents to establish and query transitive trust relationships using ENS names as identifiers. Trust is expressed at four levels (Unknown, None, Marginal, Full) and propagates along certification paths, adopting the trust levels and path model of the OpenPGP web of trust described in [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html), which obsoletes [RFC 4880](https://www.rfc-editor.org/rfc/rfc4880.html). Unlike OpenPGP, path verification checks a single path against a minimum per-edge trust level and does not accumulate marginal attestations.

The registry serves as the **trust and delegation module** anticipated by [ERC-8001](./eip-8001.md), enabling coordinators to gate participation based on trust graph proximity. An agent is considered valid from a coordinator's perspective if a verified trust path exists from the gate's gatekeeper to the agent that satisfies the gate's parameters, and the gatekeeper has not denied any agent on that path.

The registry keeps two independent judgements per relationship. An **endorsement** (a trust level) is the trustor's own vouching for the trustee, and withdrawing it removes only that edge. A **denial** is the trustor's refusal to rely on the trustee at all, which overrides endorsements by other agents within the trustor's own trust decisions. Endorsements are signed by the name controller and may be withdrawn by its approved operators; denials are managed by the name controller alone.

This standard specifies trust attestation structures, the path verification algorithm, ENS integration semantics, and [ERC-8001](./eip-8001.md) coordination hooks.

## Motivation

[ERC-8001](./eip-8001.md) defines minimal primitives for multi-party agent coordination and defers everything above them, including reputation, to modules. Its Security Considerations name the gap directly:

> "Equivocation: A participant can sign conflicting intents. Mitigate with module-level slashing or reputation."

and its Motivation sets the boundary:

> "Privacy, thresholds, bonding, and cross-chain are left to modules."

This ERC provides that trust and delegation module. Before coordinating, agents need answers to:

1. **"Should I include this agent in my coordination?"** — Participant selection
2. **"Can I trust this agent's judgement about other agents?"** — Transitive trust
3. **"How do I update trust based on coordination outcomes?"** — Trust maintenance

### Why Web of Trust?

The web of trust model, standardised for OpenPGP in RFC 9580 (which obsoletes RFC 4880) and proven over 25+ years of deployment, solves the bootstrap problem: how do you establish trust with unknown agents without a centralised registrar?

| OpenPGP Concept | This Standard |
|---------------|---------------|
| Public key | ENS name |
| Key signing | Trust attestation |
| Owner trust levels | `TrustLevel` enum |
| Key validity | Agent validity for coordination |
| Certification path | Trust chain through agents |

This standard adopts OpenPGP's trust levels and certification paths, but not its
validity calculation. OpenPGP treats a key as valid once it carries one fully trusted
signature or enough marginally trusted ones. `verifyPath` instead checks one path, and
every edge on it must meet `minEdgeTrust`. This standard does not define marginal
accumulation; see [Divergence from OpenPGP](#divergence-from-openpgp).

### Identity Continuity

ENS names are the identity. When an ENS name is transferred, the new owner inherits existing trust relationships where that name is the trustee, and can manage trust where that name is the trustor. Gates name their gatekeeper and anchors the same way, so a gate follows those names rather than their controllers. Short attestation expiries bound part of the exposure this creates; the Specification states the requirements under [Identity Continuity](#identity-continuity-1).

### Trust Levels

Implementations MUST use the canonical enum:

```solidity
enum TrustLevel {
   Unknown,   // 0: No trust relationship established
   None,      // 1: Endorsement withdrawn
   Marginal,  // 2: Partial trust — accepted on an edge when minEdgeTrust <= Marginal
   Full       // 3: Complete trust — satisfies any minEdgeTrust
}
```

#### Semantic Definitions

| Level | Meaning | Validation Contribution |
|-------|---------|------------------------|
| `Unknown` | Default state; no data about agent | Cannot contribute to validation |
| `None` | The trustor has withdrawn its endorsement | Voids an edge whose effective level it is. Does not affect paths that do not use that edge |
| `Marginal` | Agent generally trustworthy | Contributes to validation when `minEdgeTrust <= Marginal` |
| `Full` | Agent's judgement equals own verification | Always contributes to validation |

#### Level Transitions

Attestations grant trust; revocations withdraw it. Each level has exactly one way to
reach it:

* `Marginal` and `Full` are reached only by a valid attestation with a higher nonce
* `None` is reached only by `revokeTrust` or `revokeTrustBatch`
* `Unknown` is the default and cannot be reassigned; a relationship, once created, is
  never removed from storage

`setTrust` therefore MUST reject attestations whose level is `Unknown` or `None`, and
withdrawal is not permanent: a later attestation with a higher nonce restores trust from
`None` to `Marginal` or `Full`.

No level transition changes the denial flag, and changing the denial flag changes no
level (see [Denial](#denial)).

### Denial

The registry represents three distinct intentions of a trustor `A` towards a trustee `B`
in a scope `s`:

| Intention | Meaning | Operation |
|-----------|---------|-----------|
| Endorsement | `A` trusts `B` | `setTrust`, `setTrustBatch` (level `Marginal` or `Full`) |
| Withdrawal | `A` no longer endorses `B` itself | `revokeTrust`, `revokeTrustBatch` (level `None`) |
| Denial | `A` refuses to rely on `B`, even when other agents endorse `B` | `setDenial`, cleared by `clearDenial` |

Each trust record therefore holds a boolean **denial flag** alongside its level. The
flag and the level are independent:

* `setTrust`, `setTrustBatch`, `revokeTrust` and `revokeTrustBatch` MUST NOT change the
  denial flag
* `setDenial` and `clearDenial` MUST NOT change the level, the expiry, or any other
  stored part of the record

Withdrawal does not imply denial, and denial does not imply withdrawal:

```text
Withdraw(A, B, s) ⇏ Deny(A, B, s)
Deny(A, B, s)     ⇏ Withdraw(A, B, s)
```

Denial is not subject to scope fallback. Writing `Deny(A, B, s)` for the flag stored at
scope `s`, the **effective denial** in scope `s` is:

```text
EffectiveDeny(A, B, s) = Deny(A, B, bytes32(0)) ∨ Deny(A, B, s)
```

At universal scope this reduces to `Deny(A, B, bytes32(0))`. A scoped flag that is
`false` never overrides a universal flag that is `true`. Path verification applies
effective denial to every edge and, from the validator, to every later node on the path
(see Validator denial).

Clearing a denial reveals the stored endorsement exactly as it stands: `Full` or
`Marginal` applies again, `None` and `Unknown` still void the edge, and a scoped denial
still applies after a universal one is cleared. An attestation submitted while a denial
is in force updates the stored endorsement but does not clear the denial.

Because a clear reveals whatever is stored when it executes, `clearDenial` takes the
trustor's nonce as the caller observed it during review, and reverts if any attestation
has landed since. That check cannot stop an attestation signed earlier from landing
after the clear, where it applies immediately. Closing that case depends on raising the
nonce floor before the review (see `clearDenial`).

### ENS Integration

The Trust Registry uses ENS namehashes as agent identifiers.

This standard requires access to an ENS registry. On Ethereum mainnet, use the canonical ENS deployment. On other networks, use network-specific ENS deployments or bridges. Implementations also take the network's NameWrapper address, or the zero address where no NameWrapper is deployed. CCIP-Read ([ERC-3668](./eip-3668.md)) is a client-side mechanism and cannot be used for on-chain validation, so agents relying on on-chain identity gates need an on-chain resolver.

```solidity
// ENS namehash computation (per ERC-137)
bytes32 node = keccak256(abi.encodePacked(
   keccak256(abi.encodePacked(bytes32(0), keccak256("eth"))),
   keccak256("alice")
));
// node = namehash("alice.eth")
```

#### External Interfaces

The registry reads three external contracts:

```solidity
interface IENS {
   function owner(bytes32 node) external view returns (address);
   function resolver(bytes32 node) external view returns (address);
   function isApprovedForAll(address owner, address operator) external view returns (bool);
}

/// @dev NameWrapper is an ERC-1155; the token holder is the real name controller
interface INameWrapper {
   function ownerOf(uint256 id) external view returns (address);
   function isApprovedForAll(address owner, address operator) external view returns (bool);
}

interface IAddrResolver {
   function addr(bytes32 node) external view returns (address payable);
}
```

#### Name Controller Resolution

`ens.owner(node)` returns the registry controller. For **wrapped** names that controller
is the NameWrapper contract rather than the party actually controlling the name.
NameWrapper does not implement [ERC-1271](./eip-1271.md), so treating it as the signing
authority would leave every wrapped name unable to attest.

Implementations MUST resolve the controller as follows:

```solidity
function controllerOf(bytes32 node) internal view returns (address) {
   address owner = ens.owner(node);
   if (owner == address(0)) return address(0);

   // Wrapped name: the ERC-1155 holder is the real controller
   if (nameWrapper != address(0) && owner == nameWrapper) {
      try INameWrapper(nameWrapper).ownerOf(uint256(node)) returns (address wrapped) {
         return wrapped; // see Wrapped Name Lifecycle
      } catch {
         return address(0);
      }
   }

   return owner;
}
```

Wherever this standard refers to "the ENS name owner", it means `controllerOf(node)`.

The NameWrapper keeps a set of *fuses* for each wrapped name: permission flags that, once
burned, cannot be unburned until the name's NameWrapper expiry passes. Burning
`PARENT_CANNOT_CONTROL` on a subname *emancipates* it, so its parent can no longer replace
or unwrap it.

Authority follows ownership as the registry and the NameWrapper report it, not ENS
management permissions. `controllerOf` does not consult `canModifyName`, fuses, or the
`.eth` registrar's expiry.

#### Wrapped Name Lifecycle

The NameWrapper's `ownerOf` reports a holder until the name's NameWrapper expiry has
passed. Once it has, all fuses reset. `ownerOf` then returns the zero address only if
`PARENT_CANNOT_CONTROL` was burned, so `controllerOf` behaves as follows:

| Name | Before NameWrapper expiry | After NameWrapper expiry |
|------|---------------------------|--------------------------|
| Wrapped `.eth` second-level name | holder, including during the 90-day grace period | zero address |
| Emancipated subname (`PARENT_CANNOT_CONTROL` burned) | holder | zero address |
| Unemancipated wrapped subname | holder | holder; fuses reset |

An unwrapped name has no NameWrapper expiry: `controllerOf` returns its registry owner
before and after the registrar expiry (see [Expired Unwrapped Names](#expired-unwrapped-names)).

For a wrapped `.eth` second-level name, the NameWrapper sets its expiry to the registrar
expiry plus the 90-day grace period when the name is wrapped, and a renewal through the
NameWrapper (`NameWrapper.renew`) normally sets it again. A renewal that calls the
BaseRegistrar's `renew` directly extends the registrar expiry but not the NameWrapper
expiry. Registrar controllers on mainnet have used both paths. The holder then loses control when the old
NameWrapper expiry passes, although the name is still registered and no one else can
register it. A later renewal through the NameWrapper can set the NameWrapper expiry from
the registrar expiry again, and the same holder then regains control. Neither kind of
renewal emits a NameWrapper event, so whether a wrapped name has a controller is read
from state (`controllerOf`, or the NameWrapper expiry from `getData`), not inferred from
renewals. Where this standard refers to the end of a wrapped name's grace period, it
means its NameWrapper expiry.

For the 90 days before its NameWrapper expiry, the NameWrapper treats a wrapped `.eth`
second-level name as in its grace period. It refuses every management operation on the
name (`canModifyName` returns false), but `ownerOf` still returns the holder, and the
holder keeps every power this standard grants. Normally this is the registrar grace
period, during which no one else can register the name.

Emancipated subnames have no grace period. An unemancipated subname never loses its
holder through expiry. Its NameWrapper expiry is often zero, and its parent can reassign
it at any time (see Parent-Controlled Subnames).

An endorsement (`Marginal` or `Full`) issued while its trustor, a `.eth` second-level
name, is past its registrar expiry is the one most likely to outlive the registration
that issued it, since an unrenewed name passes to its next registrant with every record
it set. The contract accepts it like any other. The recommendations below guide signers
and coordinators, and do not change what the contract accepts or what the
path-validation functions return. For such names, wrapped or unwrapped:

* A trustor that signs or sets an endorsement after its registrar expiry SHOULD give it
  an `expiry` no later than the end of the grace period, and SHOULD issue it again after
  renewing.
* A coordinator that relies on such an endorsement SHOULD apply two separate checks:
  * **Continuity: has the name been registered again?** The coordinator SHOULD treat
    the endorsement as ineligible once the BaseRegistrar has emitted `NameRegistered`
    for the trustor's label after the endorsement's `TrustSet` event. That event is
    the latest `TrustSet` for the record the path uses: the trustor, trustee and scope
    that scope fallback selects for the validation scope (see [Scope Fallback
    Semantics](#scope-fallback-semantics)), not the latest record for the pair in any scope. `NameRenewed` does
    not end it, however many renewals follow. Both events are indexed by the
    labelhash, so the coordinator needs the trustor's label, checked against the node. A
    later `nameExpires` alone does not show a renewal, because a registration after the
    grace period also produces one. The coordinator orders the `TrustSet` event against
    these events by block number, transaction index and log index, not by block
    timestamp, because events in the same block share a timestamp. A registration by the
    same holder also ends the endorsement, which the trustor then issues again. The
    check concerns registration, not control: a transfer within one registration emits
    no `NameRegistered` (see [Monitoring Control Changes](#monitoring-control-changes)). A coordinator that cannot
    establish the label, or every such event from the `TrustSet` event to the block at
    which it decides, SHOULD NOT rely on the endorsement. This check is not limited to
    endorsements issued past the trustor's expiry: a coordinator applies it to every
    attestation a `.eth` second-level name sets or receives, whenever it was issued (see
    below).
  * **Liveness, for a wrapped trustor: does the name have a controller now?** The
    coordinator reads `controllerOf(node)` (in practice the NameWrapper's `ownerOf`) or
    the NameWrapper expiry (`getData(node)`) when it makes its decision, and SHOULD NOT
    rely on the endorsement while the name has no controller. A `NameRenewed` event is
    not evidence of liveness: a renewal that bypasses the NameWrapper emits it without
    extending the NameWrapper expiry. Like the continuity check, this check is not
    limited to endorsements issued past the trustor's expiry: a coordinator applies it to
    every endorsement a wrapped trustor on the path sets, whenever it was issued.
* A coordinator that relies on such an endorsement SHOULD validate with `enforceExpiry`
  set, monitor the trustor's control, its registrar expiry and, for a wrapped trustor,
  its NameWrapper expiry, and re-evaluate its gates when control changes (see Monitoring
  Control Changes).

An expiry on the name's own endorsements does not bound a path through it. The next
registrant inherits every attestation naming the name as trustee, and can set new
endorsements from it at once. Once the name is re-registered, a path from an earlier
trustor through the name reaches any party the new registrant endorses, however the
earlier holder capped its own endorsements. Only the attestation that points to the name
bounds such a path. For an attestation whose trustee is a `.eth` second-level name,
wrapped or unwrapped:

* A trustor SHOULD give it an `expiry` no later than the end of the trustee's grace
  period, and SHOULD issue it again after the trustee renews. An attestation signed
  before the trustee's registrar expiry, with the 90-day maximum recommended under
  Identity Continuity, already meets this.
* A coordinator SHOULD apply the continuity check above to every `.eth` second-level
  name on the path, as trustee as well as trustor, and SHOULD validate with
  `enforceExpiry` set. It treats an attestation pointing to the name as ineligible once
  the name has been registered again after the attestation's `TrustSet` event. This
  bounds the path where the trustor did not cap the expiry, and spares the trustor a new
  signature after each renewal.
* For an attestation whose trustee is an emancipated subname, a trustor SHOULD give it
  an `expiry` no later than the subname's NameWrapper expiry, after which the parent can
  create the subname again for another holder (see Parent-Controlled Subnames).
* A coordinator SHOULD apply the same check to every name on the path below a `.eth`
  second-level name. It treats such a name as registered again whenever its
  second-level ancestor is, since the ancestor's next registrant can reassign it, and
  whenever the name, or an ancestor of it below the second-level name, has been wrapped
  again after the attestation's `TrustSet` event. A name has been wrapped again when the
  NameWrapper emits `NameWrapped` for its node, which is indexed. The NameWrapper emits
  it whenever a name becomes wrapped, including when a parent creates an emancipated
  subname again after its NameWrapper expiry. It does not emit it when a parent
  reassigns a subname that still has a holder in the NameWrapper, which is a change of
  control (see Parent-Controlled Subnames). A holder that unwraps its subname and wraps
  it again also emits it, and its trustors then sign again. The coordinator orders the
  event as above. Finding the ancestors needs the name, checked against the node, as the
  check above needs the label.
* A registration by the same holder ends these attestations too, not only the
  holder's own endorsements. A holder that lets its name pass its grace period and
  registers it again therefore needs every trustor that endorsed it to sign again. A
  trustor SHOULD watch its trustees' registrations as well as their expiries.

Implementations MUST pin the `nameWrapper` address at deployment, and MUST NOT allow it
to be changed afterwards: a registry pointed at a hostile contract in that slot would let
it claim control of every wrapped name. Implementations deployed on networks with no
NameWrapper deployment MUST set `nameWrapper` to the zero address, which disables
unwrapping.

#### Agent Address Resolution

[ERC-8001](./eip-8001.md) identifies participants by address (`address[] participants`),
while this registry identifies agents by ENS namehash. The binding between the two is
the node's forward address record ([ERC-137](./eip-137.md)):

```solidity
/// @dev Gas forwarded to a node's resolver
uint256 internal constant RESOLVE_GAS = 50_000;

function resolveAgent(bytes32 node) public view returns (address) {
   address resolver = ens.resolver(node);
   if (resolver == address(0)) return address(0);

   // Low-level, gas-capped, bounded-copy call: a hostile resolver can neither make
   // resolution revert nor consume more than RESOLVE_GAS
   bytes memory data = abi.encodeWithSelector(IAddrResolver.addr.selector, node);
   bool ok;
   uint256 word;
   uint256 size;
   assembly ("memory-safe") {
      ok := staticcall(RESOLVE_GAS, resolver, add(data, 0x20), mload(data), 0, 0x20)
      size := returndatasize()
      word := mload(0)
   }
   if (!ok || size < 0x20 || word >> 160 != 0) return address(0);
   return address(uint160(word));
}
```

An address `a` is bound to node `n` if and only if `resolveAgent(n) == a` and
`a != address(0)`. No separate registration step is required: the `addr` record is the
controller's statement of which address the name denotes. That statement can outlive the
controller that made it, because ENS does not clear the record when a name expires or is
re-registered. After a re-registration the record keeps naming the previous holder's
address until the new controller changes it, and a wrapped name keeps its record after
its NameWrapper expiry passes, while nobody controls it. `validateParticipantAddress`
therefore also requires the node to have a controller, which covers the second case but
not the first (see [Resolver Trust](#resolver-trust)).

Resolution is a **verification** primitive, not a search. Callers supply the node as the
terminal element of a `TrustPath` and the registry confirms that it resolves to the
participant address. This standard does not use reverse resolution, which is
self-asserted and would require on-chain string handling to verify.

`resolveAgent` MUST NOT revert because of the resolver's behaviour. It MUST return the
zero address when the node has no resolver, or when the call to `addr` reverts, runs out
of gas, returns fewer than 32 bytes, or returns a first word with any of its upper 96
bits set. Return data beyond the first 32 bytes MUST be ignored. Implementations MUST
bound the gas forwarded to the resolver; the reference implementation forwards 50,000.

Nodes served by an off-chain resolver (CCIP-Read) cannot be resolved during on-chain
validation: `addr` reverts and `resolveAgent` returns the zero address. Agents that need
to pass on-chain identity gates MUST publish an on-chain `addr` record, served by a
resolver that answers `addr` within the gas bound.

#### Identity Continuity

The ENS name, not the key behind it, is the identity. When a name is transferred, the new
controller inherits every attestation naming it as trustee, and gains authority over
every attestation and every denial in which it is the trustor.

The same holds for gates. A gate's `gatekeeperNode` and `requiredAnchors` identify ENS
names, not their controllers. When control of one of those names changes, its role in
the gate passes to the new controller, and the gate configuration does not change.
Coordinators SHOULD monitor control changes for the gatekeeper and anchor nodes of their
gates, and SHOULD re-evaluate the affected gates when one occurs. See Gatekeeper and
Anchor Names.

Attestations covering high-stakes scopes SHOULD carry short expiries (RECOMMENDED: 90
days maximum), so that a transfer cannot carry inherited trust forward indefinitely.
Agents SHOULD monitor control changes on ENS names they trust, and re-evaluate trust
when a trusted name changes hands. No single event stream reports every change of
control; see Monitoring Control Changes.

Agents SHOULD use wrapped `.eth` second-level names or emancipated subnames, whose
authority ends when their NameWrapper expiry passes, normally the end of the 90-day grace
period for a `.eth` second-level name (see
[Wrapped Name Lifecycle](#wrapped-name-lifecycle)). Gatekeepers SHOULD prefer such names
for gatekeeper and anchor nodes. An unwrapped name keeps its authority after it expires,
and an unemancipated wrapped subname keeps it indefinitely (see
[Expired Unwrapped Names](#expired-unwrapped-names)). A name keeps this expiry only while
it stays wrapped: unless `CANNOT_UNWRAP` is burned its holder can unwrap it, and the
current `.eth` registrar controller registers names unwrapped, so a name that lapses
while wrapped is unwrapped under its next registrant unless that registrant wraps it.
Coordinators SHOULD therefore check whether a name is wrapped when they verify a path or
gate, not rely on its status when an endorsement was issued. Fuses can also stop a name
changing hands, at a long-term cost (see [Name Locking with Fuses](#name-locking-with-fuses)).

### Signature Authority

Trust attestations MUST be signed by an address with signing authority for the ENS name.

**Signing authority** is limited to:

* The ENS name controller (`controllerOf(node)`, which unwraps NameWrapper names), OR
* For contract controllers: any signer the contract validates via [ERC-1271](./eip-1271.md)

**Transaction submission** is governed by the following authority model. "Approved
operator" means an address for which `isApprovedForAll` returns true on whichever
contract holds the name, per `canSubmitRevocation`. A per-token approval (`approve` on
the NameWrapper or the `.eth` registrar) is not an operator approval and grants no
authority under this standard, although it carries powers in ENS itself (see below). An
operator approval belongs to the holder that granted it, so it no longer applies once
the name changes hands.

| Operation | Controller | Approved operator | Any address |
|-----------|:----------:|:-----------------:|:-----------:|
| `setTrust`, `setTrustBatch` | signs | no | MAY submit a valid signature |
| `revokeTrust`, `revokeTrustBatch` | MAY call | MAY call | no |
| `setDenial`, `clearDenial` | MAY call | **MUST NOT** | no |
| `invalidateNonces` | MAY call | **MUST NOT** | no |
| `setIdentityGate`, `removeIdentityGate` | keyed by `msg.sender`; no ENS authority involved | | |

Approved operators MAY perform **withdrawal** because its effect is bounded to the
trustor's own endorsement of one trustee, in the scopes named in the call.

Approved operators MUST NOT call `setDenial` or `clearDenial`: denial decides whose
judgement the trustor accepts, the same authority as signing an attestation. A
controller that wants to delegate it can use a contract controller.

Approved operators MUST NOT call `invalidateNonces`: raising the nonce floor voids every
outstanding attestation of the trustor, for every trustee and scope, which a name
management approval was not granted to do (see
[Why Is `invalidateNonces` Controller-Only?](#why-is-invalidatenonces-controller-only)).

These restrictions are only as strong as the ENS ownership model beneath them. An
address approved through `isApprovedForAll` can change a name's registry owner, or
transfer its NameWrapper token unless `CANNOT_TRANSFER` is burned, and a per-token
approval on the `.eth` registrar can transfer or `reclaim` an unwrapped name. Such an
operator can make itself the controller and acquire every controller-only power, or
migrate the name to ENSv2, which ends all authority over it under this standard. The
restrictions stop an approval being used as controller authority in place; they do not
stop an operator with transfer authority taking control. Trustors SHOULD grant
`isApprovedForAll`, and per-token approvals on the `.eth` registrar, only to parties they
would trust with control of the name. A per-token approval on the NameWrapper cannot
transfer the name, but lets its holder extend the expiry of the name's subnames, which
prolongs an emancipated subname holder's authority; if `CANNOT_APPROVE` is burned, it
also survives a transfer of the name.

Implementations MUST attempt ECDSA recovery before [ERC-1271](./eip-1271.md), and MUST
reject malleable (high-s) signatures. A controller that has code is not necessarily a
contract account: an EOA with an [EIP-7702](./eip-7702.md) delegation has code, and its
delegate need not implement `isValidSignature`, so routing every controller with code
straight to [ERC-1271](./eip-1271.md) would reject that EOA's valid signatures.

An [ERC-1271](./eip-1271.md) call that reverts, returns fewer than 32 bytes, or returns a
first word other than the magic value `0x1626ba7e` left-aligned with zero padding MUST be
treated as a failed signature, so `setTrust` reverts with `InvalidSignature` rather than
with the controller's revert data or an empty revert.

```solidity
/// @dev Verify signature - signing authority is the name controller only
function verifySignature(
   bytes32 node,
   bytes32 digest,
   bytes calldata signature
) internal view returns (bool) {
   address controller = controllerOf(node);
   if (controller == address(0)) return false;

   // ECDSA first: covers plain EOAs and EIP-7702 delegated EOAs
   (address recovered, ECDSA.RecoverError err, ) = ECDSA.tryRecover(digest, signature);
   if (err == ECDSA.RecoverError.NoError && recovered == controller) return true;

   // ERC-1271 fallback for any controller with code
   if (controller.code.length == 0) return false;
   // Low-level call with a returndata length check: a high-level call would revert
   // with empty data (not InvalidSignature) when the controller's code returns
   // nothing, e.g. an EIP-7702 delegate with an empty fallback
   return SignatureChecker.isValidERC1271SignatureNow(controller, digest, signature);
}

/// @dev Check if caller can submit a revokeTrust transaction
function canSubmitRevocation(bytes32 node, address caller) internal view returns (bool) {
   address controller = controllerOf(node);
   if (controller == address(0)) return false;
   if (caller == controller) return true;

   // Approvals live on whichever contract actually holds the name
   if (nameWrapper != address(0) && ens.owner(node) == nameWrapper) {
      return INameWrapper(nameWrapper).isApprovedForAll(controller, caller);
   }

   return ens.isApprovedForAll(controller, caller);
}
```

### Primary Types

```solidity
struct TrustAttestation {
   bytes32 trustorNode;       // ENS namehash of trustor
   bytes32 trusteeNode;       // ENS namehash of trustee
   TrustLevel level;          // Trust level assigned
   bytes32 scope;             // Scope restriction; bytes32(0) = universal
   uint64 expiry;             // Unix timestamp; 0 = no expiry
   uint64 nonce;              // Per-trustor monotonic nonce
}

struct ValidationParams {
   uint8 maxPathLength;       // Maximum trust chain depth (1-10)
   TrustLevel minEdgeTrust;   // Minimum trust level required on each edge
   bytes32 scope;             // Scope to verify against; bytes32(0) = universal
   bool enforceExpiry;        // Check expiry on all chain elements
   bytes32[] requiredAnchors; // Path MUST traverse at least one anchor; empty = no requirement
}

struct TrustPath {
   bytes32[] nodes;           // [validator, ...intermediaries..., target]
}
```

**Path length definition**: Path length is the number of edges (trust relationships) in the path. A direct trust relationship has path length 1. A path `[A, B, C]` has length 2.

#### Default Validation Parameters

When not specified, implementations SHOULD use:

```solidity
ValidationParams({
   maxPathLength: 5,
   minEdgeTrust: TrustLevel.Marginal,
   scope: bytes32(0),
   enforceExpiry: true,
   requiredAnchors: new bytes32[](0)
})
```

#### Validation Parameters Constraints

Implementations MUST reject `ValidationParams` where:

| Condition | Error |
|-----------|-------|
| `maxPathLength == 0` or `maxPathLength > 10` | `InvalidMaxPathLength` |
| `minEdgeTrust == TrustLevel.Unknown` or `minEdgeTrust == TrustLevel.None` | `InvalidMinEdgeTrust` |
| `requiredAnchors.length > 10` | `TooManyRequiredAnchors` |

Both `verifyPath` and `setIdentityGate` MUST apply these constraints, through a shared
routine, before the parameters are used. The Gate Constraints below are not part of that
routine.

#### Gate Constraints

`setIdentityGate` MUST also reject the following parameters, which no path can satisfy:

| Condition | Error |
|-----------|-------|
| `requiredAnchors.length > 0` and `maxPathLength < 2` | `UnsatisfiableAnchors` |

Only intermediary nodes satisfy an anchor (see Anchor semantics), and a path of one edge
has none, so such a gate would reject every participant. `setIdentityGate` applies this
check after the Validation Parameters Constraints. `verifyPath` MUST NOT apply it: given
these parameters directly, it returns `false`, as it does for any path that misses its
anchors. This is the only unsatisfiable configuration `setIdentityGate` rejects. Others,
such as a gate whose only anchor is its own gatekeeper, are accepted and reject every
participant.

### Interface Detection

Implementations MUST implement [ERC-165](./eip-165.md) and MUST return `true` from
`supportsInterface` for:

| Interface | Identifier |
|-----------|------------|
| `IERC165` | `0x01ffc9a7` |
| `ITrustRegistry` | `0x94f0ee34` |

Per [ERC-165](./eip-165.md), `supportsInterface` MUST return `false` for `0xffffffff`
and MUST use at most 30,000 gas.

`ITrustRegistry`'s identifier is the XOR of the selectors of the seventeen functions
declared in this document, excluding the inherited `supportsInterface`, matching
Solidity's `type(ITrustRegistry).interfaceId`.

Adding, removing, or changing the signature of any function in `ITrustRegistry` changes
its identifier. Implementations tracking a draft revision of this standard SHOULD
recompute rather than hard-code the constant.

Earlier drafts had two other identifiers, and implementations of this revision MUST NOT
report `true` for either:

* `0x42b46ef5`, for drafts with no denial. The functions it covers are still present,
  but their path verification semantics differ
* `0x31f35e83`, for drafts in which `setDenial(bytes32,bytes32,bytes32,bool,bytes32)`
  both set and cleared a denial, with no check on what the clear would reveal

Earlier drafts also declared an optional `ITrustRegistryExtended`, identified by
`0x93e686a3`. This revision does not define it, and assigns that identifier no meaning.

### Semantics

#### `setTrust`

`setTrust` MUST revert, in the order given under Revert Order, if:

* `attestation.trustorNode == attestation.trusteeNode` (self-trust prohibited)
* `attestation.level` is `Unknown` or `None` (withdrawal is expressed by revocation, not attestation)
* `attestation.expiry != 0 && attestation.expiry <= block.timestamp`
* The ENS name for `trustorNode` does not exist (`ens.owner(trustorNode)` is the zero address)
* `attestation.nonce <= getNonce(attestation.trustorNode)`
* `attestation.nonce > getNonce(attestation.trustorNode) + 2**32`, with the same
  overflow-safe bound as `invalidateNonces`. The error is
  `NonceJumpTooLarge(attestation.nonce, bound)`
* The signature does not verify per the Signature Authority section, including when
  `controllerOf` returns the zero address, as it does for a wrapped `.eth` name past its
  NameWrapper expiry

If valid:

* The trust level and expiry MUST be stored, keyed by `(trustorNode, trusteeNode, scope)`
* The denial flag for that key MUST NOT change
* `getNonce(trustorNode)` MUST return the attestation's nonce
* `TrustSet` MUST be emitted

An attestation is accepted while the trustee is denied. It updates the stored
endorsement, which takes effect only when the denial is cleared.

#### `setTrustBatch`

`setTrustBatch` MUST revert, in the order given under Revert Order, if:

* `attestations.length != signatures.length`
* `attestations` is empty
* Any attestation has a different `trustorNode` than the first attestation
* Nonces within the batch are not strictly increasing
* Any individual attestation would fail `setTrust` validation

The batch-level conditions apply to the whole batch before any attestation is checked
individually.

#### `revokeTrust`

`revokeTrust` withdraws the trustor's endorsement. It is the only way to reach
`TrustLevel.None`.

`revokeTrust` MUST revert if:

* Caller is not the name controller or an approved operator for `trustorNode`

If valid:

* Trust level MUST be set to `None`
* The stored expiry MUST be set to `0`, so `getTrust` returns `(None, 0)` for every
  revoked record
* The denial flag MUST NOT change
* `TrustRevoked` MUST be emitted
* The relationship MUST remain in storage (not deleted) to preserve the withdrawal

A prior trust relationship is **not** required. A trustor MAY withdraw in a scope it never
granted. Such a preemptive withdrawal is a tombstone: it blocks the universal fallback in
that scope, and so blocks paths that would otherwise route through the edge there.
Callers that want to distinguish withdrawing an existing endorsement from a preemptive
tombstone MUST read `getTrust` first; the registry does not make that distinction.

A withdrawal at `bytes32(0)` voids the trustor's edge to the trustee in every scope,
overriding positive scoped records for the same pair. A withdrawal in any other scope
affects that scope only. In both cases only the named record is written, so `getTrust`
for another scope still returns that scope's stored record; the override is applied
during path verification (see [Scope Fallback Semantics](#scope-fallback-semantics)).

Withdrawal removes an edge and nothing else: paths through other agents that still
endorse the trustee remain valid, including paths the trustor evaluates as validator,
whatever the reason code. A trustor that refuses to rely on the trustee at all MUST use
`setDenial`.

Withdrawal does **not** invalidate attestations the trustor has already signed but not
yet submitted. See `revokeTrustBatch` and `invalidateNonces`.

#### `revokeTrustBatch`

`revokeTrustBatch` applies `revokeTrust` to several scopes for the same
`(trustorNode, trusteeNode)` pair in a single transaction.

`revokeTrustBatch` MUST revert if:

* Caller is not the name controller or an approved operator for `trustorNode`
* `scopes` is empty

If valid, for each listed scope:

* Trust level MUST be set to `None`
* The stored expiry MUST be set to `0`
* The denial flag MUST NOT change
* `TrustRevoked` MUST be emitted
* The relationship MUST remain in storage

Because trust is keyed by `(trustorNode, trusteeNode, scope)`, a trustor that has
granted trust in several scopes must name each one. Implementations MUST NOT enumerate
scopes on-chain; callers derive the list from `TrustSet` logs, which is the same
off-chain indexing this standard already assumes for path computation.

#### `setDenial`

`setDenial` denies `trusteeNode` within the trustor's decisions in `scope`.

`setDenial` MUST revert, in the order given under Revert Order, if:

* Caller is not the name controller for `trustorNode` (approved operators are **not**
  sufficient; see [Signature Authority](#signature-authority)). This includes a name whose `controllerOf` is the
  zero address
* `trustorNode == trusteeNode`

If valid and the stored flag is `false`:

* The stored flag for `(trustorNode, trusteeNode, scope)` MUST be set to `true`
* The trust level, expiry and every other stored part of the record MUST NOT change
* `DenialSet` MUST be emitted with `denied = true`

If the stored flag is already `true`, `setDenial` MUST succeed without changing storage
and MUST NOT emit `DenialSet`. `setDenial` takes no nonce: denying is never blocked by
other activity on the trustor's name.

#### `clearDenial`

`clearDenial` clears the trustor's denial of `trusteeNode` in `scope`, on condition that
the endorsements it would reveal are the ones the caller reviewed.

`clearDenial` MUST revert, in the order given under Revert Order, if:

* Caller is not the name controller for `trustorNode`, as for `setDenial`
* `trustorNode == trusteeNode`
* `getNonce(trustorNode) != expectedNonce`, with `NonceChanged(expectedNonce, current)`

The nonce check applies whether or not the flag is set. Every attestation that is
stored raises the trustor's nonce, as does `invalidateNonces`, so an unchanged nonce
means no endorsement by the trustor, for any trustee and in any scope, has been written
since the caller read it. Withdrawals do not raise the nonce, but can only reduce trust.

If valid and the stored flag is `true`:

* The stored flag for `(trustorNode, trusteeNode, scope)` MUST be set to `false`
* The trust level, expiry and every other stored part of the record MUST NOT change
* `DenialSet` MUST be emitted with `denied = false`

If the stored flag is already `false`, `clearDenial` MUST succeed without changing
storage and MUST NOT emit `DenialSet`. Every `DenialSet` event from either function
therefore records a change, and the latest event for a key gives its stored flag.

The nonce check stops an attestation that lands *before* the clear from taking effect
through it. It cannot stop one that lands *after*: an attestation signed above the
current nonce stays submittable, and once the denial is cleared it applies as soon as it
is stored. A caller SHOULD therefore clear in this order:

1. If the trustor may have signed attestations that are not yet stored, call
   `invalidateNonces` with a floor above every nonce the trustor has signed
2. After that call has executed, read `getNonce(trustorNode)`, review the stored
   endorsements, and pass the nonce read to `clearDenial`

After step 1 no attestation signed earlier can be stored, so the endorsements reviewed
are the ones the clear reveals. An attestation the trustor signs after step 1 and holds
until after the clear applies once stored; that is fresh authorisation by the
controller, so no further mechanism is specified. A caller that must not let
unreviewed attestations take effect right after reinstatement SHOULD pause or serialise
the trustor's signing from step 1 until the clear has executed, especially when
different components handle signing and recovery. If `clearDenial` reverts with
`NonceChanged`, the caller SHOULD review again before retrying with the new nonce.

Prior trust is not required: a trustor MAY deny an agent it never endorsed. A universal
denial applies in every scope, and no scoped flag can lift it. Denial has no expiry; it
holds until the controller clears it.

#### `getDenial`

`getDenial` MUST return the denial flag stored for exactly `(trustorNode, trusteeNode,
scope)`. It MUST NOT return the effective denial: after a universal denial,
`getDenial` for a named scope returns that scope's own flag. This matches `getTrust`,
which also returns stored data, and lets clients inspect each scope's flag.

Callers derive the effective denial from two reads:

```text
effectiveDenial(A, B, s) = getDenial(A, B, bytes32(0)) || getDenial(A, B, s)
```

A scoped flag that is `false` never overrides a universal flag that is `true`. To lift
an effective denial in scope `s`, both the universal flag and the flag for `s` have to be
cleared.

#### `invalidateNonces`

An attestation carries no signing timestamp, so one signed at nonce `N` remains
submittable until the trustor's nonce reaches `N`, whatever has been revoked since.
`invalidateNonces` lets a trustor raise that floor.

`invalidateNonces` MUST revert if:

* Caller is not the name controller for `trustorNode` (approved operators are **not**
  sufficient; see [Signature Authority](#signature-authority))
* `newNonce <= getNonce(trustorNode)`
* `newNonce > getNonce(trustorNode) + 2**32`, evaluated without overflow: when that sum
  exceeds `type(uint64).max`, the bound is `type(uint64).max`. The error is
  `NonceJumpTooLarge(newNonce, bound)`

If valid:

* `getNonce(trustorNode)` MUST return `newNonce`
* `NoncesInvalidated` MUST be emitted

Every attestation signed with a nonce at or below `newNonce` becomes permanently
unusable, whichever trustee or scope it names.

Trustors SHOULD issue nonces sequentially (`getNonce(trustorNode) + 1`) so that the
highest outstanding nonce is always known. Signing far ahead of the current nonce
creates attestations that stay submittable indefinitely; `setTrust` rejects an
attestation more than 2^32 above the current nonce.

To quarantine a compromised or misbehaving counterparty, a trustor SHOULD:

1. **Set denial** at universal scope. The counterparty then fails every edge from the
   trustor and every path the trustor evaluates as validator, so gates whose gatekeeper
   is the trustor reject it in every evaluation from then on, even while other agents
   still vouch for it. Gates whose gatekeeper is any other agent are unaffected.
2. **Invalidate outstanding nonces**, with a floor above every nonce the trustor has
   signed. This is trustor-wide: it voids the trustor's outstanding attestations for
   every trustee and scope, not only the counterparty's. Attestations signed with a
   nonce above the chosen floor remain submittable.
3. **Investigate and recover**: once step 2 has executed, read the trustor's nonce,
   review the stored endorsements, withdraw those that should not return, then call
   `clearDenial` with the nonce read if the counterparty is reinstated.

The denial does not depend on step 2: a pre-signed attestation submitted later updates
the stored endorsement but cannot lift the denial. Step 2 matters for recovery, since
clearing the denial reveals whatever endorsement is stored at that time, and the nonce
check in `clearDenial` relies on it (see [`clearDenial`](#cleardenial)).

Every step requires the name controller. The procedure assumes the trustor's own
controller is sound; see [Key Compromise](#key-compromise).

#### `verifyPath` — Path Verification Algorithm

`verifyPath` validates a pre-computed trust path.

`verifyPath` returns a single verdict. It MUST return `false` unless **every**
requirement is satisfied, including the `requiredAnchors` constraint. A path whose
edges all verify but which does not traverse a required anchor is not valid, and
implementations MUST NOT report it as such.

**Parameter validation:** `verifyPath` MUST reject `ValidationParams` that violate the
Validation Parameters Constraints **before** using them, through the same routine
`setIdentityGate` uses. Without this, `minEdgeTrust == TrustLevel.Unknown` would make
the per-edge comparison `level < minEdgeTrust` never true, and a path with no trust at
all would verify.

`validateParticipantWithPath` and `validateParticipantAddress` read parameters from a
stored gate rather than from the caller. Those parameters were validated when
`setIdentityGate` stored them, so those functions MAY skip revalidation, as the
pseudocode below does by passing `validateParams = false`; they MUST NOT accept
parameters from any other source.

##### Algorithm

The external functions are thin wrappers around internal helpers that take `memory`
arguments: `_verifyPath`, `_getTrust` (the stored record, as `getTrust` returns it) and
`_getIdentityGate` (the stored gate, as `getIdentityGate` returns it). The
`validateParams` flag is `false` only for parameters read from a stored gate.

```solidity
function verifyPath(
   TrustPath calldata path,
   ValidationParams calldata params
) external view returns (bool valid) {
   return _verifyPath(path, params, true);
}

function _verifyPath(
   TrustPath memory path,
   ValidationParams memory params,
   bool validateParams
) internal view returns (bool) {
   // Parameters are validated BEFORE they are used. Skipping this would let
   // minEdgeTrust == Unknown make every edge comparison vacuously pass.
   if (validateParams) requireValidParams(params);

   // Path must have at least 2 nodes (validator and target)
   if (path.nodes.length < 2) return false;

   // Path length constraint (edges = nodes - 1)
   if (path.nodes.length - 1 > params.maxPathLength) return false;

   // Nodes MUST be distinct; a repeated node inflates length without adding trust.
   // maxPathLength caps this at 11 nodes, so the quadratic scan is bounded.
   for (uint256 i = 0; i < path.nodes.length; i++) {
      for (uint256 j = i + 1; j < path.nodes.length; j++) {
         if (path.nodes[i] == path.nodes[j]) return false;
      }
   }

   // The validator's denial overrides any indirect endorsement.
   // k = 1 is already covered by the first edge check.
   bytes32 validator = path.nodes[0];
   for (uint256 k = 2; k < path.nodes.length; ++k) {
      (, , bool validatorDenies) = _edgeTrust(validator, path.nodes[k], params.scope);
      if (validatorDenies) return false;
   }

   // Track anchor satisfaction
   bool foundAnchor = params.requiredAnchors.length == 0;

   // Verify each edge
   for (uint256 i = 0; i < path.nodes.length - 1; i++) {
      // Universal None, then a stored scoped record, then universal trust
      (TrustLevel level, uint64 expiry, bool denied) =
         _edgeTrust(path.nodes[i], path.nodes[i + 1], params.scope);

      // Denial voids the edge whatever its endorsement
      if (denied) return false;

      // Edge must meet minimum trust level
      if (level < params.minEdgeTrust) return false;

      // None explicitly voids (even if minEdgeTrust is somehow None)
      if (level == TrustLevel.None) return false;

      // Expiry check
      if (params.enforceExpiry && expiry != 0 && expiry <= block.timestamp) {
         return false;
      }

      // Anchor check (intermediate nodes only, not first or last)
      if (!foundAnchor && i > 0) {
         for (uint256 j = 0; j < params.requiredAnchors.length; j++) {
            if (path.nodes[i] == params.requiredAnchors[j]) {
               foundAnchor = true;
               break;
            }
         }
      }
   }

   // Anchors are part of the verdict, not a separate advisory signal
   return foundAnchor;
}
```

**Node uniqueness:** A path MUST NOT contain the same node twice. Repeated nodes cannot
manufacture trust, since every edge is still checked, but they inflate path length and
serve no purpose. `maxPathLength` bounds a path at 11 nodes, so the duplicate scan is at
most 55 comparisons.

**Edge denial:** `verifyPath` MUST return `false` if, for any edge `nodes[i] → nodes[i+1]`,
`EffectiveDeny(nodes[i], nodes[i+1], params.scope)` holds (see [Denial](#denial)). This applies
whatever endorsement the edge stores, whether or not `enforceExpiry` is set, and
whatever `minEdgeTrust` is.

**Validator denial:** `verifyPath` MUST return `false` if, for any node `nodes[k]` with
`k >= 2`, `EffectiveDeny(nodes[0], nodes[k], params.scope)` holds. For `k = 1` the edge
denial check already applies.

The validator check is per validator, not global. It applies only to paths evaluated
with the denying agent as `nodes[0]`. A denial held by any other node on the path voids
the path only through the edge check on that node's own outgoing edge. The validator
check reads denial only: the validator's trust levels for nodes beyond the first,
including `None` and `Unknown`, do not void the path.

**Formal statement.** Write a path as `P = [P0, …, Pn]` with `n ≥ 1`, write `s` for
`params.scope`, write `L(A, B, s)` and `x(A, B, s)` for the level and expiry chosen by the
Scope fallback semantics, and write `D(A, B, s)` for `EffectiveDeny(A, B, s)`. A path
that has distinct nodes, satisfies `n ≤ maxPathLength`, and meets the anchor
requirement is valid if and only if both of the following hold:

```text
Endorsement:  ∀ i ∈ [0, n):  L(Pi, Pi+1, s) ≥ minEdgeTrust
                             ∧ ¬(enforceExpiry ∧ x(Pi, Pi+1, s) ≠ 0 ∧ x(Pi, Pi+1, s) ≤ now)

Denial:       ∀ i ∈ [0, n):  ¬D(Pi, Pi+1, s)
              ∀ k ∈ [2, n]:  ¬D(P0, Pk, s)
```

Together the two denial lines give `¬D(P0, Pk, s)` for every `k ∈ [1, n]`. The two checks
read different state under different authority. The endorsement check reads levels,
which are written by signed attestations and by withdrawals that approved operators may
submit. The denial check reads denial flags, which only the name controller can write.
A withdrawal therefore changes only the endorsement check, and only for the edge it
names.

**Anchor semantics:** Only intermediary nodes (indices `1` through
`nodes.length - 2`) can satisfy `requiredAnchors`. The validator and the target
are excluded, so a direct edge `[A, B]` can never satisfy a non-empty
`requiredAnchors`. For the same reason `setIdentityGate` rejects a gate that requires
anchors but allows only one edge (see [Gate Constraints](#gate-constraints)). Callers that want anchors to
be advisory MUST pass an empty `requiredAnchors` array rather than inspecting a partial
result.

##### Scope Fallback Semantics

"Universal" below means the record stored at `bytes32(0)`. When `params.scope` is
`bytes32(0)`, the universal record applies. Otherwise, implementations MUST determine
each edge's trust as follows:

1. If the universal level is `None`, the edge is `None`: universal withdrawal voids the
   edge in every scope
2. Otherwise, if a record is stored at `params.scope` (its level is not `Unknown`), that
   record applies, whether or not it has expired
3. Otherwise, the universal record applies

An expired scoped record therefore never falls back to universal trust: with
`enforceExpiry` set, the edge fails.

Denial does not use these fallback rules. `_edgeTrust` returns the effective denial
alongside the level and expiry, read from the same records. The reference
implementation packs the level, expiry, write time and denial flag of each record into
one storage slot, so the edge denial check needs no storage read beyond those the
fallback rules already make. The validator denial check reuses the same function for
the pair `(nodes[0], nodes[k])` and ignores its level and expiry.

```solidity
function _edgeTrust(bytes32 from, bytes32 to, bytes32 scope)
   internal view returns (TrustLevel level, uint64 expiry, bool denied)
{
   TrustRecord storage u = _trust[from][to][bytes32(0)];

   // Universal denial holds in every scope, so no scoped record can lift it
   if (scope == bytes32(0) || u.denied) return (u.level, u.expiry, u.denied);

   TrustRecord storage s = _trust[from][to][scope];

   // 1. Universal None voids the endorsement in every scope
   if (u.level == TrustLevel.None) return (TrustLevel.None, u.expiry, s.denied);

   // 2. Any stored scoped record is authoritative, expired or not
   if (s.level != TrustLevel.Unknown) return (s.level, s.expiry, s.denied);

   // 3. Otherwise universal applies
   return (u.level, u.expiry, s.denied);
}
```

`TrustRecord` and `_trust` are the reference implementation's storage. Implementations
MAY store records differently, provided `_edgeTrust` returns the same values.

#### `setIdentityGate`

Gates are stored under the key `(msg.sender, coordinationType)`. A caller can only
create, replace, or remove gates within its own namespace, so no cross-caller
authorisation check is required and two callers can never collide on the same
`coordinationType`.

`setIdentityGate` MUST revert if `params` violates the Validation Parameters
Constraints or the Gate Constraints, in the order given under Revert Order.

`setIdentityGate` MUST NOT require the caller to control `gatekeeperNode`. Naming a
gatekeeper only reads that agent's public attestations; it neither modifies them nor
makes any claim on the gatekeeper's behalf.

If valid:

* The gate MUST be stored at `(msg.sender, coordinationType)` and marked enabled
* `IdentityGateSet` MUST be emitted

#### `removeIdentityGate`

`removeIdentityGate` MUST revert with `GateNotFound` if no enabled gate exists at
`(msg.sender, coordinationType)`.

If valid:

* The gate MUST be disabled
* `IdentityGateRemoved` MUST be emitted

#### `validateParticipantWithPath`

This function gates [ERC-8001](./eip-8001.md) coordination participation for a participant
identified by ENS node.

The caller names the agent being gated. Implementations MUST bind the result to that
agent by requiring the path to terminate at `participantNode`; a path that merely
originates at the gatekeeper proves nothing about the participant.

```solidity
function validateParticipantWithPath(
   address coordinator,
   bytes32 coordinationType,
   bytes32 participantNode,
   TrustPath calldata path
) external view returns (bool isValid) {
   (bytes32 gatekeeperNode, ValidationParams memory params, bool enabled) =
               _getIdentityGate(coordinator, coordinationType);

   // No gate = misconfiguration, not open participation
   if (!enabled) revert GateNotFound(coordinationType);

   if (path.nodes.length < 2) return false;

   // Path MUST start at the gatekeeper...
   if (path.nodes[0] != gatekeeperNode) return false;

   // ...and MUST terminate at the participant being gated
   if (path.nodes[path.nodes.length - 1] != participantNode) return false;

   return _verifyPath(path, params, false);
}
```

`validateParticipantWithPath` MUST return `false` if:

* `path.nodes.length < 2`
* `path.nodes[0] != gatekeeperNode`
* `path.nodes[path.nodes.length - 1] != participantNode`
* `verifyPath(path, params)` returns `false`

It MUST revert with `GateNotFound` when no gate is enabled at
`(coordinator, coordinationType)`, before any other check. An unconfigured gate is a
misconfiguration, not open participation; see [Why Do Unconfigured Gates Revert?](#why-do-unconfigured-gates-revert).

#### `validateParticipantAddress`

This is the hook an [ERC-8001](./eip-8001.md) coordinator calls for each entry in an
intent's `participants` array. It differs from `validateParticipantWithPath` only in
how the participant is identified: by address rather than by node.

```solidity
function validateParticipantAddress(
   address coordinator,
   bytes32 coordinationType,
   address participant,
   TrustPath calldata path
) external view returns (bool isValid) {
   (bytes32 gatekeeperNode, ValidationParams memory params, bool enabled) =
               _getIdentityGate(coordinator, coordinationType);

   // No gate = misconfiguration, not open participation
   if (!enabled) revert GateNotFound(coordinationType);

   if (participant == address(0)) return false;
   if (path.nodes.length < 2) return false;
   if (path.nodes[0] != gatekeeperNode) return false;

   // The terminal node MUST be bound to the participant address
   if (resolveAgent(path.nodes[path.nodes.length - 1]) != participant) return false;

   // A name nobody controls cannot vouch for its addr record, which may be stale
   if (controllerOf(path.nodes[path.nodes.length - 1]) == address(0)) return false;

   return _verifyPath(path, params, false);
}
```

`validateParticipantAddress` MUST return `false` if:

* `participant == address(0)`
* `path.nodes.length < 2`
* `path.nodes[0] != gatekeeperNode`
* `resolveAgent(path.nodes[path.nodes.length - 1]) != participant`
* `controllerOf(path.nodes[path.nodes.length - 1]) == address(0)`
* `verifyPath(path, params)` returns `false`

It MUST revert with `GateNotFound` when no gate is enabled at
`(coordinator, coordinationType)`, before any other check.

Because an unresolvable node yields `address(0)`, the `participant == address(0)` check
also prevents a node with no `addr` record from matching a zero participant address.

The controller check fails closed: ENS does not clear an `addr` record when its name
loses its controller, so a wrapped name past its NameWrapper expiry, or an emancipated
subname past its expiry, still resolves although nobody can act for the name. The check
reads `controllerOf` only, not expiry or fuses, so it does not reject an expired
unwrapped name, a name in its grace period, or a migrated name whose legacy resolver is
kept, and a wrapped name passes again once a renewal through the NameWrapper restores its
holder (see [Wrapped Name Lifecycle](#wrapped-name-lifecycle)).
`validateParticipantWithPath` does not consult control.

A coordinator gating a full [ERC-8001](./eip-8001.md) intent calls this once per entry in
`participants`, supplying one pre-computed path per participant.

The result describes the registry's state when it is evaluated. A denial, withdrawal,
expiry or change of control affects later evaluations only, so a participant admitted
when it accepted an intent stays admitted unless the coordinator calls the hook again. A
coordinator whose execution relies on its participants still passing the gate SHOULD
evaluate the gate again in the transaction that executes, for example in
`executeCoordination`, with the paths supplied in its `executionData`.

That evaluation establishes registry-level eligibility only: the stored records, their
levels, expiries and denials, and any control the function reads, as they stand when it
runs. It cannot apply the continuity check under Wrapped Name Lifecycle, which reads
BaseRegistrar, NameWrapper and registry events that no transaction can see.
Continuity-checked authorization is registry-level eligibility together with that check
over every event up to the point of reliance. A coordinator that relies on the check
SHOULD perform it off-chain on the paths it will supply, and SHOULD NOT treat the
on-chain result as covering it. A check run to block B covers events up to and including
block B. A registration of a name on the path after block B, including one in the
executing block ordered before the executing transaction, ends attestations the path
uses, yet the on-chain evaluation still accepts them. Checking close to execution narrows
this window but does not close it.

For a `.eth` second-level name on its paths, a coordinator can close the window with the
expiry E that the BaseRegistrar's `nameExpires` returns for the name at block B. In the
executing transaction it requires either that `block.timestamp` is no later than E plus
the BaseRegistrar's `GRACE_PERIOD`, or that `nameExpires` still returns E. The
BaseRegistrar accepts a registration only once the current expiry plus the grace period
has passed, and sets a later expiry, and no operation lowers the expiry, so either
condition shows that no registration has occurred since block B. A renewal in the window
changes the expiry but not the deadline. E is the value read at block B: an expiry read
in the executing transaction already reflects any registration that preceded it. This
standard defines no comparable check for a name below a second-level name being wrapped
again, and for such names the window remains.

The liveness check under Wrapped Name Lifecycle reads state, so a coordinator can repeat
it in the executing transaction, which the on-chain evaluation does not do:
`validateParticipantAddress` requires a controller for the terminal node only, and
`validateParticipantWithPath` reads none. A wrapped trustor on the path, such as an
emancipated subname passing its NameWrapper expiry, can lose its controller after the
check. A coordinator that relies on the liveness check can read the NameWrapper's
`ownerOf` for each wrapped trustor on the path in the executing transaction, and not
execute while any of them returns the zero address.

## Rationale

### Why ENS Instead of a New Identity System?

ENS is finalised ([ERC-137](./eip-137.md)), widely deployed, and already provides what
this standard needs: identifiers that survive key rotation, ownership semantics through
`owner()` and `isApprovedForAll()`, human-readable names, and subdomain delegation for
protocol-issued agent identities. A new identity system would fragment the ecosystem and
add a dependency on draft standards.

Agent registries that represent each agent as an [ERC-721](./eip-721.md) token can be
consumed through an adapter. For example, a protocol can issue an ENS subname per agent
token, keep the subname's controller in step with the token's holder, and point its `addr`
record at the agent. Keeping that dependency in an adapter means `requires` lists only
finalised standards.

### Why Scope as Storage Key?

A trustor may trust the same trustee differently in different contexts, for example fully
for DeFi coordination and marginally for gaming. Making scope part of the storage key
`(trustorNode, trusteeNode, scope)` expresses this directly, with universal trust
`bytes32(0)` as the fallback where no scoped record exists.

### Divergence from OpenPGP

OpenPGP keeps two quantities apart: validity, computed from certifications, says whether
a key belongs to its claimed holder; owner trust, assigned privately, says how far a user
relies on a key holder's certifications. This standard keeps one quantity, the level on
an edge. Where the trustee is an intermediary, the level acts as owner trust; where it is
the target, it acts as validity. The binding between a name and its controller comes from
ENS ownership rather than from attestations.

`verifyPath` also performs no marginal accumulation. OpenPGP accepts a key with one fully
trusted certification or several marginally trusted ones. Here one path is checked and
every edge must reach `minEdgeTrust`, so verification has a single verdict per path at
O(path length) cost, and needs no threshold parameters. An application that wants
accumulation can verify several paths and combine the verdicts under its own rule.

### Why Four Trust Levels?

The four levels follow OpenPGP. `minEdgeTrust` lets an application accept `Marginal`
edges or require `Full` ones.

Denial is a flag beside the level, not a fifth level. A level says how far the trustor
vouches for an agent; denial says whether the trustor will rely on the agent at all. A
trustor needs to deny without losing the endorsement it would restore afterwards, and to
withdraw without denying, which a single ordered enum cannot express. A fifth value would
also break the ordering that `minEdgeTrust` comparisons rely on.

### Why Separate Signing Authority from Transaction Submission?

ENS operator approvals exist so operators can manage names. Letting them sign
attestations would break the binding between an attestation and the name's controller.
Signing therefore stays with the controller (or its [ERC-1271](./eip-1271.md) contract),
while anyone may relay a signed attestation and approved operators may withdraw.

### Why verifyPath Only (No On-Chain Search)?

On-chain graph traversal has unpredictable gas cost, and attackers can inflate adjacency
lists. Requiring pre-computed paths keeps verification O(path length) and leaves search to
off-chain indexers. This standard defines no on-chain search, enumeration or aggregation.
A later extension could, but to be interoperable it would have to state how each function
applies scope fallback, expiry, withdrawal, edge denial and validator denial, as
`verifyPath` does.

### Why Required Anchors?

Sybil attacks are the main threat to a web of trust. Required anchors force paths through
established nodes such as DAOs, protocols or auditors, which turns Sybil resistance from
application advice into an enforced gate parameter.

### Why Are Gates Keyed by Caller Address?

An [ERC-8001](./eip-8001.md) `coordinationType` is a proposer-chosen identifier with no
namespace, so unrelated applications will choose the same value. Keying gates by
`coordinationType` alone would let the first registrant squat it for everyone. Keying by
`(msg.sender, coordinationType)` gives each caller a namespace it owns, needs no ENS name,
and keeps published coordination types safe to use. Keying by the gatekeeper's node was
rejected because it conflates the party that sets a policy with the party whose trust
graph the policy reads.

### Why Do Unconfigured Gates Revert?

The integrator supplies both halves of the gate key, so a mistyped coordination type or a
wrong coordinator address finds no gate. An open default would admit every participant
while looking like a working gate. Returning `false` would fail closed but blame the
participant. Reverting with `GateNotFound` names the real problem at the first call.
Coordinators that want open participation simply do not call the hook for those types,
and can read `getIdentityGate(...).enabled` first if they need to branch.

### Why Forward Resolution Instead of a Binding Registry?

The `addr` record is already the controller's statement of which address a name denotes,
so reusing it needs no registration step and no second source of truth. Reverse records
were rejected: they are self-asserted, and verifying one on-chain requires a forward
lookup plus string handling over untrusted input.

The trade-off is that resolution follows the `addr` record, not the controller. A
controller can repoint the record, and ENS does not clear it on expiry or re-registration,
so it can keep naming a previous holder's address. Requiring the terminal node to have a
controller removes only the case of a wrapped name nobody controls. See
[Resolver Trust](#resolver-trust) and [Expired Unwrapped Names](#expired-unwrapped-names).

### Why Does Resolution Cap Gas and Never Revert?

Participants choose their own resolvers, and a coordinator typically validates every
participant in one call. If resolution could revert or consume most of the remaining gas,
one participant could abort validation for all of them. Capping the forwarded gas and
treating every malformed answer as "no address" fails closed for that participant only.
The 50,000 cap is well above what deployed resolvers need (under 20,000 gas on every
resolver sampled at mainnet block 26,173,410, with state cold), and is left to
implementations because gas repricing could change those figures.

[ERC-1271](./eip-1271.md) checks are not capped. They run only when an attestation is
submitted, and a batch carries one trustor, so an expensive controller only wastes gas for
whoever submits its own attestations. Validation never verifies signatures.

### Why a Single Per-Trustor Nonce?

A single monotonic nonce per trustor serialises its attestations: a signature is stranded
if a higher-nonced one lands first. The alternatives were rejected:

* **Unordered nonce bitmap.** There is no floor to raise, so a trustor responding to a
  compromise would have to burn every outstanding nonce individually, which requires
  knowing them.
* **Ordered nonces per `(trustor, trustee, scope)`.** Invalidation works only one record at
  a time, and signers track one counter per relationship.
* **Global floor plus per-trustee floor.** This allows quarantining one counterparty, but
  adds a storage read to `setTrust`, a second nonce dimension for every signer, and a
  larger interface, and does not help when the trustor's own key is compromised. The case
  it improves, outstanding signatures for both the quarantined counterparty and others
  the trustor wants to keep, is narrow, and its cost is re-signing the attestations
  still in flight.

Attestations are infrequent and correct revocation matters more than issuance throughput.
Agents that need throughput can batch with `setTrustBatch`, which consumes a contiguous
nonce range.

### Why Attestations Grant and Revocations Withdraw?

Restricting attestations to `Marginal` and `Full`, and routing every withdrawal through
revocation, gives each level one path, one event and one authorisation rule. Because
revocation requires no prior trust, a trustor can withdraw preemptively in a scope it
never granted, which blocks the universal fallback there.

### Why Explicit Nonce Invalidation?

Revocation cannot undo an attestation that is signed but not yet submitted. The only
ordering between "signed" and "revoked" is the nonce, and only the trustor knows the
highest nonce it has issued, so advancing the nonce by a fixed step during `revokeTrust`
would not reliably invalidate anything. `invalidateNonces` is therefore a separate
operation, and quarantining a counterparty takes a denial and an invalidation.

### Why Is `invalidateNonces` Controller-Only?

A withdrawal affects one pair and the scopes named, so delegating it lets an operations
key handle routine incident response. Raising the nonce floor is not bounded: it
permanently voids every outstanding attestation of the trustor. ENS `isApprovedForAll` is
a coarse approval often granted to marketplaces and management tools, and reading it as
authority to void an agent's attestations would give them a power their grantor never
intended.

### Why Is Universal Withdrawal Authoritative?

A trustor that withdraws at universal scope means it everywhere. If universal `None`
applied only where no scoped record existed, every earlier scoped grant, and every scoped
attestation signed earlier but submitted later, would keep the edge alive. Making it
override every scope for the pair gives the trustor one call that holds everywhere. The
override is confined to that trustor and trustee, and costs one extra storage read per
edge when verifying in a named scope.

The override lasts only while the universal record is `None`. A later universal
attestation replaces it, and every positive scoped record for the pair applies again,
including scoped grants made long before the withdrawal. A trustor re-endorsing at
universal scope SHOULD first review, or withdraw, the scoped grants it does not want to
return.

The rule is applied during verification, so `getTrust` stays literal. An expired scoped
record does not fall back to universal trust, since that would let a lapsed narrow grant
widen silently.

### Why Separate Withdrawal from Denial?

A trustor that stops vouching for an agent may mean that it no longer endorses the agent,
or that it refuses to rely on the agent at all. Expressing both with `None` leaves no
neutral withdrawal, and lets an approved operator, who may withdraw, decide whose
judgement the trustor accepts. `None` therefore withdraws one edge and stays delegable,
while denial is a separate flag that only the controller writes.

### Why Does a Validator's Denial Override Indirect Paths?

Suppose Alice trusts Bob, Bob trusts Carol, and Alice has denied Carol. Checking only
edges, `[Alice, Bob, Carol]` would verify, and Bob's endorsement would override Alice's
refusal inside Alice's own trust decision. The validator check prevents that, for
intermediaries as well as the target, since a path relies on each intermediary's
judgement.

Only the validator's denial counts. Checking every pair of nodes would cost O(n²) reads
and let any agent placed on a path veto it by denying a node it was never asked to vouch
for.

The edge check reads no extra storage slot, since the flag shares a slot with the level
and expiry. The validator check adds one lookup per node from index 2: in the reference
implementation, about 6,000 gas per node in a named scope and 3,000 at universal scope,
with storage cold.

### Why Does Clearing a Denial Check the Trustor's Nonce?

An attestation can land while a denial is in force and is revealed when the denial is
cleared. Without a check, a relayer could front-run a reviewed clear with another valid
attestation, which the clear would then activate unreviewed. Checking the trustor's nonce
covers every scope with one storage read, since every stored attestation raises it. The
cost is false positives, which fail closed.

The check does not stop an attestation signed before the review and submitted after the
clear. Only raising the nonce floor first closes that case, which is why `clearDenial`
directs callers to read the nonce after `invalidateNonces`. Folding the floor into
`clearDenial` would void the trustor's outstanding attestations for every other trustee.

Denying takes no nonce: it is the emergency operation and must not fail because an
attestation landed first. The guard is a separate function rather than an optional
argument, so that the unguarded call is not the easier one.

### Why Is Denial Controller-Only?

Denial changes which agents' endorsements the trustor accepts, and clearing it readmits
an agent the controller excluded. Both carry the authority of the trustor's judgement, so
both stay with the controller. A controller that needs to delegate can use a contract
controller.

### Why Batch Revocation Instead of Revoke-All?

Universal revocation already voids an edge in every scope. `revokeTrustBatch` covers
withdrawing in several named scopes while keeping trust elsewhere. A revoke-all would have
to enumerate scopes on-chain or shadow records with an epoch that `getTrust` would not
report literally. The trustor's client derives its scope list from its own `TrustSet` logs.

### Why Unwrap NameWrapper Names?

For a wrapped name `ens.owner(node)` returns the NameWrapper, which does not implement
[ERC-1271](./eip-1271.md), so using it as the signing authority would leave every wrapped
name unable to attest. Unwrapping through `ownerOf` recovers the actual controller and
inherits the NameWrapper's expiry behaviour (see
[Wrapped Name Lifecycle](#wrapped-name-lifecycle)).

### Why Does Authority Follow Ownership Rather Than Management Permission?

During a `.eth` name's grace period the NameWrapper reports the holder but refuses
management operations. Requiring `canModifyName` as well would remove the name's
authority for those 90 days, although the name has not changed hands and no one else can
register it. It would also remove the emergency controls (withdrawal, denial and nonce
invalidation) when they may be needed, would cover only part of the risk since unwrapped
names keep their registry owner after expiry, and would add a dependency on another
NameWrapper function.

Endorsements made during the grace period pass to the next registrant if the name is not
renewed, as an endorsement survives an ordinary transfer. The Specification bounds them
with recommendations to trustors and coordinators under
[Wrapped Name Lifecycle](#wrapped-name-lifecycle) and
[Identity Continuity](#identity-continuity-1), without changing on-chain acceptance.

Binding each record to the registration that issued it would let the registry reject
records from an earlier registration. ENSv1 state does not support that: a renewal and a
later registration both leave a later registrar expiry, and telling them apart needs the
BaseRegistrar's events. It would also change the storage layout and the interface, and
would work only for `.eth` second-level names. This standard leaves it to an ENSv2-native
successor.

### Why Pin the NameWrapper?

The `nameWrapper` slot decides who controls every wrapped name. Whoever could change it
could point it at a contract whose `ownerOf` returns an address of their choosing, and
then act for every wrapped name in the registry. Pinning it at deployment removes that
path. A governance-updatable slot would only move it to whoever holds the update right.

The cost falls on names that move to a successor wrapper. The registry treats a successor
as a raw controller that cannot sign, so supporting one means deploying a new registry.
Trust state does not carry over, because `verifyingContract` is part of the
[EIP-712](./eip-712.md) domain, and trustors re-attest against the new domain, which their
clients can derive from their own `TrustSet` logs.

## Backwards Compatibility

This ERC introduces new functionality and does not modify existing standards.

**ENS Compatibility**: Uses standard ENS interfaces only — `owner`, `resolver`, and `isApprovedForAll` on the registry, `addr` on the resolver ([ERC-137](./eip-137.md)), and `ownerOf`/`isApprovedForAll` on the NameWrapper. Works with any deployment that exposes these ENSv1 interfaces, and with deployments that have no NameWrapper. Both wrapped and unwrapped names are supported. ENSv2 is covered under ENSv2 Compatibility and Migration.

On-chain validation does not rely on CCIP-Read. Agents whose names are served by an off-chain resolver can still hold and issue trust, but cannot be validated by address, since `addr` is not readable on-chain for those names.

**ERC-8001 Compatibility**: Designed as a module. [ERC-8001](./eip-8001.md) coordinators can optionally integrate identity gates, calling `validateParticipantAddress` once per entry in an intent's `participants` array. Coordinators call the hook only for coordination types they have gated; for any other type it reverts with `GateNotFound`. No change to [ERC-8001](./eip-8001.md) is required, and coordinators that ignore this standard are unaffected.

**Wallet Compatibility**: Uses [EIP-712](./eip-712.md) signatures, compatible with all major wallets. Supports [ERC-1271](./eip-1271.md) for contract wallets and smart accounts.

### Deployments of Earlier Drafts

Registries built from earlier drafts of this ERC are not compatible with this revision.
Some report the same `ITrustRegistry` identifier and [EIP-712](./eip-712.md) domain
version as this revision while behaving differently, and both are self-reported in any
case. A consumer that depends on this revision's behaviour identifies the registry by its
deployment address and verified source, and, for a registry behind an upgradeable proxy,
by its current implementation and the holder of its upgrade authority. Signatures are
bound to the registry's [EIP-712](./eip-712.md) domain, so moving to a new registry
requires fresh attestations.

### ENSv2 Compatibility and Migration

This ERC specifies trust authority and address resolution using ENSv1 registry
interfaces and a NameWrapper address pinned at deployment. It does not specify native
ENSv2 controller resolution, role-based signing authority, or address resolution.

The descriptions of ENSv2 contracts in this section are informative, not normative. They
record the published ENSv2 migration process as deployed on Sepolia, checked against
that deployment at block 11,906,480 (13 October 2026). ENSv2 is not deployed on Ethereum
mainnet. Its mainnet contracts, migration process and timing may differ, and nothing in
this section describes how they will behave. The controller-resolution rules of this
standard do not depend on it: `controllerOf` returns whatever the ENSv1 registry and the
pinned NameWrapper report, whichever contract that is. The recommendations below apply
wherever names migrate in the way described.

Under that process, a migrated name's ENSv1 token is
transferred to the ENSv2 Graveyard contract. An unwrapped or unlocked wrapped name is
unwrapped to the Graveyard, and a locked name stays wrapped with the Graveyard as its
holder. Either way, `controllerOf` returns the Graveyard after migration. The Graveyard
does not implement [ERC-1271](./eip-1271.md), so neither the name's new ENSv2 owner, nor
its former controller, nor any approved operator can manage trust for that name through
this ERC. Migration clears the ENSv1 resolver, except for a locked name with
`CANNOT_SET_RESOLVER` burned, which keeps its legacy resolver. An approved operator can
migrate a name and choose the new ENSv2 owner.

Migration does not remove existing trust relationships from the Trust Registry. The
required path verification algorithm evaluates stored relationships and does not
require each path node to retain an active ENSv1 controller. Previously established
trust paths can therefore remain valid after a name migrates, subject to their trust
levels, expiry and gate constraints. Address-based validation still fails where the
terminal node's resolver was cleared.

A migrated name can no longer withdraw endorsements it has issued, set denials, or clear
them. Migration freezes both its outgoing endorsements and its denials: they stay in
storage and keep applying, and the former controller loses the authority to change
them. Outgoing endorsements persist until they expire, and those with `expiry == 0`
persist indefinitely. A migrated gatekeeper therefore continues to admit participants
through stored paths, cannot exclude further agents, and cannot readmit agents it has
denied. Before migrating, agents SHOULD withdraw endorsements they may later need to
withdraw, set or clear denials so that the frozen state is the one they intend, and
gatekeepers SHOULD reconfigure dependent gates. Conversely, attestations a migrated name
signed but never submitted can no longer be submitted, because its signatures no longer
verify.

Subnames of a migrated parent keep their controller and resolver until any party calls
the Graveyard's permissionless `clear` function. `clear` then hands unwrapped subnames
and unemancipated wrapped subnames to the Graveyard and clears their resolvers, which
freezes their trust state as described above. It reverts for an emancipated subname that
has not expired. Protocols that issue agent subnames SHOULD NOT migrate the parent name
while those subnames are in use with this standard.

On that deployment, `clear` also applies to `.eth` second-level names that were never
migrated. Once such a name is past its grace period, `clear` re-registers it in ENSv1 to
the Graveyard and clears its resolver. From then on `controllerOf` returns the
Graveyard, which ends the lapsed holder's authority over an expired unwrapped name (see
Expired Unwrapped Names) and freezes the name's trust state. `clear` reverts for a name
that is active or in its grace period. On that deployment ENSv1 registration is also
closed: at the block above, the BaseRegistrar's only controllers are the Graveyard and a
renewal controller with no registration function, so a name that lapses in ENSv1 cannot
be re-registered there by a new owner. Whether and when ENSv1 registration closes on
mainnet is not established. A new owner in ENSv2 gains no authority under this standard.

Coordinators SHOULD monitor migration of gatekeeper, anchor and participant names, and
re-evaluate the affected gates. Applications using address-based validation SHOULD
account for the loss or retention of legacy resolver records. For high-assurance
coordination, time-limited attestations and explicit gate reconfiguration are
RECOMMENDED.

New names registered only through ENSv2 are not directly supported by this ERC's ENSv1
interfaces. Supporting ENSv2 requires a separate integration that defines its
controller, signing and resolution semantics. A successor Trust Registry may provide
such support without changing this ERC's interface. Trust state does not migrate
automatically between registries. Existing signatures are bound to their original
verifying contract through [EIP-712](./eip-712.md), so establishing trust in a successor
registry requires fresh attestations. This is the successor-registry pattern described
for a successor wrapper under "Why Pin the NameWrapper?".

## Security Considerations

### Sybil Attacks and Graph Manipulation

An attacker can create many ENS names, establish mutual trust between them, and try to
place them on many trust paths.

#### Mitigations

* Require anchors (`requiredAnchors`), so paths traverse established community nodes
* Keep `maxPathLength` short and require `minEdgeTrust: Full` for high-value coordination
* In application logic, weight trust by name age or registration cost, add stake
  requirements, or require several independent paths, each checked with `verifyPath`
* Monitor trust graphs off-chain for anomalous patterns

### Key Compromise

When a **counterparty** is compromised, the trustor's own controller is sound: it denies
the counterparty at universal scope and follows the quarantine procedure under
`invalidateNonces`. A universal denial voids the trustor's edges to the node in every
scope and excludes it from every path the trustor evaluates as validator, including
paths through agents that still vouch for it; a gate whose gatekeeper has denied the node
rejects it in every evaluation after the denial. Withdrawal, even at universal scope with
the `COMPROMISED` reason code, removes only the withdrawing agent's own edge. Denial
applies to the node, not to the address it resolves to (see
[Address Aliases](#address-aliases)).

When the **trustor's own controller** is compromised, denial is not sufficient: the
attacker holds the same controller and nonce space, so it can clear denials, withdraw
endorsements and sign new attestations, and the trustor cannot undo attestations the
attacker has already signed. Rotating the controller stops new attestations but retracts
nothing. The complete remedy is denial by counterparties, which the attacker cannot clear
because each denial is stored under the counterparty's own name. An attacker holding the
controller may also move the name, so trusted, gatekeeper and anchor names need their
control monitored (see [Monitoring Control Changes](#monitoring-control-changes)).

Neither an attestation nor an `invalidateNonces` call can raise the nonce floor by more
than 2^32. Without that bound, one call or one attestation with nonce `type(uint64).max`
would stop the name from ever attesting again, and since the nonce belongs to the name,
the lockout would pass to every future controller.

### Pre-Signed Attestations

An attestation carries no signing timestamp and is submittable by anyone holding the
signature until the trustor's nonce passes it, so revoking trust does not retract
signatures issued earlier. If Alice signs an attestation for `bob.eth` at nonce 10, then
revokes trust in `bob.eth`, anyone holding the nonce-10 signature can restore it.

#### Mitigations

* Issue nonces sequentially, so the highest outstanding nonce is always known
* To quarantine a counterparty, deny it at universal scope and call `invalidateNonces`
  above every nonce ever signed. Both calls require the name controller
* Before clearing a denial, raise the nonce floor, then read the nonce passed to
  `clearDenial`. The nonce check catches an attestation that lands first; the floor
  stops one signed earlier from landing after the clear
* Prefer short `expiry` values, which bound how long a stray signature stays usable

`invalidateNonces` is trustor-wide: it voids the trustor's outstanding attestations for
every trustee and scope. It does not affect relationships already stored.

### ENS Name Transfer

When control of a name changes, the new controller inherits every attestation naming it
as trustee, gains authority over every attestation and denial in which it is the trustor,
and takes over any gatekeeper or anchor role the name has. Attestations the old
controller stored stay in force until they expire or are withdrawn. Attestations it
signed but did not submit fail after the transfer, and become submittable again if
control returns to the signer while their nonces are unused.

#### Mitigations

* Use short expiries for high-stakes trust
* Monitor control changes, and re-evaluate trust and the gates that name the node after
  any change

### Gatekeeper and Anchor Names

A gate stores its gatekeeper and anchors as namehashes, so a change of control moves the
role to the new controller and nothing in the gate records it.

A new controller of `gatekeeperNode` can attest directly from it. Where the gate requires
no anchor, one qualifying attestation admits any agent it chooses. A gate with a
non-empty `requiredAnchors` rejects direct paths, so the new controller can admit an
agent only through a path that traverses an anchor and meets every other parameter. In
either case it can deny agents, or clear denials a previous controller set.

A new controller of an anchor inherits every attestation naming the anchor as trustee,
and can attest from it to any agent. Time-limited inbound attestations bound how long
the anchor stays reachable, but attestations with `expiry == 0` do not.

#### Mitigations

* Monitor control of every gatekeeper and anchor node, and reconfigure the affected
  gates when it changes
* Use a non-empty `requiredAnchors` where a change of gatekeeper control would be costly
* Give attestations leading to anchors an expiry
* Consider locking gatekeeper and anchor names with fuses, weighing the cost described
  under [Name Locking with Fuses](#name-locking-with-fuses)

### Monitoring Control Changes

No single event reports every change of control. Depending on how a name is held, a
change appears as:

* A registry `NewOwner` event from `setSubnodeOwner`, used by registration, reclaiming a
  `.eth` name and a parent reassigning a subname
* A registry `Transfer` event from `setOwner`
* For unwrapped `.eth` second-level names, a BaseRegistrar [ERC-721](./eip-721.md)
  transfer. The registry owner does not change until the new registrant reclaims the name
* For wrapped names, a NameWrapper [ERC-1155](./eip-1155.md) `TransferSingle` or
  `TransferBatch` event

A wrapped name also loses control, with no event, when its NameWrapper expiry passes,
which after a renewal that bypassed the NameWrapper happens while the name is still
registered. Control returns to the same holder, again with no NameWrapper event, when a
renewal through the NameWrapper sets the expiry again (see
[Wrapped Name Lifecycle](#wrapped-name-lifecycle)).

After any relevant event, monitors are RECOMMENDED to re-check the name's effective
controller (`controllerOf`), its fuses and its expiry (for a wrapped name, its
NameWrapper expiry from `getData` as well as its registrar expiry), rather than relying
on any single event stream. Expiry emits no event at all, so a wrapped name also needs
re-checking when its NameWrapper expiry passes.

### Resolver Trust

Address resolution reads the node's `addr` record, which the controller can change at any
time, so a trusted name can be repointed and gates keyed on it will admit the new address
without any attestation changing. A resolver is chosen by the controller, so trusting a
node means trusting its resolver.

The record can also be stale. ENS does not clear it when a name expires or changes hands,
so after a re-registration it keeps naming the previous holder's address until the new
registrant changes it, and `validateParticipantAddress` keeps admitting that address. A
wrapped name past its NameWrapper expiry also keeps its record, but
`validateParticipantAddress` rejects it because it has no controller. Monitoring
`AddrChanged` catches neither case. A registration that sets the `addr` record in the
same transaction leaves no stale window.

A resolver that reverts, returns malformed data or consumes gas fails closed for its own
node and costs the caller at most the gas cap (see
[Agent Address Resolution](#agent-address-resolution)). Callers that validate many
participants in one call SHOULD budget for that cap on each participant. A controller
contract can likewise consume all gas forwarded to `isValidSignature`. This only affects
the party that submits that controller's attestations, which SHOULD simulate a submission
before relaying it.

#### Mitigations

* Use short expiries, so trust is re-attested after a repoint
* Monitor `AddrChanged` and control changes on nodes that appear in trust paths, and
  treat a node's `addr` record as unconfirmed after a change of control until the new
  controller has set it

### Address Aliases

Denial excludes a name, not the address it resolves to. If `agent.eth` and `backup.eth`
both resolve to `X` and both have eligible paths from a gatekeeper, `X` still passes
`validateParticipantAddress` through `backup.eth` after the gatekeeper denies
`agent.eth`. The gatekeeper does not choose which names resolve to `X`: the controller
of any name with an eligible path can point it there.

#### Mitigations

* When quarantining an agent, deny every name known to resolve to its address. This does
  not cover a name pointed at the address later
* To exclude an address, apply an address-level policy alongside the gate, such as a
  denylist checked before `validateParticipantAddress`
* Identify participants by node, through `validateParticipantWithPath`, where denial of
  the name is what matters

### Expired Unwrapped Names

When an unwrapped `.eth` second-level name expires, `ens.owner(node)` keeps returning the
lapsed holder until the name is re-registered or, where the ENSv2 Graveyard is deployed,
cleared. Until then the lapsed holder keeps every authority this standard grants, and
after the grace period can still repoint the `addr` record. The registry cannot detect
this, because `.eth` expiry is recorded against the labelhash, which cannot be derived
from the namehash. On re-registration the new registrant inherits the name's trust at
once, as on a transfer but with no action by the previous holder, and the previous
holder's `addr` record stays in place until changed (see [Resolver Trust](#resolver-trust)).

#### Mitigations

* Use wrapped `.eth` second-level names or emancipated subnames, which lose authority
  once their NameWrapper expiry passes
* Use short attestation expiries
* Monitor the expiry of trusted unwrapped names off-chain, and withdraw or deny names
  that lapse

### Parent-Controlled Subnames

An unwrapped parent, or a wrapped parent whose subname does not have
`PARENT_CANNOT_CONTROL` burned, can reassign the subname at any time, and whoever
registers the parent next can do the same. The new controller inherits the subname's
trust, and any gatekeeper or anchor role it has, without the holder's consent. A
reassignment emits a registry `NewOwner` event. `PARENT_CANNOT_CONTROL` protects an
emancipated subname only until its NameWrapper expiry, after which the parent can create
it again for another holder. The continuity check under
[Wrapped Name Lifecycle](#wrapped-name-lifecycle) bounds both cases for coordinators
that apply it.

Trustors SHOULD treat such a subname as no more trustworthy than its parent, and SHOULD
prefer subnames with `PARENT_CANNOT_CONTROL` burned. This standard does not inspect
fuses, so trustors and gatekeepers check them off-chain.

### Name Locking with Fuses

`PARENT_CANNOT_CONTROL`, `CANNOT_UNWRAP` and `CANNOT_TRANSFER` together stop a wrapped
name being reassigned by its parent or transferred by its holder. `CANNOT_UNWRAP` must be
burned before any other owner-controlled fuse, and wrapped `.eth` second-level names have
`PARENT_CANNOT_CONTROL` burned when wrapped. Every fuse resets when the NameWrapper expiry
passes, so expiry still needs monitoring.

Locking is a long-term commitment. Under ENS's published migration process, as deployed
on Sepolia, names with `CANNOT_TRANSFER` burned cannot migrate to ENSv2 (see
[ENSv2 Compatibility and Migration](#ensv2-compatibility-and-migration)). This standard
neither inspects nor requires fuses.

### ENSv2 Migration

A name that migrates to ENSv2 can no longer act through this ERC, while the relationships
and denials it recorded stay in force; see
[ENSv2 Compatibility and Migration](#ensv2-compatibility-and-migration).

### Replay Protection

The [EIP-712](./eip-712.md) domain prevents cross-contract and cross-chain replay, and
monotonic nonces prevent replay within the registry. Nonces do not stop an attestation
being applied late; see [Pre-Signed Attestations](#pre-signed-attestations).

### Stale Trust

Relationships become stale when agents do not update them. Validate with
`enforceExpiry: true`, set reasonable `expiry` values (90 days maximum for high-stakes
scopes), and monitor `TrustSet` events off-chain.

### Off-Chain Path Computation

Off-chain indexers compute paths, and a malicious one can omit valid paths or return
suboptimal ones. Invalid paths are always rejected by `verifyPath`, and users can run
their own indexers or use several. An indexer that follows only trusted edges also
returns paths over denied edges and through nodes the validator has denied, so indexers
follow `DenialSet` as well as `TrustSet` and `TrustRevoked`. Indexers SHOULD apply every
rule of the path verification algorithm during search, evaluated from the validator's
perspective, so that the paths they return verify.
