## Abstract

This ERC defines an [EIP-712](./eip-712.md) format for a service provider to sign payment terms for a specific priced request.

A quote authenticates the issuer, optional payer, recipient, payment asset, exact amount, request commitment, quote identifier, validity window, and settlement chain. The request commitment is derived according to a separately identified request scheme, allowing the same quote format to be carried by HTTP payment protocols, agent protocols, wallet APIs, or other transports.

The quote does not authorize payer funds, execute settlement, establish provider identity, or prove service delivery.

## Motivation

Machine-to-machine and agentic payment flows commonly separate two decisions:

1. a provider states the terms under which it will perform a service; and
2. a payer authorizes a payment that satisfies those terms.

Existing payment authorizations authenticate the second decision. They do not necessarily provide a transport-independent EVM object proving which terms the provider asserted for the concrete service request before the payer authorized payment.

Protocol-specific signed-offer mechanisms, including the x402 Offer and Receipt extension, are prior art for provider-authenticated payment terms. This ERC standardizes a smaller EVM interoperability primitive that can be carried by x402 or by other transports without depending on a particular x402 version or field layout. Its distinguishing properties are:

- an EIP-712 provider signature;
- an explicit commitment to the priced request;
- optional binding to a known payer;
- EVM settlement-chain and asset semantics; and
- verification by both externally owned accounts (EOAs) and [ERC-1271](./eip-1271.md) contract accounts.

Request serialization is intentionally not standardized by this ERC. HTTP, Model Context Protocol (MCP), Agent2Agent (A2A), JSON-RPC, x402, or another protocol can define a request scheme appropriate to that protocol while reusing the same signed quote object.

This separation keeps the ERC focused on the EVM commercial artifact rather than defining another HTTP or agent-protocol canonicalization standard.

## Specification

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Definitions

- **Issuer**: The service-provider account whose signature authenticates a quote.
- **Expected issuer**: The issuer account that a verifier has independently associated with the service through an authenticated endpoint, registry, configuration, allowlist, or another trust mechanism.
- **Payer**: The account whose assets fund the quoted commercial payment.
- **Recipient**: The immediate account or contract designated to receive the quoted commercial payment.
- **Bearer quote**: A quote whose `payer` is the zero address. The surrounding application selects the payer when settlement is authorized.
- **Request scheme**: A named and versioned rule that defines the canonical bytes of the priced service request.
- **Request hash**: The Keccak-256 commitment to the canonical request bytes defined by the request scheme.
- **Quote ID**: An issuer-scoped identifier for one concrete signed quote.
- **Verification time**: The time at which quote validity is checked. An on-chain verifier uses `block.timestamp`; an off-chain verifier uses a trusted local Unix clock.
- **Submission time**: The time at which a settlement transaction or authorization is submitted to the selected settlement mechanism.

### Quote structure

A conforming quote MUST contain the following fields in the stated order and with the stated types:

```solidity
struct ServicePaymentQuote {
    address issuer;
    address payer;
    address recipient;
    address asset;
    uint256 amount;
    string requestScheme;
    bytes32 requestHash;
    bytes32 quoteId;
    uint64 validAfter;
    uint64 validUntil;
}
```

The fields have the following meanings:

| Field           | Meaning                                                                              |
| --------------- | ------------------------------------------------------------------------------------ |
| `issuer`        | Account whose signature authenticates the quote.                                     |
| `payer`         | Account permitted to fund the payment, or the zero address for a bearer quote.       |
| `recipient`     | Immediate recipient of the commercial payment.                                       |
| `asset`         | Payment token contract, or the zero address for the settlement chain's native asset. |
| `amount`        | Exact nominal payment amount in the asset's smallest unit.                           |
| `requestScheme` | Identifier of the canonical request-binding rules.                                   |
| `requestHash`   | Keccak-256 commitment to the canonical priced request.                               |
| `quoteId`       | Issuer-scoped identifier for this concrete quote.                                    |
| `validAfter`    | Unix timestamp before which the quote is not valid.                                  |
| `validUntil`    | Unix timestamp after which new settlement submission is not permitted.               |

`issuer`, `recipient`, `amount`, and `quoteId` MUST be non-zero.

`validAfter` MUST be less than or equal to `validUntil`.

The zero address in `payer` designates a bearer quote.

The zero address in `asset` designates the native asset of the settlement chain.

The quote defines an exact nominal commercial payment. Gas, relayer fees, facilitator fees, protocol fees, conversion fees, and other additional charges are outside `amount` and MUST be separately disclosed and authorized.

### Request binding

`requestScheme` MUST identify a deterministic and versioned algorithm for deriving canonical request bytes from the service invocation being priced.

`requestScheme` MUST contain between 1 and 128 bytes when UTF-8 encoded and MUST consist only of visible ASCII bytes `0x21` through `0x7E`.

A request scheme specification MUST define:

1. the service or operation identity included in the canonical request;
2. the request fields included in the canonical request;
3. the exact canonical serialization;
4. how equivalent and non-equivalent requests are distinguished; and
5. any transport metadata that can change the meaning or price of the request.

A request scheme MUST bind enough context to distinguish two operations that could interpret the same payload differently.

The request hash MUST be:

```text
requestHash = keccak256(canonicalRequestBytes)
```

This ERC does not define any built-in request scheme.

Applications MAY define request schemes in separate ERCs, protocol specifications, or application specifications. Globally published schemes SHOULD use an identifier that avoids collisions, such as an absolute URI or a reverse-DNS-based name.

Two implementations have request-binding interoperability only when they support at least one common `requestScheme`. A transport binding claiming request-bound interoperability MUST select a request scheme understood by both issuer and verifier.

A verifier MUST NOT claim that a quote is bound to a request unless it supports the signed `requestScheme`, independently derives the canonical request bytes for the invocation being priced, recomputes `requestHash`, and obtains the signed value.

A component that verifies only the quote signature and payment fields MAY describe the quote as signature-valid, but MUST NOT describe the request binding as verified.

### Quote identifier

`quoteId` identifies one concrete signed quote.

An issuer MUST NOT intentionally assign the same `quoteId` to two non-identical quote bodies.

An issuer SHOULD generate `quoteId` from at least 128 bits of entropy or from another issuer-side unique record.

`quoteId` does not imply one-time use, replacement, revocation, or grouping with other quotes.

A reissued quote MUST use a new `quoteId`.

This ERC deliberately does not define an offer-group identifier or cross-quote consumption semantics. Applications that present mutually exclusive payment alternatives or require single-use consumption MUST define and enforce that state outside this quote.

### Validity

A quote is valid at verification time `t` when:

```text
validAfter <= t <= validUntil
```

`validUntil` limits creation or submission of a new settlement based on the quote. It does not require an already-submitted blockchain transaction to be included in a block before `validUntil`.

A verifier MUST reject a quote before `validAfter` or after `validUntil`.

A settlement mechanism that enforces quote validity at execution time MUST reject execution after `validUntil`. An on-chain component MAY verify only the signature and settlement fields; unless it can independently derive the canonical request according to `requestScheme`, it MUST NOT claim that the request binding has been verified.

When the selected payer authorization or settlement mechanism contains its own deadline, that deadline MUST NOT exceed `validUntil`.

An implementation SHOULD account for clock skew and expected transaction-submission latency when selecting quote validity periods.

### EIP-712 domain

Quotes MUST use the following EIP-712 domain:

```text
name:    "Signed Service Payment Quotes"
version: "1"
chainId: settlement chain ID
```

The domain type is:

```text
EIP712Domain(string name,string version,uint256 chainId)
```

`chainId` MUST identify the chain on which `asset` and `recipient` are interpreted.

The domain intentionally omits `verifyingContract` because the quote is independent of a particular settlement contract.

A verifier MUST reject a quote whose domain `chainId` differs from the intended settlement chain.

### Typed data

The canonical quote type string is:

```text
ServicePaymentQuote(address issuer,address payer,address recipient,address asset,uint256 amount,string requestScheme,bytes32 requestHash,bytes32 quoteId,uint64 validAfter,uint64 validUntil)
```

The domain separator MUST be calculated according to EIP-712 using the domain defined above.

The quote struct hash MUST be calculated according to EIP-712. In particular, `requestScheme` is encoded as the Keccak-256 hash of its UTF-8 bytes as required for EIP-712 dynamic values.

The quote digest is:

```text
quoteDigest = keccak256("\x19\x01" || domainSeparator || quoteStructHash)
```

### Signature verification

A verifier MUST first establish `expectedIssuer` independently from the quote.

A quote MUST be rejected unless:

```text
quote.issuer == expectedIssuer
```

For an issuer account with no code on the settlement chain, a verifier MUST validate a secp256k1 signature over `quoteDigest` and require the recovered address to equal `issuer`.

A 65-byte ECDSA signature MAY encode recovery parity as either `27`/`28` or `0`/`1`. A verifier supporting both forms MUST normalize them before recovery.

ECDSA verification MUST reject zero `r`, zero `s`, and high-`s` signatures.

For an issuer account with code on the settlement chain, a verifier MUST call ERC-1271:

```solidity
isValidSignature(quoteDigest, signature)
```

and accept only the ERC-1271 magic value:

```text
0x1626ba7e
```

A verifier MUST NOT fall back to ECDSA recovery when an issuer is classified as an ERC-1271 account.

A verifier whose trust configuration explicitly pins an issuer authentication method MAY use that pinned method instead of classifying by code presence.

A verifier that has neither a pinned authentication method nor authenticated access to settlement-chain state MUST NOT treat the quote as authenticated.

Counterfactual contract issuers and wrapped counterfactual signatures are outside the scope of this ERC.

### Payer binding

A non-zero `payer` binds the quote to that payer.

Before settlement, a verifier MUST determine the non-zero account whose assets fund the commercial payment.

For a non-zero `quote.payer`, the selected payer MUST equal `quote.payer`.

For a bearer quote, the surrounding application MUST explicitly permit bearer quotes and MUST bind the selected payer through the separate payer authorization or settlement mechanism.

A bearer quote does not authorize any account to spend funds.

Applications using bearer quotes for single-use or non-idempotent requests SHOULD include a client-generated nonce inside the request committed by `requestHash`.

### Verifier procedure

Before treating a quote as authenticated terms for a concrete request, a verifier MUST:

1. establish the `expectedIssuer`;
2. check all structural field requirements;
3. check the intended settlement `chainId`;
4. check `validAfter <= verificationTime <= validUntil`;
5. determine the effective payer and apply the payer-binding rules;
6. support the signed `requestScheme`;
7. independently derive the canonical priced request and verify `requestHash`;
8. recompute `quoteDigest`;
9. verify the issuer signature; and
10. compare the settlement terms against the quote before payer authorization or submission.

### Settlement conformance

The issuer signature authenticates provider terms. It does not authorize payer funds.

The payer MUST separately authorize the selected settlement mechanism.

A settlement integration claiming conformance with this ERC MUST ensure that the commercial payment matches:

- the quote domain `chainId`;
- the effective payer;
- `quote.asset`;
- `quote.recipient`; and
- `quote.amount`.

For a bearer quote, the effective payer is the non-zero payer selected by the surrounding application and bound by the payer authorization.

A settlement integration MUST NOT replace the signed chain, asset, recipient, or amount merely because another payer authorization would be valid.

If the settlement uses an escrow, router, account-abstraction entry point, payment facilitator, or another mechanism whose behavior affects the payer, the payer authorization or application policy MUST separately authenticate those settlement semantics.

This ERC does not define a payment scheme, settlement contract, fee model, refund rule, or escrow lifecycle.

### Transport bindings

This ERC does not define how a quote is transported.

A transport binding that carries this quote MUST define:

1. how `expectedIssuer` is authenticated for the service;
2. the allowed `requestScheme` values;
3. where the quote and signature are carried;
4. the bearer-quote policy; and
5. how the selected payer is bound to the eventual payer authorization.

An HTTP, x402, MCP, A2A, JSON-RPC, or other binding MAY reuse the same quote format without changing the EIP-712 schema.

### JSON transport encoding

When this ERC is carried as a standalone JSON object, the envelope MUST contain the top-level members `chainId`, `quote`, and `signature`. `chainId` is the EIP-712 domain chain ID. The domain `name` and `version` are fixed by this ERC and are not repeated in the envelope.

Additional top-level members MAY be defined by transport bindings. They MUST NOT alter the interpretation of `chainId`, `quote`, or `signature`, and MUST NOT be treated as authenticated by the quote signature unless they are separately cryptographically bound. Generic implementations SHOULD ignore unrecognized top-level members.

The `quote` object MUST use the field names defined by `ServicePaymentQuote` exactly as written in the quote structure.

The example below uses the same quote as the canonical test vector in the Test Cases section:

```json
{
  "chainId": "8453",
  "quote": {
    "issuer": "0x7e5f4552091a69125d5dfcb7b8c2659029395bdf",
    "payer": "0x2222222222222222222222222222222222222222",
    "recipient": "0x3333333333333333333333333333333333333333",
    "asset": "0x4444444444444444444444444444444444444444",
    "amount": "1000000",
    "requestScheme": "com.example.service/1",
    "requestHash": "0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "quoteId": "0xbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "validAfter": "1788372000",
    "validUntil": "1788372300"
  },
  "signature": "0x2051fd043967b356866060fb9bf95e11b735f03cab03d0f7f6c736abbdf55a42311f85b1f7f34e4f1008a494fb10aed2965589f96fca3f99c2bb72994ab345e41c"
}
```

The JSON encoding MUST satisfy all of the following:

- `chainId` and `amount` MUST be encoded as base-10 strings;
- `validAfter` and `validUntil` MUST be encoded as base-10 strings;
- base-10 integer strings MUST match `0|[1-9][0-9]*` and decode within the range of their corresponding EIP-712 integer type;
- addresses MUST be encoded as `0x` followed by exactly 40 hexadecimal digits;
- `requestHash` and `quoteId` MUST be encoded as `0x` followed by exactly 64 hexadecimal digits; and
- `signature` MUST be encoded as a `0x`-prefixed even-length hexadecimal byte string.

Transport-level JSON key ordering, whitespace, and address letter case do not participate directly in the EIP-712 signature because the signature is computed from the parsed typed values.

## Rationale

### Why a separate ERC

Provider-signed offers already exist in payment protocols, including the x402 Offer and Receipt extension.

This ERC does not attempt to replace those protocol-specific offers. It standardizes an EVM artifact that can be reused by multiple transports and verified with the same EIP-712 and ERC-1271 semantics.

The interoperability target is therefore not "signed offers" in general. It is the representation and verification of a request-bound provider payment quote for EVM settlement.

An x402 binding can carry this quote, but an MCP, A2A, wallet, or direct application flow can carry the same quote without adopting x402 as its transport.

### Why request canonicalization is outside this ERC

Different transports do not share one natural request representation.

HTTP has methods, targets, headers, and content. MCP and A2A have protocol-specific operation and payload structures. JSON-RPC has method and parameter semantics. Attempting to define all of those canonicalization rules inside one ERC would couple the quote format to unrelated transport standards and substantially increase implementation risk.

This ERC therefore signs two request-binding values:

- `requestScheme`, identifying the canonicalization rules; and
- `requestHash`, committing to the result.

The transport or application binding defines the scheme. Request-binding interoperability therefore requires issuer and verifier to implement at least one common scheme. Widely reusable schemes can be standardized separately without changing the quote format defined by this ERC.

This is analogous to separating a generic signed envelope from the protocol-specific data placed inside that envelope.

### Request commitment design

Using separate commitments for the operation identifier and request payload would create two independent canonicalization surfaces and could permit combinations in which one component is bound while another semantically relevant component is omitted.

This ERC requires the request scheme to include the service or operation identity in the canonical request itself. A single hash therefore commits to the complete priced invocation defined by the binding.

### Quote identity and offer grouping

A logical offer can contain alternative chains, assets, refreshed prices, or reusable terms. The consumption semantics of such a group are application-specific and can require shared cross-chain state.

A signed identifier alone cannot make alternatives mutually exclusive or revoke older quotes.

This ERC therefore defines only `quoteId`, which identifies one immutable signed quote. Grouping, replacement, revocation, and one-time consumption are intentionally outside scope.

### Validity without issuance time

An issuer-signed issuance timestamp proves only that the issuer asserted a time; it does not independently prove when the quote existed.

The security property required by this ERC is a bounded period in which the quote may be used. `validAfter` and `validUntil` provide that property without adding another timestamp semantic.

Applications requiring maximum quote age can use shorter validity periods or define additional metadata in a higher-level protocol.

### Why `uint64` timestamps

Unix timestamps do not require the range of `uint256`.

Using `uint64` gives a fixed and more than sufficient range while avoiding arithmetic edge cases when settlement protocols derive nearby time bounds.

EIP-712 still encodes the value deterministically according to its declared `uint64` type.

### Why `verifyingContract` is omitted

The provider quote can be consumed by different settlement mechanisms.

Binding it to one `verifyingContract` would prevent the same quote from being used with a direct transfer, an authorization-based transfer, an escrow, or another adapter.

The settlement chain remains in the EIP-712 domain because token and account addresses are chain-scoped commercial terms.

### Why settlement mechanics are not signed

This quote authenticates the provider's commercial payment leg: payer policy, chain, asset, recipient, and exact amount.

It does not claim that two settlement mechanisms are semantically equivalent.

When a particular escrow, router, facilitator, or execution path matters to the payer, that behavior is authenticated by the separate payer authorization or enforced by the surrounding application.

A protocol that requires the provider itself to commit to settlement-program semantics can define a higher-level order object rather than changing the meaning of this minimal quote.

### Relationship to x402 Offer and Receipt

Protocol-specific signed offers, including the x402 Offer and Receipt extension, are prior art for provider-authenticated payment terms.

Such artifacts are defined as part of their respective payment protocols. This ERC instead standardizes an EVM quote representation that can be carried by multiple protocols and does not depend on a particular x402 version or field layout.

The main additional semantic provided here is a signed commitment to the exact priced request under an identified request scheme. It also defines ERC-1271 verification and optional pre-payment payer binding.

An implementation that uses both protocols can define an x402 binding for this quote. The signed artifacts are not intended to be wire-compatible.

### Relationship to HTTP Message Signatures

HTTP Message Signatures can authenticate selected components of an HTTP message and are appropriate for HTTP-specific request or response authentication.

This ERC does not replace them.

An HTTP request scheme can be defined using HTTP Message Signature component derivation or another deterministic HTTP representation, while the resulting commitment is carried inside this EVM-specific commercial quote.

The distinction is the signed object: this ERC authenticates EVM payment terms and an opaque request commitment, rather than defining a general HTTP-message signature format.

### Lightweight issuer verification

General-purpose off-chain verifiers may classify an issuer by authenticated settlement-chain code state. Deployments that require offline or lightweight verification can instead pin the issuer authentication method as part of the independently authenticated issuer configuration.

### Relationship to payer authorizations

Payer authorization standards prove that a payer approved a transfer.

This ERC proves a complementary statement: an authenticated provider asserted the quoted terms for the committed request.

A payment flow can therefore validate the provider quote before constructing the payer authorization, and then ensure that the authorization matches the quote.

## Backwards Compatibility

This ERC introduces a new off-chain typed-data format and does not modify Ethereum consensus, transaction validity, [ERC-20](./eip-20.md) behavior, ERC-1271, or existing payment protocols.

Existing systems can ignore the quote.

Protocol bindings can introduce this quote alongside their existing payment messages without changing the EIP-712 schema defined here.

## Security Considerations

### Provider identity

A valid signature proves control of the `issuer` account. It does not prove that the account belongs to the service the payer intended to use.

The verifier must obtain `expectedIssuer` from an independently authenticated trust mechanism.

A malicious intermediary that can replace both the service identity and the quote remains outside the protection of this ERC.

### Quote signatures do not authorize funds

The issuer signature is not a payer signature.

Any implementation that treats the provider quote as authority to transfer payer assets creates an independent asset-theft vulnerability.

### Request-scheme completeness

The security of request binding depends on the request scheme.

If a field can change the operation, price, recipient behavior, or requested result but is omitted by the scheme, the quote does not authenticate that field.

Published request schemes should therefore be narrow, deterministic, versioned, and explicit about all semantically relevant components.

### Request transformation

The issuer and verifier must derive the same canonical request.

If an intermediary transforms a request between the verifier and issuer, the request scheme must be defined at a layer observed consistently by both parties or the transformer becomes part of the trusted boundary.

The quote does not prove the semantics of data after an uncommitted transformation.

### Request privacy

`requestHash` is a commitment, not encryption.

Low-entropy requests can be guessed by dictionary attack if an observer obtains the quote.

Applications requiring confidentiality should include unpredictable committed entropy or use a separate privacy-preserving mechanism.

### Bearer quotes

A bearer quote can be used by any payer permitted by the surrounding application.

For single-use or non-idempotent operations, interception can allow another payer to race the intended payer.

A client-generated nonce inside the committed request and delivery bound to the actual settling payer reduce this risk.

### Replay

`quoteId`, payer binding, request binding, chain binding, and the validity window limit replay contexts but do not create global consumption state.

A quote may be presented more than once while valid.

Applications that require exactly-once execution must maintain consumption state separately.

### Quote replacement and revocation

Issuing a new quote does not revoke an earlier quote.

Each validly signed quote remains usable until its own `validUntil` unless a higher-level protocol defines revocation.

Applications should use short validity periods when rapid repricing or revocation is required.

### Settlement expiry

`validUntil` governs new authorization or submission, not blockchain inclusion time.

A transaction submitted while the quote is valid can be included after expiry.

Applications requiring an on-chain execution deadline must use a settlement mechanism or adapter that enforces one.

### Additional fees

The signed `amount` covers only the quoted commercial payment.

Additional gas, facilitator, relayer, conversion, or protocol fees are not authenticated by the provider quote.

A payer or autonomous agent must apply its own policy to those separately authorized costs.

### Asset identity and token behavior

The signed asset identity is the pair of settlement `chainId` and `asset` address.

Token symbols, names, and decimals are not signed identifiers.

Fee-on-transfer, rebasing, callback-enabled, upgradeable, or malicious token contracts can behave differently from a simple nominal transfer. Settlement integrations remain responsible for token-specific execution risk.

### Counterfactual issuers

This ERC does not define verification for counterfactual contract issuers or [ERC-6492](./eip-6492.md) wrapped signatures. Higher-level bindings can add such support without changing the signed quote structure.

### ERC-1271 mutability

ERC-1271 validity can change over time because contract ownership, code, delegation, or policy can change.

A verifier requiring durable historical evidence should retain the quote, signature, verification result, and relevant chain context at the time of acceptance.

### Delegated accounts

An account with code is verified through ERC-1271 under the default classification rule.

This includes an account whose code is an [EIP-7702](./eip-7702.md) delegation designator.

A delegated account whose implementation does not support ERC-1271 cannot authenticate quotes through the contract-account path unless the verifier trust configuration explicitly pins another supported method.
