## Abstract

This standard defines a common lifecycle for the authorities that authorize a native account-abstraction account: how an authority is added, rotated, and revoked. An authority (a signing key, or more generally an authorization predicate such as a spending lock or a limit) is a leaf in a per-account committed tree whose root the account publishes referenceably. A transaction carries a membership proof for the acting authority and names the root it proves against; the account verifies the proof in its own authorization step and withholds authorization on failure. Add is a leaf insertion, rotate is a leaf replacement, and revoke is a leaf removal, each realized as a new committed root.

The lifecycle is stated over a committed root and a membership proof, not over any one account model's opcodes. It therefore binds to more than one native account-abstraction family as a peer of each: this document gives a normative binding to [EIP-8141](./eip-8141.md) frame transactions and an informative binding to [EIP-8130](./eip-8130.md) keystore accounts. A single transaction type can then carry both an account whose own code is the authority and an account backed by a shared keystore, because both reduce to the same check.

## Motivation

Native account-abstraction designs let a transaction reach a target while the account is named as the caller, without running the account's own entry-point code. Any rule an account enforces only inside that entry point is therefore not consulted on such a path. The account must re-express the rule where authorization is decided.

The families that decide authorization do so differently. In the code-is-authority model (EIP-8141) the account's own code runs in a frame that can withhold approval. In the keystore or registry model (EIP-8130) the account declares an authenticator and the node reads the account's configuration. What is missing across both is a shared meaning for the operations wallets perform on an account's authority set: add, rotate, revoke. Without one, every model defines these independently and wallets must reconcile all of them.

A shared lifecycle is also what lets a single transaction type stay light while serving both models. Without it, one transaction type has to either branch on which authority model applies or read a foreign keystore during validation, which is expensive and hard to admit to a public mempool. When both models reduce to the same operation, prove the acting authority is a leaf under the account's named committed root, the transaction type carries neither a per-model branch nor a foreign state read. [EIP-8272](./eip-8272.md) supplies exactly this primitive: it lets a transaction name a recent commitment-tree root and have clients check the reference against pre-state before any account code runs, and its own Motivation names "wallet authorization roots" as an intended use.

This standard fixes that shared meaning once, model-agnostically: it constrains what add, rotate, and revoke mean over a committed authority root, not which authenticator or account layout an implementation uses.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

The core (Authority tree, Lifecycle operations, Authorization check, Isolation) is stated model-neutrally. Each binding below realizes the core with one family's primitives and defines the family-specific terms it uses.

### Authority tree

An account MUST associate its authorities with a single committed tree. Each leaf is an `authorization`:

```text
authorization = (authority_id, predicate)
```

- `authority_id` is a 32-byte stable handle for an authority slot or role. It is chosen at add time and is independent of the key material, so rotating the underlying key does not change it.
- `predicate` is the account-defined data the account's authorization step evaluates: for example a public key, an authenticator address, a threshold, a spend ceiling, or an unlock time.

The leaf encoding MUST be a deterministic function of `(authority_id, predicate)`. Implementations SHOULD use `leaf = keccak256(authority_id || predicate)` so that independent tooling can reconstruct and index a tree without account-specific knowledge.

The tree root MUST be published as a committed root the account controls and is the sole writer for: a root that a transaction can name and that clients can check against pre-state before the authorization step runs. Each binding below specifies the referencing mechanism.

### Lifecycle operations

An account changes its authorities only by publishing a new root:

- **add**: insert a leaf for a new `authorization`, publish the new root.
- **rotate**: replace an existing `authority_id`'s `predicate` (for example bind a new key to the same slot), publish the new root.
- **revoke**: remove a leaf, publish the new root.

An operation takes effect when the new root becomes referenceable. Each binding specifies when that is.

### Authorization check

The transaction MUST carry the membership proof for the acting `authorization` and MUST name the committed root it proves against. The tree shape and proof format are account-defined; the root proven against MUST be a referenceable committed root, not a value read from mutable storage. Each binding specifies how the proof and the root reference are carried and read.

The authorization check MUST run in the account's own authorization step: the step whose failure withholds authorization of the transaction, and which runs code the account controls. Placing the check where the account's own code does not run does not satisfy this requirement. Each binding names this step.

The authorization step MUST NOT authorize execution unless the carried proof verifies for the acting `authorization` against an accepted root. Two conformance tiers are defined; an account MUST implement at least one.

- **Tier 1 (root-bound, mempool-cheap).** The check reads only the transaction-named root reference and the carried proof. It accepts any referenceable root under the account's fixed root source and grants authorization only if the proof verifies against it. It MUST NOT read mutable account or external storage. Revocation latency is bounded by the referencing mechanism's recency window: a dropped leaf's earlier root stays referenceable until it leaves the window.

- **Tier 2 (floor-bound, instant revocation).** In addition to Tier 1, the check reads one account-owned monotonic value (a rotation-floor slot) with a single storage read and rejects any reference whose slot is below the floor. Raising the floor on rotate or revoke makes the change effective at the next block, at the cost of the mempool-cheap admission tier. A single-authority account MAY instead read its current authorized root directly, which is the degenerate case of the same rule.

The account MUST fail closed: if no accepted authorization is proven, the authorization step MUST NOT authorize execution, and the transaction is invalid.

### Isolation

Authorization MUST be keyed by the account: an authority proven for one account MUST NOT authorize another. Because each account proves against its own subtree under its own root source, revoking an authority affects only that account and does not invalidate authorities held by other accounts.

### Binding: EIP-8141

Terms `FrameTx`, `VERIFY`, `SENDER`, frame modes, `APPROVE`, `TXPARAM`, `FRAMEDATALOAD`, and `RECENTROOTREFLOAD` have the meanings defined in [EIP-8141](./eip-8141.md) and [EIP-8272](./eip-8272.md).

Under [EIP-8141](./eip-8141.md) the account's authorization step is a `VERIFY` frame targeting the account, or a `SENDER` frame that self-`APPROVE`s; withholding authorization is withholding that frame's `APPROVE`. Placing the check in a dispatched frame that targets another contract does not satisfy the core, because that frame does not run the account's code.

The membership proof is carried in frame-declared data and read with `FRAMEDATALOAD`. The committed root is named as an [EIP-8272](./eip-8272.md) recent-root reference and read with `RECENTROOTREFLOAD`; the root MUST be published as an EIP-8272 recent root under a `source_id` the account controls and is the sole writer for. The `source_id` a Tier-1 account accepts is fixed in the account's code at deployment. The one-slot effect delay of a lifecycle operation is the EIP-8272 recent-root delay.

This binding applies to accounts with code; a codeless default account (EIP-8141) runs protocol-default behavior and has no authorizing code to carry the check.

### Binding: EIP-8130

This binding is informative. It shows how the core maps onto the [EIP-8130](./eip-8130.md) keystore-account family as a peer of the EIP-8141 binding, and locates the one primitive that family has not yet published.

The datum and its lifecycle map directly, and this mapping is stable across the family's revisions: an authority is an actor `(actorId, config)`, where `actorId` is a 32-byte stable handle and the actor's configuration (its authenticator, scope, expiry, and any policy commitment) is the account-defined predicate; the family's authorize and revoke batch operations, signed and sequenced, are add, rotate, and revoke. So `actorId` is the `authority_id`, the actor configuration is the `predicate`, and the batch operations are the lifecycle operations. Isolation already holds, because every actor is keyed by its account.

What the family does not publish is a referenceable current-state root. It commits an account's *birth* actor set into the account address, as a hash over the sorted actor leaves, and reconstructs the *current* set either by reading the live per-actor configuration or, on its stateless path, by replaying the signed change chain carried in the transaction. The family's Stateless Accounts proposal makes this explicit: a compact proof that the current set is a valid descendant of the birth set, replacing replay of every batch, is named as a later addition and left unspecified. This standard's committed-root binding is that piece for authority state. Because the family already commits the sorted actor leaves at birth, publishing the *current* set as a referenceable root over the same leaves is additive rather than a redesign. The authorization step is then the family's authenticator-and-scope check, verifying one authority's membership proof against the named published root instead of reading or replaying the configuration.

This preserves the family's property that a node sees a transaction's validation cost without executing wallet code, and adds Tier 1's no-mutable-read admission. Until such a root is published, an account in the family is admitted by reading or replaying its configuration, a bounded-witness shape outside this standard's two membership-proof tiers; adopting the committed-root binding is what moves it onto them.

## Rationale

The ideal external keystore is no external keystore: placing the authority datum in the account's own committed tree, keyed by the account, removes cross-account invalidation. One account's rotation cannot invalidate another's pending transactions, because there is no shared authority whose change fans out.

This also resolves the apparent choice between an account header and a keystore. A header selects the authorizing code; the tree supplies which authority is authorized as proven data. A single-authority account can stay on the header alone; multi-signature and session-key accounts keep the tree. Neither is required to adopt the other.

Because the core is stated over a committed root and a membership proof rather than over any one model's opcodes, the code-is-authority and keystore-backed families are peer bindings of it, not a primary and a special case. A single transaction type can then serve both without branching on the model or reading a foreign keystore during validation: each account proves against its own published root, and both reduce to the same check. This is what keeps the shared transaction type light, because the expensive alternatives, simulating wallet code or reading foreign mutable state per transaction, are replaced by one proof against a named root.

Making `authority_id` a stable handle independent of key material lets rotate change the bound key while preserving the account's reference to that authority slot, which is what a key rotation is. Add, rotate, and revoke are expressed as root transitions rather than as protocol operations so the same lifecycle applies whether the authority is a key, a lock, or a limit. This lets an account enforce an execution-time invariant, such as a lock or a ceiling, at authorization time, on the direct-dispatch path where its entry-point code does not run.

The two tiers make the revocation-latency trade-off explicit rather than hidden. Tier 1 keeps the check free of mutable reads, so it fits a bounded public mempool, at the cost of revocation latency up to the recency window. Tier 2 buys next-block revocation with one mutable read, moving admission to the tier that permits it. Both keep invalidation account-bounded.

### General principle

The split into two tiers is not arbitrary. The cost of an authorization check is set by how much mutable state it reads. Tier 1 reads nothing beyond its carried proof and a committed root, so it is admissible to a bounded public mempool. Tier 2 reads one account-owned monotonic value, so it moves to the admission tier that permits a mutable read. A check that would depend on live external state gains no tier here; it is outside the mempool-cheap path by construction.

The same rule applies to every input a check consumes, not only to the acting authority. Where a dependency can be committed ahead of time, an account SHOULD carry it as a proof rather than read it at authorization. A sponsor authority, for example, is proven as a leaf in the sponsor's own committed root and carried in the transaction, instead of read from the sponsor's live account. A carried capability MUST be bound to the account that consumes it, so that a proof valid for one account does not authorize another. Its revocation follows the same two tiers as an account's own authority: under Tier 1 a rotated-away capability stays provable until its last authorizing root leaves the recency window, and prompt revocation requires the granting account to keep a Tier 2 floor. Only a dependency that is genuinely live and cannot be pre-committed stays outside the cheap path.

## Backwards Compatibility

This standard adds no transaction type, opcode, or consensus rule. It is a convention over primitives its bindings already provide. Accounts that do not adopt it are unaffected. An account that adopts it is authorized exactly as before on any path that runs its authorizing code.

## Security Considerations

- **Opt-in.** The protection exists only for accounts whose authorizing code performs the check. An account that does not is not protected on the direct-dispatch path. This is inherent to any account-defined authorization and is not specific to this standard.
- **Revocation latency (Tier 1).** Under Tier 1 a revoked authority stays provable until its last authorizing root leaves the referencing mechanism's recency window. Accounts that require prompt revocation MUST use Tier 2.
- **Root-source liveness.** If the account's root source stops publishing, the authority set freezes at the last root and, once it ages out of the window, references fail closed. Accounts SHOULD provide a fallback authority path.
- **Cross-chain rotation is not atomic.** An authority rotated on one chain remains usable on another until that chain's root is updated. This is a property shared by any cross-chain shared-authority design and is not resolved here.
- **Keyed nonces do not bypass the check.** Under [EIP-8250](./eip-8250.md) each frame still runs the account's authorizing code, so choosing a different nonce domain does not skip authorization.
- **Carried capabilities.** A capability proven against a granting account's root and carried in the transaction MUST be bound to the consuming account, or a proof valid for one account replays on another. A revoked capability also stays provable for the granting account's Tier 1 recency window unless the granting account keeps a Tier 2 floor, so a capability meant to be promptly revocable MUST be granted under Tier 2.
- **Keystore-family binding is gated on a published root.** The keystore-family binding is informative because that family does not yet publish a referenceable current-state authority root; the family's Stateless Accounts proposal names such a compact proof as a later addition. Until one exists, an account in the family is admitted by reading or replaying its configuration, a bounded-witness shape outside this standard's two membership-proof tiers, and gains the mempool-cheap Tier 1 only once a current-state root is published to prove against.
