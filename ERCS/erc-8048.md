## Abstract

This ERC defines an onchain metadata standard for multi-token and NFT registries including [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), and [ERC-6909](./eip-6909.md). The standard provides a key-value store allowing for arbitrary bytes to be stored onchain.

## Motivation

This ERC addresses the need for fully onchain metadata while maintaining compatibility with existing [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), and [ERC-6909](./eip-6909.md) standards. It has been a long-felt need for developers to store metadata onchain for NFTs and other multitoken contracts; however, there has been no uniform standard way to do this. Some projects have used the `tokenURI` field to store metadata onchain using Data URLs, which introduces gas inefficiencies and has other downstream effects (for example making storage proofs more complex). This standard provides a uniform way to store metadata onchain, and is backwards compatible with existing [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), and [ERC-6909](./eip-6909.md) standards.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Scope

This ERC is an optional extension that MAY be implemented by any [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), or [ERC-6909](./eip-6909.md) compliant registries.

### Required Metadata Function and Event

Contracts implementing this ERC MUST implement the following interface:

```solidity
interface IERC8048Metadata {
    /// @notice Get metadata value for a key.
    function metadata(uint256 tokenId, string calldata key) external view returns (bytes memory);
    
    /// @notice Emitted when metadata is set for a token.
    event MetadataSet(uint256 indexed tokenId, string indexed indexedKey, string key, bytes value);
}
```

- `metadata(tokenId, key)`: Returns the metadata value for the given token ID and key as bytes

Contracts implementing this ERC MAY also expose a `setMetadata(uint256 tokenId, string calldata key, bytes calldata value)` function to allow metadata updates, with write policy determined by the contract.

Contracts implementing this ERC MUST emit the following event when metadata is set:

```solidity
event MetadataSet(uint256 indexed tokenId, string indexed indexedKey, string key, bytes value);
```

### Interface Detection

The interface ID is `0xdf670be1`.

Contracts implementing `IERC8048Metadata` MUST implement [ERC-165](./eip-165.md) and MUST return `true` from `supportsInterface` for both `0xdf670be1` (this interface) and `0x01ffc9a7` ([ERC-165](./eip-165.md) itself), so that callers can detect onchain-metadata support before reading records.

### Key/Value Pairs

This ERC specifies that the key is a string type and the value is bytes type. This provides flexibility for storing any type of data while maintaining an intuitive string-based key interface.

### Optional Key Parameters

Keys MAY include parameters to represent variations or instances of a metadata type, such as `"registration[1]"` or `"name[maria]"`; see [ERC-8119](./eip-8119.md) for the standard parameterized key format.

### Examples

Event tickets are a good fit for onchain metadata. A ticket's details are what give it value, so they belong with the token, and the token remains a complete record of the event after it ends.

#### Example: Event ticket

An [ERC-721](./eip-721.md) token is a single ticket. For `tokenId == 1`:

- `"event"` → `bytes("Example Jazz Festival 2027, Night 1")`
- `"venue"` → `bytes("Example Arena, Lisbon")`
- `"start"` → `abi.encode(uint64(1815249600))` (Unix time, July 10, 2027, 20:00 UTC)
- `"seat"` → `bytes("Section 104, Row F, Seat 12")`

A venue contract or scanner can read these values onchain at the door without an offchain API. After the event, the issuer can add records such as `"setlist"`, so the ticket also becomes a commemorative item.

#### Example: Biometric Identity for Proof of Personhood

A biometric identity system using open source hardware to create universal proof of personhood tokens.

- Key: `"biometric_hash"` → Value: `bytes(bytes32(identity_commitment))`
- Key: `"verification_time"` → Value: `bytes(bytes32(timestamp))`
- Key: `"device_proof"` → Value: `bytes(bytes32(device_attestation))`

### Agent Metadata Profile (ERC-721T)

This profile, nicknamed **ERC-721T**, defines a reserved set of this ERC's metadata keys for [ERC-721](./eip-721.md) tokens that represent, expose, control, or are associated with agents. It is a standard *use* of this ERC's existing key-value interface; it does **not** define a new Solidity interface, a new [ERC-165](./eip-165.md) interface ID, or new events. Consumers read and write these records through `metadata(uint256,string)` and rely on the `MetadataSet` event for change notifications, exactly as for any other key under this ERC.

A contract implementing this profile MUST implement ERC-721 and this ERC. The profile reserves the following per-token keys:

| Key | Meaning | Value (`bytes`) |
| :--- | :--- | :--- |
| `context` | Agent context for the token. | UTF-8 text. Markdown is RECOMMENDED; issuers MAY embed a fenced JSON block for machine-readable fields. |
| `endpoint[<type>]` | Endpoint for the named protocol `<type>`. | UTF-8 text. For `endpoint[web]`, an `https` URI is RECOMMENDED. |
| `address[<chain-id>]` | The agent's account on the chain identified by `<chain-id>`, where `<chain-id>` is the [ERC-7930](./eip-7930.md) Chain Identifier (see "Chain-keyed addresses" below). | The Address component of an [ERC-7930](./eip-7930.md) Interoperable Address for the chain named by `<chain-id>`. For an EVM chain, the 20-byte address. |
| `account[<chain-id>][<index>]` | OPTIONAL. An additional account of the agent on the chain identified by `<chain-id>`, distinguished by `<index>`. See "Additional accounts" below. | The Address component of an [ERC-7930](./eip-7930.md) Interoperable Address for the chain named by `<chain-id>`. For an EVM chain, the 20-byte address. |

#### Endpoint types

Keys are case-sensitive (the value of `key` is compared as exact bytes). Endpoint types in this profile are therefore lowercase: `endpoint[mcp]` and `endpoint[MCP]` are distinct keys, and only the lowercase spelling carries the meaning reserved here. Implementations MUST write the canonical lowercase spelling for the types this profile reserves.

The canonical endpoint types are:

- `mcp`: Model Context Protocol endpoint URI.
- `a2a`: Agent-to-Agent endpoint URI.
- `web`: general web endpoint (aligned with [ERC-8004](./eip-8004.md) `web` service usage; the value MAY be any URI, with `https` RECOMMENDED).
- `x402`: payment-enabled endpoint URI.
- `ens`: the agent's ENS name, for example `agent.eth`. The value is the name as UTF-8 text.

Additional endpoint types MAY be used without changing this profile, provided they use the `endpoint[<type>]` form. Standards that reserve new types SHOULD define their exact canonical (lowercase) spelling.

#### Chain-keyed addresses

In `address[<chain-id>]`, `<chain-id>` is the [ERC-7930](./eip-7930.md) **Chain Identifier**, an Interoperable Address with a zero-length address part, encoded as a lowercase `0x`-prefixed hex string. The stored value is the Address component of an ERC-7930 Interoperable Address for that chain, the chain's native address bytes. It is the Address component alone, not a full Interoperable Address.

For example, the Chain Identifier for Ethereum mainnet (chain ID `1`) is `0x00010000010100`, and for Base (chain ID `8453`, i.e. `0x2105`) is `0x0001000002210500`. The agent's mainnet account would be stored as:

- Key: `"address[0x00010000010100]"` → Value: the 20 bytes of the EVM address.

#### Additional accounts

An agent MAY list additional accounts under the OPTIONAL key `account[<chain-id>][<index>]`. Any account qualifies, for example a token-bound account or a smart contract wallet.

`address[<chain-id>]` is the agent's primary account on that chain. Clients SHOULD send funds to `address[<chain-id>]` and SHOULD NOT assume an account listed under `account[<chain-id>][<index>]` accepts payments.

`<chain-id>` is the [ERC-7930](./eip-7930.md) Chain Identifier and the stored value is the ERC-7930 Address component for that chain, both exactly as in `address[<chain-id>]`.

`<index>`, an unsigned base-10 integer with no leading zeros, distinguishes multiple accounts on the same chain.

For example, an agent's additional account at index `0` on Ethereum mainnet would be stored as:

- Key: `"account[0x00010000010100][0]"` → Value: the 20 bytes of the EVM address.

#### Marketplace compatibility

`tokenURI(uint256)` remains the ERC-721 marketplace metadata mechanism and is unchanged by this profile. Contracts SHOULD keep `tokenURI` JSON compatible with existing marketplaces (`name`, `description`, `image`). Agent-aware clients SHOULD read the keys above from this ERC's records rather than from `tokenURI`, and SHOULD treat both endpoints and `context` as untrusted input. Transferring the token transfers ownership of the record, not any offchain server, key, balance, or memory the records may reference. Where the contract implements the **Holder Metadata** or **Collection Authority** extension, clients SHOULD read `canHolderUpdateMetadata()` and `collectionAuthority()` to learn who can change the token's records.

### Optional Collection Authority Extension

This optional, standalone extension names one **collection authority** for the whole contract. The authority can be an account or a contract. A contract authority, called a policy contract here, can apply its own rules, for example letting different parties write different tokens or different keys.

An implementation of this extension MUST also implement `IERC8048Metadata` and [ERC-165](./eip-165.md).

The standardized surface is one read function and one event.

```solidity
interface IERC8048CollectionAuthority {
    /// @notice The collection authority, or the zero address when none is set.
    function collectionAuthority() external view returns (address);

    /// @notice Emitted whenever the authority changes, with the new authority.
    event CollectionAuthorityUpdated(address indexed authority);
}
```

#### Collection Authority Interface Detection

This extension's ERC-165 interface ID is `0x2d2a6041`, the selector of `collectionAuthority()`. Contracts implementing it MUST return `true` from `supportsInterface` for `0x2d2a6041`.

#### Authorization

The authority is the address that `collectionAuthority()` returns. The following rules apply to every function that writes metadata, including `setMetadata` and any batch function.

- When the authority is the zero address, no authority is set. The contract's own write policy decides who can write, which may be the contract owner or nobody.
- When the authority is not the zero address, the contract MUST authorize only that exact address to write metadata, for every token. The contract's own write policy no longer authorizes anyone. The one exception is a token's holder, when the contract also implements the Holder Metadata extension below and `canHolderUpdateMetadata()` returns `true`.
- A call that fails authorization MUST revert and MUST NOT emit `MetadataSet`.

#### Changing the authority

How the authority is changed, and whether it can be locked, is not part of this extension and is up to the implementation. Whatever mechanism an implementation uses, the following rules apply.

- The contract MUST emit `CollectionAuthorityUpdated` whenever the address that `collectionAuthority()` returns changes, with the new address.
- A contract that starts with a nonzero authority MUST emit `CollectionAuthorityUpdated` with that address when it is deployed.

### Optional Holder Metadata Extension

This optional, standalone extension is a flag that tells clients whether a token's current holder can write that token's metadata.

An implementation of this extension MUST also implement `IERC8048Metadata` and [ERC-165](./eip-165.md).

The standardized surface is one read function and one event.

```solidity
interface IERC8048HolderMetadata {
    /// @notice Whether a token's current holder can write that token's metadata.
    function canHolderUpdateMetadata() external view returns (bool);

    /// @notice Emitted whenever the flag changes, with the new value.
    event HolderCanUpdateMetadataSet(bool canUpdate);
}
```

#### Holder Metadata Interface Detection

This extension's ERC-165 interface ID is `0x12c220bd`, the selector of `canHolderUpdateMetadata()`. Contracts implementing it MUST return `true` from `supportsInterface` for `0x12c220bd`.

#### Holder writes

When `canHolderUpdateMetadata()` returns `true`, every function that writes metadata, including `setMetadata` and any batch function, MUST authorize a token's current holder to write that token's metadata.

For an [ERC-721](./eip-721.md) contract, the holder of a token is the address that `ownerOf(tokenId)` returns at the time of the write. After a transfer the new holder is authorized and the previous holder is not. An approved address or an operator is not the holder. A token that does not exist has no holder.

#### Changing the flag

How the flag is changed, and whether it can be locked, is not part of this extension and is up to the implementation. Whatever mechanism an implementation uses, the following rules apply.

- The contract MUST emit `HolderCanUpdateMetadataSet` whenever the value that `canHolderUpdateMetadata()` returns changes, with the new value.
- A contract that starts with the flag `true` MUST emit `HolderCanUpdateMetadataSet` with `true` when it is deployed.

### Contracts Implementing Both Extensions

A contract MAY implement the Collection Authority extension, the Holder Metadata extension, or both. The following rules apply only to a contract that implements both.

- When `canHolderUpdateMetadata()` returns `true`, the contract MUST authorize a token's current holder to write that token's metadata whether or not an authority is set.
- When the collection authority is not the zero address, the contract MUST still authorize it to write the metadata of every token, including records a holder wrote.

Who can change the authority and the holder flag is up to the implementation, as in each extension.

#### Example: a policy contract for a real-world asset

Consider houses tokenized as [ERC-721](./eip-721.md) tokens. Two public bodies each maintain their own regulated fields, while the owner of each house maintains everything else.

- The housing authority writes `gov.housing-authority.size`, the assessed size.
- The county assessor writes `gov.county-assessor.value`, the assessed value.
- The owner of the house writes `usr.<key>` records, for example `usr.listing-note`.

The contract sets a policy contract as the collection authority, and `canHolderUpdateMetadata()` returns `false`. Each party sends its write to the policy contract, which checks the caller against the key and then calls `setMetadata` on the token contract. The policy contract lets the housing authority write only the size and the county assessor write only the value. For a `usr.*` key it reads `ownerOf(tokenId)` and accepts the write only from that address, so after a sale the new owner writes these records and the seller no longer can. A direct call to `setMetadata` from any of the three parties reverts, because only the policy contract is authorized. Whether the contract owner can later replace the policy contract is up to the implementation.

### Onchain Metadata Contract Reference (Optional Extension)

Many [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), and [ERC-6909](./eip-6909.md) registries are already deployed without the `metadata` function or without storage reserved for the onchain key-value mapping. Adding that interface or storage layout is often impossible without an upgrade path, so those contracts cannot adopt the core pattern of this ERC on the token contract itself.

This optional extension keeps discovery compatible with existing `tokenURI` / `uri` flows while directing clients to a separate **metadata contract** that implements `metadata(uint256,string)` as defined in this ERC. The target is identified by its address, carried in JSON, and is on the same chain as the token registry. The function to call and its signature are fixed by this specification.

#### `tokenURI` / `uri` JSON field

When `tokenURI` ([ERC-721](./eip-721.md)), `uri` ([ERC-1155](./eip-1155.md)), or the equivalent URI function for [ERC-6909](./eip-6909.md) returns a string that resolves to a JSON document (including JSON embedded in a `data:` URL), the document MAY include a top-level string property named `"metadata_contract"`.

The value of `"metadata_contract"` MUST be the address of the metadata contract encoded as a single JSON string: a `0x` prefix followed by the 40 hexadecimal characters of the 20-byte address. Clients MUST accept any letter case.

Agent NFT Example:

```json
{
  "name": "Example",
  "image": "ipfs://bafybeigdyrzt5sfp7udm7hu76uh7y26nf3efuylqabf3oclgtqy55fbzdi",
  "metadata_contract": "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045",
  "endpoint[mcp]": "https://agents.example.com/mcp/1",
  "context": "I am an agent that can swap tokens on Ethereum mainnet."
}
```

It is possible to include metadata both directly in the `tokenURI` / `uri` JSON and in the `metadata_contract` for additional metadata.

#### Client behavior

Clients that support this extension:

1. Obtain and parse the JSON from `tokenURI` / `uri` as they already do for display metadata.
2. If a top-level `"metadata_contract"` string is present, parse the value as a 20-byte address. If it is not a `0x`-prefixed string of 40 hexadecimal characters, ignore it.
3. Read `metadata(uint256 tokenId, string key)` from that contract on the same chain as the token registry, using the same `tokenId` as for the `tokenURI` / `uri` call and the metadata key from this ERC. The return value is the same as if the token contract had stored the mapping locally.

The metadata contract is always on the same chain as the token registry. The target MUST implement `metadata(uint256,string)`, which makes it an EVM contract, so a chain-agnostic address format adds nothing here, and a plain address is what an implementer reaches for first.

Clients that do not implement this extension or do not trust the target contract address MAY ignore `"metadata_contract"` and continue to use other JSON fields.

#### Relationship to `IERC8048Metadata`

Registries using only this extension are NOT required to implement `IERC8048Metadata` on the token contract. The contract referenced by `metadata_contract` MUST implement the `metadata(uint256,string) external view returns (bytes)` function from this ERC (or a compatible implementation).

Security: clients SHOULD only call metadata contracts they consider trustworthy; a malicious or mistaken `metadata_contract` could return attacker-controlled `bytes`. Clients SHOULD show or verify the target address the same as for any new contract interaction.

## Rationale

This ERC standardizes a simple string-key, bytes-value metadata store for existing token registries. The optional `setMetadata` function allows updates under the contract's chosen write policy, and `MetadataSet` provides an onchain audit trail. **Onchain Metadata Contract Reference** extends this model to already-deployed tokens by pointing `metadata_contract` in `tokenURI` / `uri` JSON to a sidecar by its contract address.

The **Collection Authority** extension names one authority for the whole contract instead of one per token. Most collections are governed in one place, and a per-token authority cannot describe that well, because changing the authority of a collection would take one event for every token. With a collection authority, one read and one event tell a client who governs the records of every token. When different parties need to write different tokens or different keys, the authority can be a policy contract that applies those rules. The extensions do not define a lock or who can change the authority or the holder flag, because the standard covers what a client reads, and those rules differ from one implementation to the next.

The **Holder Metadata** extension is separate from the collection authority so that marketplaces have one standard read for it. When holders can write, a seller can change a token's records just before a sale lands, and a marketplace that reads `canHolderUpdateMetadata()` can warn the buyer. A contract can also offer holder writes without having a collection authority. The holder is defined for ERC-721, where `ownerOf` gives every client the same answer about who the holder is. Contracts of other token types can define their own holder rule.

## Backwards Compatibility

- Fully compatible with [ERC-721](./eip-721.md), [ERC-1155](./eip-1155.md), and [ERC-6909](./eip-6909.md).
- Non-supporting clients can ignore the scheme.
- The **Onchain Metadata Contract Reference** extension only adds an optional JSON property; clients that do not read `"metadata_contract"` behave as they do today.

## Reference Implementation

The interface is defined in the Required Metadata Function and Event section above. Here are reference implementations:

### Basic Implementation

```solidity
pragma solidity ^0.8.25;

import "./IERC8048Metadata.sol";

interface IERC165 {
    function supportsInterface(bytes4 interfaceId) external view returns (bool);
}

contract OnchainMetadataExample is IERC8048Metadata, IERC165 {
    // Mapping from tokenId => key => value
    mapping(uint256 => mapping(string => bytes)) private _metadata;
    
    /// @notice Get metadata value for a key
    function metadata(uint256 tokenId, string calldata key) 
        external view override returns (bytes memory) {
        return _metadata[tokenId][key];
    }
    
    /// @notice Set metadata for a token (optional implementation)
    function setMetadata(uint256 tokenId, string calldata key, bytes calldata value) 
        external {
        _metadata[tokenId][key] = value;
        emit MetadataSet(tokenId, key, key, value);
    }

    /// @notice ERC-165 interface detection
    function supportsInterface(bytes4 interfaceId) public pure override returns (bool) {
        return interfaceId == 0xdf670be1 || interfaceId == type(IERC165).interfaceId;
    }
}
```

### Collection Authority and Holder Metadata Implementation

```solidity
pragma solidity ^0.8.25;

import "./IERC8048Metadata.sol";
import "./IERC8048CollectionAuthority.sol";
import "./IERC8048HolderMetadata.sol";

interface IERC165 {
    function supportsInterface(bytes4 interfaceId) external view returns (bool);
}

/// @dev Reference implementation of the core interface plus the collection authority
///      and holder metadata extensions, written for ERC-721. It is abstract. A concrete
///      contract supplies `_contractOwner` and `_holderOf`. The lock, the
///      `authorityLocked` view, `setCollectionAuthority` and `setHolderCanUpdateMetadata`
///      are one example of how the values can be changed. They are not part of the
///      standard. The two events the setters emit are.
abstract contract OnchainMetadataAuthorityAndHolderExample is
    IERC8048Metadata,
    IERC8048CollectionAuthority,
    IERC8048HolderMetadata,
    IERC165
{
    // Mapping from tokenId => key => value
    mapping(uint256 => mapping(string => bytes)) private _metadata;

    // The collection authority, its lock and the holder flag. All three start at zero.
    address private _authority;
    bool private _authorityLocked;
    bool private _holderCanUpdate;

    /// @dev The contract owner. This contract's own write policy is that the owner
    ///      writes while no authority is set.
    function _contractOwner() internal view virtual returns (address);

    /// @dev The ERC-721 `ownerOf(tokenId)`, or the zero address if the token does not
    ///      exist. Approved addresses and operators are not holders.
    function _holderOf(uint256 tokenId) internal view virtual returns (address);

    function metadata(uint256 tokenId, string calldata key)
        external view override returns (bytes memory) {
        return _metadata[tokenId][key];
    }

    function collectionAuthority() external view override returns (address) {
        return _authority;
    }

    /// @dev Example only, not part of the standard. Whether the contract owner can no
    ///      longer change the authority or the holder flag.
    function authorityLocked() external view returns (bool) {
        return _authorityLocked;
    }

    function canHolderUpdateMetadata() external view override returns (bool) {
        return _holderCanUpdate;
    }

    function setMetadata(uint256 tokenId, string calldata key, bytes calldata value)
        external {
        require(_canWrite(tokenId, msg.sender), "not authorized");
        _metadata[tokenId][key] = value;
        emit MetadataSet(tokenId, key, key, value);
    }

    /// @dev Example only, not part of the standard. A zero authority cannot be locked.
    function setCollectionAuthority(address authority, bool locked) external {
        _checkCanChangeSettings();
        require(!locked || authority != address(0), "cannot lock zero authority");
        _authority = authority;
        _authorityLocked = locked;
        emit CollectionAuthorityUpdated(authority);
    }

    /// @dev Example only, not part of the standard.
    function setHolderCanUpdateMetadata(bool canUpdate) external {
        _checkCanChangeSettings();
        _holderCanUpdate = canUpdate;
        emit HolderCanUpdateMetadataSet(canUpdate);
    }

    /// @dev Example only, not part of the standard. The current authority can always
    ///      change the settings. The contract owner can change them until the authority
    ///      is locked.
    function _checkCanChangeSettings() internal view {
        if (msg.sender != _authority) {
            require(msg.sender == _contractOwner(), "not authorized");
            require(!_authorityLocked, "authority locked");
        }
    }

    /// @dev The authority writes any token, or the contract owner while no authority
    ///      is set. The token's current holder also writes when the holder flag is true.
    function _canWrite(uint256 tokenId, address account) internal view returns (bool) {
        address writer = _authority == address(0) ? _contractOwner() : _authority;
        if (account == writer) return true;
        if (!_holderCanUpdate) return false;
        address holder = _holderOf(tokenId);
        return holder != address(0) && account == holder;
    }

    /// @notice ERC-165 interface detection for the core, both extensions and ERC-165.
    function supportsInterface(bytes4 interfaceId) public pure override returns (bool) {
        return interfaceId == 0xdf670be1
            || interfaceId == 0x2d2a6041
            || interfaceId == 0x12c220bd
            || interfaceId == type(IERC165).interfaceId;
    }
}
```

#### Common setups of this implementation

The table shows common setups of the reference implementation above. It describes that implementation only. The lock is its own setting, read from its `authorityLocked()` view, and is not part of the standard. The contract owner can change the authority, the lock and the holder flag until the authority is locked. The holder flag is the value that `canHolderUpdateMetadata()` returns. The burn address is `0x000000000000000000000000000000000000dEaD`, an address nobody controls.

| Setup | Authority | Holder flag | Locked | Result |
| :--- | :--- | :--- | :--- | :--- |
| Owner only | zero address | `false` | `false` | Only the contract owner writes. |
| Holders write, owner in control | zero address | `true` | `false` | Each holder writes the records of the token they hold. The contract owner can write any token and can change the settings. |
| Holders for good | burn address | `true` | `true` | Each holder writes the records of the token they hold. Nobody else can write, and nobody can change the settings. |
| A policy | policy contract | `false` | `false` | Every write goes through the policy contract. The contract owner can replace it. |
| A locked policy | policy contract | `false` | `true` | Every write goes through the policy contract. Only the policy contract can hand the authority on. |
| Every record frozen | burn address | `false` | `true` | Nobody can write any record or change the settings, including for tokens minted later. |

## Security Considerations

This ERC is designed to put metadata onchain, providing security benefits through onchain storage.

The following points apply to the **Holder Metadata** extension.

- When `canHolderUpdateMetadata()` returns `true`, a seller can change a token's records right before a sale lands. A marketplace can read the flag and warn buyers. A buyer is safer reading the records again after the transfer than relying on what was shown before it.
- The flag only covers writes that the token contract itself allows. A policy contract set as the collection authority can let holders write through it, so when the authority is a contract, a flag that is `false` only means that holders cannot write to the token contract directly. When no authority is set, the contract's own write policy applies, and this ERC does not limit it.

The following points apply to the **Collection Authority** extension.

- This ERC does not say who can replace the authority or whether it can be replaced at all. The rules of a policy contract hold only while it stays the authority, and only while nobody can change the rules inside it. A client that relies on those rules has to know the implementation, for example whether it locks the authority, and whether the policy contract itself can be changed.
- An authority set to an address nobody controls can write nothing. If the implementation also stops anyone from replacing it, that state is permanent. If holders cannot write either, no record can be written again, including for tokens minted later.
