## Abstract

This standard gives lenders, lessors and the people who fund them a common way to ask three questions about a GPU that secures a debt: which financiers have filed a pledge of it, is there evidence that it still exists, and is there evidence that it delivered compute during a period. It defines:

- a **device key** that names one physical GPU, derived from the hardware identity certificate where the GPU has one, so that the same GPU has the same name in every registry;
- a **statement**: one observer's evidence about one GPU for one period, signed with [EIP-712](./eip-712.md);
- a **registry** that records which servicer has pledged which device keys under which collateral, returns every active pledge of a device key, and records per-period aggregate reports that commit to a set of statements by a Merkle root.

The registry records filings and assertions and makes conflicts visible. It does not verify statements or hardware attestation, does not decide priority between financiers, and does not value collateral.

## Motivation

GPUs are now financed like aircraft and ships: through secured loans, sale-and-leaseback and financial leases, increasingly by on-chain lenders whose depositors cannot inspect a data hall. Each of these structures rests on facts the financier cannot observe directly:

1. **Exclusivity.** A GPU server pledged to one financier can be pledged again to another. Public filing systems exist for this reason, but none of them indexes a GPU by an identifier the GPU can itself prove, and none is readable by a lending contract.
2. **Existence.** In a sale-and-leaseback the financier pays for equipment it never takes possession of. Lessors report that they often lack access to device-level data such as baseboard-management telemetry, so a fleet can shrink, move or never have existed without the financier learning of it before default.
3. **Delivery.** Repayment comes from rental revenue, and rental revenue comes from GPU-hours actually served. A borrowing base or debt-service covenant computed from self-reported utilization is only as good as whoever reports it.

Data-centre GPUs already carry the means to anchor the first two questions: recent accelerators hold a unique identity key with a certificate chain to the vendor and answer attestation challenges with it. What is missing is a common way to name a device by that key, to record who has pledged it, and to publish dated, attributable evidence about it in one format that a contract, an auditor and a depositor all read the same way.

[ERC-8325](./eip-8325.md) binds a token to an off-chain asset claim but has no notion of a device or of periodic evidence. Financial-lease interfaces expose servicing inputs as opaque attestations. Inference-receipt and inference-token proposals meter model calls, not the hardware that serves them. This standard supplies the device-level layer those designs leave to implementers.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Terms

- **Device**: one physical GPU. A server with eight GPUs is eight devices.
- **Device key**: the 32-byte name of a device defined in [Device keys](#device-keys).
- **Servicer**: the account that pledges devices, releases them and submits reports under a collateral. It may be the lender, a third-party servicer or the borrower. The registry records which account it is and nothing more.
- **Collateral**: a set of devices that secures one obligation, named by a servicer-chosen `bytes32` collateral identifier. All registry state is scoped to the pair (servicer, collateral identifier).
- **Observer**: the account that signs a statement, in one of the roles `servicer`, `lessee`, `lender` or `third-party`. A role is a label chosen by the observer, not a verified fact.
- **Period**: a half-open interval `[periodStart, periodEnd)` of Unix seconds.
- **GPU-second**: one device for one second.

### Device keys

```
deviceKey = keccak256(abi.encodePacked("ERC8515.device", uint16(pciVendorId), uint8(idType), idBytes))
```

`pciVendorId` is the PCI vendor identifier of the GPU (for example `0x10de`), and:

| `idType` | `idBytes` | Strength |
| --- | --- | --- |
| `0x01` | The exact DER-encoded SubjectPublicKeyInfo bytes from the vendor-designated device identity certificate | The device can prove possession of the key in response to a challenge |
| `0x02` | The vendor's canonical serial number of the device as UTF-8, exactly as the vendor's management interface reports it, preserving case and leading zeros | A label only; anyone can claim any serial number |

1. A servicer MUST use `idType` `0x01` for a device that has a vendor-designated identity certificate.
2. A consumer MUST NOT treat evidence about an `0x02` key as evidence that a device exists.
3. Device keys are not salted, so that the same device has the same key in every registry and under every servicer. Two filings name the same device only if both used the same identity bytes. A certificate reissued over the same key leaves the device key unchanged; a new identity key, or a different serial spelling, yields a different device key.

### Statements

A statement is one observer's evidence about one device for one period: a JSON object with exactly the members below and no duplicate member names.

| Member | Type | Meaning |
| --- | --- | --- |
| `kind` | string | The constant `"ERC8515/statement/1"` |
| `registry` | account | The registry contract the statement is made for |
| `servicer` | account | The servicer of the collateral |
| `collateralId` | bytes32 | The collateral identifier |
| `deviceKey` | bytes32 | The device |
| `pciDeviceId` | string | The PCI device identifier, four lowercase hexadecimal digits, for example `"2330"` |
| `location` | string | The country of the site as claimed by the observer, written as an ISO 3166-1 alpha-2 code in two uppercase letters. Conformance checks the form only |
| `periodStart`, `periodEnd` | integer | The period |
| `observer` | account | The signer |
| `role` | string | `servicer`, `lessee`, `lender` or `third-party` |
| `method` | string | How the observer observed. See below |
| `checksPassed`, `checksFailed` | integer | Attestation challenges issued in the period that the device answered correctly, and that it failed or did not answer |
| `servedSeconds`, `missedSeconds`, `unknownSeconds` | integer | GPU-seconds of the period in which the observer observed the device deliver work, observed it fail to deliver, or did not observe either |
| `evidence` | array | Zero or more objects with exactly the members `{ "type": string, "uri": string, "hash": bytes32 }`, where `hash` is the keccak256 of the exact bytes at `uri` |

Encodings:

- An integer is a string matching `0|[1-9][0-9]*`, evaluated with exact arithmetic. `periodStart` and `periodEnd` MUST fit in `uint64`.
- A `bytes32` is a string matching `0x[0-9a-f]{64}`.
- An account is a string `eip155:<chainId>:<address>`, where `<chainId>` is an integer as above that fits in `uint256` and `<address>` matches `0x[0-9a-f]{40}`. `registry`, `servicer` and `observer` MUST have the same `<chainId>`.

`method` is one of:

- `hw-attestation`: challenges answered with the device identity key. A passed check shows a device holding that key answered at that instant.
- `bmc-telemetry`: power, temperature and health readings from the server's baseboard management controller.
- `workload-meter`: a scheduler or billing meter that records work run on the device.
- `site-inspection`: a physical visit.

Rules:

1. `periodEnd` MUST be greater than `periodStart`, and `servedSeconds + missedSeconds + unknownSeconds` MUST equal `periodEnd - periodStart`.
2. `servedSeconds` counts only time in which the observer observed the identified device deliver work, and `missedSeconds` only time in which it observed the device fail to deliver work it was due to deliver. Allocation of the device to a lessee, or health readings, establish neither. All other time is `unknownSeconds`.
3. Methods that observe instants, `hw-attestation` and `site-inspection`, MUST report the whole period as `unknownSeconds`. `checksPassed` and `checksFailed` MUST be zero for every method other than `hw-attestation`.
4. Each statement has exactly one observer. Evidence from several observers about the same device and period is several statements.

#### Identifier and signature

The **statement identifier** is the keccak256 hash of the UTF-8 bytes of the statement serialized under RFC 8785 (JSON Canonicalization Scheme). Signatures are not members of the statement.

The observer signs the statement identifier as EIP-712 typed data with primary type `Statement`:

```
EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)
Statement(bytes32 statementId)
```

with `name` `"GPU Collateral Evidence"`, `version` `"1"`, and `chainId` and `verifyingContract` taken from `registry`. A statement is distributed in an envelope `{ "statement": {...}, "signature": "0x..." }`.

1. `signature` is lowercase `0x`-prefixed hexadecimal. Where `observer` is an externally owned account, it is 65 bytes `r || s || v` with `s` at most half the secp256k1 group order and `v` equal to 27 or 28, and MUST recover to `observer`.
2. Where `observer` is a contract, [ERC-1271](./eip-1271.md) `isValidSignature(digest, signature)` MUST return `0x1626ba7e` when called with the registry address as caller, evaluated against the state after the block that includes the report committing to the statement. A consumer that cannot read that state MUST treat the statement as unverified.

#### Statement root

A report commits to a set of statements by a Merkle root. The leaves are the statement identifiers in ascending numerical order, without duplicates, each hashed as `keccak256(abi.encodePacked(bytes1(0x00), statementId))`. At each level, adjacent nodes are paired in order, the earlier on the left, and a parent is `keccak256(abi.encodePacked(bytes1(0x01), left, right))`. An unpaired last node is carried up unchanged. The root of one statement is its leaf. The root of no statements is `bytes32(0)`.

### Registry

```solidity
// SPDX-License-Identifier: CC0-1.0
pragma solidity ^0.8.20;

interface IGPUCollateralEvidence {
    /// A servicer's assertion about one period of one collateral.
    struct Report {
        uint64 periodStart;
        uint64 periodEnd;
        uint32 devicesReported; // devices with at least one committed statement
        uint32 devicesAttested; // devices with a committed hw-attestation statement claiming checksPassed > 0
        uint64 servedSeconds;   // GPU-seconds, summed over the selected statement of each reported device
        uint64 missedSeconds;
        uint64 unknownSeconds;
        bytes32 statementRoot;
    }

    event DevicePledged(address indexed servicer, bytes32 indexed collateralId, bytes32 indexed deviceKey);
    event DeviceReleased(address indexed servicer, bytes32 indexed collateralId, bytes32 indexed deviceKey);
    event Reported(address indexed servicer, bytes32 indexed collateralId, Report report, string uri);

    /// Pledge devices under the caller's collateral.
    function pledge(bytes32 collateralId, bytes32[] calldata deviceKeys) external;

    /// Release devices from the caller's collateral.
    function release(bytes32 collateralId, bytes32[] calldata deviceKeys) external;

    /// Record the caller's report for one period of its collateral.
    /// `uri` locates the statement envelopes the report commits to.
    function report(bytes32 collateralId, Report calldata r, string calldata uri) external;

    /// Number of active pledges of a device key, across all servicers and collateral.
    function pledgeCount(bytes32 deviceKey) external view returns (uint256);

    /// The active pledge of a device key at `index`, in no defined order.
    function pledgeAt(bytes32 deviceKey, uint256 index)
        external view returns (address servicer, bytes32 collateralId, uint64 pledgedAt);

    /// Whether `deviceKey` is actively pledged under the servicer's collateral.
    function isPledged(address servicer, bytes32 collateralId, bytes32 deviceKey) external view returns (bool);

    /// Number of devices actively pledged under the servicer's collateral.
    function deviceCount(address servicer, bytes32 collateralId) external view returns (uint256);

    /// The latest report under the servicer's collateral. `reportedAt` is zero when there is none.
    function latestReport(address servicer, bytes32 collateralId)
        external view returns (Report memory r, uint64 reportedAt);
}
```

#### Pledges

1. `pledge`, `release` and `report` act only on state scoped to (`msg.sender`, `collateralId`).
2. `pledge` MUST revert if `deviceKeys` contains a key twice or a key already actively pledged under the same (servicer, `collateralId`). `release` MUST revert if `deviceKeys` contains a key twice or a key not actively pledged under it.
3. `pledge` MUST NOT revert because a device key is actively pledged under another servicer or another collateral. The new pledge is recorded alongside the existing ones.
4. `pledgedAt` is the timestamp of the block in which the pledge was recorded.
5. `pledgeAt` MUST revert when `index >= pledgeCount(deviceKey)`.
6. Every successful pledge and release of a device key MUST emit `DevicePledged` or `DeviceReleased` for it.

#### Reports

`report` MUST revert unless all of the following hold, and MUST succeed when they do, subject to ordinary execution failure. Arithmetic is evaluated in `uint256`.

1. `r.periodStart < r.periodEnd <= block.timestamp`.
2. `r.devicesAttested <= r.devicesReported <= deviceCount(msg.sender, collateralId)`.
3. `r.servedSeconds + r.missedSeconds + r.unknownSeconds == r.devicesReported * (r.periodEnd - r.periodStart)`.
4. There is no earlier report under the collateral; or `r.periodStart` is at least the `periodEnd` of the latest report; or `r.periodStart` and `r.periodEnd` both equal those of the latest report, in which case the new report replaces it.

A successful `report` MUST store `r` as the latest report with `reportedAt` equal to the block timestamp, and MUST emit `Reported` with the full report, so that replaced reports remain recoverable from the log.

The document at `uri` is a JSON array of the envelopes of every statement under `statementRoot`, each statement exactly once. A report is correct when every committed statement names the report's registry, servicer, collateral identifier and period, names a device key actively pledged under the collateral when the report was recorded, and the aggregates follow from the committed statements:

- `devicesReported` is the number of distinct device keys among them, and `devicesAttested` the number of those with a `hw-attestation` statement claiming `checksPassed` greater than zero.
- For each device, the **selected statement** is the one with the lowest numerical identifier among its statements whose `servedSeconds + missedSeconds` is greater than zero, or, if there is none, its statement with the lowest identifier. `servedSeconds`, `missedSeconds` and `unknownSeconds` are the sums over the selected statements.

The registry checks none of this. A report is the servicer's assertion. A consumer MUST NOT rely on a report as evidence until it has fetched the document, verified every signature, recomputed the root, checked correctness as defined above and applied its own policy on which observers it trusts. A report whose document is unavailable or fails these checks is not evidence. A lending contract that reads report values directly relies on the servicer and nothing else.

### Binding to a loan or lease

This section is informative. A collateral identifier SHOULD be derived from the obligation it secures, for example `keccak256(abi.encode(block.chainid, token, tokenId))` for a loan or lease represented by an [ERC-721](./eip-721.md) token, so that one collateral identifier corresponds to one obligation.

## Rationale

**Record conflicts, do not prevent them.** If `pledge` reverted on a device pledged elsewhere, anyone could block a device by pledging it first under a throwaway collateral. Recording every pledge with its time and servicer makes a conflict visible and attributable, and leaves priority to the law and the documents that govern the obligations, as public filing systems do.

**Scope state to the servicer.** Keying collateral by (servicer, identifier) removes any race to claim an identifier and makes every write attributable to one account. The registry does not know whether a servicer is the lender or the borrower; its consumers do, and weigh its filings and reports accordingly.

**Unsalted device keys.** Double pledging can be seen across financiers only if every financier names a device the same way. A salted key would hide fleet composition and would also hide the double pledge this standard exists to expose.

**Aggregates on chain, statements off chain.** A lending contract or a dashboard needs a few numbers per period. Storing thousands of signed statements on chain would cost more than the decision is worth. The root fixes which statements the servicer committed to, so an auditor can later check the servicer's numbers against them. It does not make the numbers true.

**Deterministic selection.** The aggregates are a function of the committed set alone, so two consumers that fetch the same document compute the same numbers, and a servicer cannot change after the fact whose evidence its totals rest on.

**Instant methods report no duration.** An attestation check every hour shows the device was alive at those instants, not that it served for the hours in between. Counting it as served time would let a servicer manufacture utilization out of liveness probes.

**No observation timestamp on chain.** A single timestamp per report would let one old observation stand for a whole fleet. Consumers that need freshness read it from the statements and their evidence.

**No on-chain attestation verification.** Vendor attestation formats change with every hardware generation, and their certificate chains are expensive to verify on chain. A verifier can be added later behind a separate interface.

## Security Considerations

**A clean lookup is not exclusivity.** `pledgeCount` counts active filings in one registry. Zero means no financier has filed in that registry, not that the device is unencumbered. Liens recorded elsewhere, in other registries or not at all remain possible. Deployers SHOULD converge on one registry per chain, and lenders SHOULD check every registry their counterparties use.

**Release authority.** The servicer can release its own pledges at any time. A pledge filed by a borrower acting as servicer can disappear while the debt is outstanding. A lender that relies on its filing persisting MUST use a servicer account whose release authority the borrower cannot exercise.

**Two signatures are not two parties.** A statement proves that the key of `observer` signed it. It does not prove the observer is independent of the borrower, and `role` is self-declared. A borrower that controls a "third-party" key can produce statements indistinguishable from honest ones. Consumers MUST establish observer independence outside this standard.

**Self-reported delivery.** When the servicer or the observer is the borrower, `servedSeconds` is the borrower's claim about its own revenue base. A lender SHOULD rely on it only together with evidence the borrower does not control, such as rental payments received into an account the lender controls.

**What attestation shows.** `devicesAttested` counts devices for which some observer claims a passed check. Before relying on a passed check as evidence of existence, a consumer MUST establish that a challenge fresh to the period was verified against a vendor-authenticated identity certificate whose key yields the reported `0x01` device key. Even then, a passed check does not show where the device is, that it is the device described in the loan documents, or that it is not serving someone else. `location` is a claim of the observer.

**Coverage.** A servicer chooses which devices, periods and statements a report includes, and can report on GPUs other than the ones financed. Consumers SHOULD compare the distinct device keys in the committed statements with the list of device keys they financed, not merely the count, and treat missing devices, missing periods and unknown time as absence of evidence, not as evidence of delivery.

**Serial-number keys.** Under `idType` `0x02` the device key is a label. Pledges of such keys detect careless double pledging between honest financiers and nothing more.

**Griefing.** Anyone can raise the `pledgeCount` of a device key they can name. Consumers SHOULD treat a pledge by an unknown servicer as a reason to investigate, not as proof of encumbrance, and SHOULD order competing pledges by `pledgedAt`.

**Disclosure.** Unsalted device keys and public pledges reveal how many devices each servicer has pledged and when devices move between collateral. Participants that cannot accept this disclosure should not use a public registry.
