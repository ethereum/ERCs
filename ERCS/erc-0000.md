## Abstract

This standard is an extension of [ERC-721](./eip-721.md). It defines a minimal interface through which a token contract advertises that its tokens can be represented as native mobile wallet passes (such as Apple Wallet PKPass bundles or Google Wallet objects), a pass manifest document that tells clients how to acquire those passes, and events that signal when pass content has changed. It standardizes discovery and delivery only. How an implementation generates, signs, and pushes passes remains out of scope.

## Motivation

Native wallet passes are the only programmable surface that ships by default on effectively every smartphone. A pass can display live state, deep-link into web experiences, and receive platform push updates, all without the holder installing an application. Several production systems already bind NFTs to wallet passes (memberships, tickets, loyalty balances, and fully interactive experiences whose state lives on chain), but each one invents a proprietary bridge. As a result:

- Wallets, marketplaces, and indexers have no uniform way to discover that a token has a pass representation, so the capability stays invisible outside the issuer's own site.
- Pass distributors have no uniform signal for when a token's pass content is stale.
- Each new integration re-derives the same security decisions (how pass links relate to ownership, what happens on transfer) with predictably uneven results.

A small, shared discovery interface lets any client (an NFT marketplace, a wallet app, an email service, a point of sale) offer "Add to Apple Wallet / Save to Google Wallet" for any compliant token, the same way [ERC-721](./eip-721.md) `tokenURI` made metadata portable.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Contract interface

Compliant contracts MUST implement the `IERC721WalletPass` interface and the [ERC-165](./eip-165.md) `supportsInterface` function, and MUST return `true` for the interface identifier `0xef5f1e71`.

```solidity
// SPDX-License-Identifier: CC0-1.0
pragma solidity ^0.8.0;

/// @title ERC-721 Wallet Pass Extension
/// @dev The ERC-165 identifier for this interface is 0xef5f1e71.
interface IERC721WalletPass {
    /// @notice Emitted when the wallet pass content bound to a token has
    ///  changed. Pass distributors SHOULD regenerate the pass and, where the
    ///  platform supports it, push the update to installed passes.
    event PassUpdate(uint256 indexed tokenId);

    /// @notice Emitted when the wallet pass content for a consecutive range
    ///  of tokens has changed.
    event BatchPassUpdate(uint256 fromTokenId, uint256 toTokenId);

    /// @notice Get the pass endpoint URI for a token.
    /// @dev Throws if `tokenId` is not a valid token. The returned URI MUST
    ///  resolve to a pass manifest as defined in this standard.
    /// @param tokenId The token whose pass endpoint is requested.
    /// @return The pass endpoint URI.
    function passURI(uint256 tokenId) external view returns (string memory);
}
```

`passURI` is intentionally parallel to `tokenURI`: a level of indirection pointing at an off-chain document, because wallet passes are signed platform artifacts that cannot be produced on chain.

### Pass manifest

The URI returned by `passURI` MUST resolve to a JSON document (the pass manifest) with the following shape:

```json
{
  "formats": {
    "apple": "https://issuer.example/passes/c3f1.../card.pkpass",
    "google": "https://pay.google.com/gp/v/save/eyJhbGciOi..."
  },
  "updatedAt": 1754500000
}
```

- `formats` is REQUIRED and MUST contain at least one entry. Each key names a pass platform; each value is an acquisition URL for that platform.
- The key `apple` identifies an Apple Wallet pass. Its URL MUST resolve to a resource served with the media type `application/vnd.apple.pkpass`.
- The key `google` identifies a Google Wallet pass. Its URL MUST be a Save to Google Wallet link.
- Additional format keys MAY be present. Clients MUST ignore format keys they do not recognize.
- `updatedAt` is OPTIONAL. When present it MUST be a Unix timestamp (integer seconds) of the last content change, and SHOULD change whenever `PassUpdate` is emitted for the token. It reflects pass content freshness only and does not indicate whether the acquisition URLs in `formats` are still valid.

### Metadata mirror (OPTIONAL)

The JSON returned by `tokenURI` MAY include a top-level `wallet_pass` property whose value is the pass manifest object defined above. This lets metadata-only consumers (for example marketplaces that never call contract methods beyond `tokenURI`) surface an add-to-wallet action without an extra fetch. When both are present, the manifest reachable through `passURI` is authoritative.

### Acquisition URLs

- Acquisition URLs SHOULD be capability URLs: unguessable, high-entropy, and not derivable from public data such as `tokenId`, token serial numbers, or metadata fields.
- `passURI` is a public view function and the manifest it returns is fetchable by any client. When the manifest is served without access control (the public configuration), its acquisition URLs are public data, one chain read away from anyone able to enumerate token ids: unguessability does not survive publication. In this configuration the capability URL is hygiene (it limits scraping and accidental sharing) and MUST NOT be treated as a proof of possession or ownership. Any state-changing action reachable from the resulting pass requires the authorization defined under Authorization of pass-reachable actions.
- Implementations MAY instead gate manifest resolution or pass acquisition behind proof of control of the owning account (the gated configuration). Only in this configuration may possession of an acquisition URL serve as a possession proof, and here acquisition URLs MUST rotate upon the implementation observing the transfer or upon the new owner's first claim, whichever comes first. Implementations SHOULD document which configuration they operate.
- Rotation is not synchronous with the on-chain transfer. An implementation observes a transfer through indexing or at the new owner's first claim, so between the transfer and rotation the previous owner's acquisition URLs remain cryptographically valid. The fresh entitlement read required under Authorization of pass-reachable actions is the authoritative control that refuses them in that interval; rotation closes the residual window rather than providing the boundary.
- When installed passes expose links that can trigger state-changing actions, acquisition URLs MUST be capability URLs and implementations SHOULD rotate them when the token is transferred (MUST in the gated configuration, per the rotation timing above), so that a pass held by a previous owner stops granting the new owner's links. Action links embedded in an installed pass are capability URLs in this sense and subject to the same rules.
- Acquisition URLs MAY be short-lived. A Save to Google Wallet link, for example, is a signed JWT that issuers commonly mint on demand and allow to expire. Clients SHOULD fetch the manifest at the moment of the user's add-to-wallet action, and MUST NOT durably cache acquisition URLs. The durable handle for a token's pass is the manifest URI returned by `passURI`; the acquisition URLs inside the manifest are not durable, and `updatedAt` says nothing about their validity.

### Authorization of pass-reachable actions

Every artifact this standard describes (the pass file, the acquisition URL, the manifest) is a bearer artifact; authorization never lives in the artifact. An action that mutates chain state and is reachable from a pass is authorized by two checks, each closing a hole the other cannot reach:

1. **Proof of control of the owning account**: a signature over a server-issued challenge. The challenge MUST name the token (chain id, contract address, and token id), the requested action, a single-use nonce issued by the verifier, an expiration time, and the identity of the verifier, and the verifier MUST check every one of these fields before acting. Where the signature alone does not identify the signing account, as with contract account signatures verified per [ERC-1271](./eip-1271.md), the challenge MUST also name the claimed account. Challenges SHOULD be serialized as Sign-In with Ethereum messages per [ERC-4361](./eip-4361.md): a conforming challenge already carries every field in which that format's security lives, and wallets and signing libraries parse the format today, for externally owned accounts and contract accounts alike. Accounts created from an email address can satisfy this check without exposing key material to the user, through an embedded signer or a contract account.
2. **A fresh on-chain read of ownership** (for [ERC-721](./eip-721.md), `ownerOf`) at the time of the request, not at pass issuance and not at URL minting.

The fresh read MUST be performed for every state-changing action: it closes the transfer window, so a sold token stops acting immediately regardless of how many valid-looking passes remain installed. The control proof MUST be required wherever the pass user experience can carry a signature: it closes forwarding, the case rotation cannot reach, in which a pass or URL leaks while ownership is unchanged. Where the pass user experience cannot carry a signature, check (1) is instead met by the capability configuration described below: an unguessable capability URL stands in for the per-action signature, sound only under the conditions stated there.

Implementations MAY extend entitlement to accounts other than the owner, for example a rental user designated per [ERC-4907](./eip-4907.md) `userOf`, or a delegate authorized through an on-chain delegation registry, provided the entitlement policy is documented and every extended entitlement is evaluated with the same request-time freshness required of `ownerOf`: read at the time of the request, never cached from pass issuance or URL minting. Where entitlement is extended this way, the claimed account named in the challenge is tested against the documented entitlement rather than bare `ownerOf` equality. Extension re-opens a question the single-owner model never had to answer: during an active rental both `ownerOf` and the rental user are live accounts, so a policy that merely adds accounts lets owner and renter act at once. A documented policy MUST therefore define precedence, and a rental entitlement (an active [ERC-4907](./eip-4907.md) `userOf`) SHOULD be exclusive of the owner for the actions it covers, while a delegation is additive by intent. Absent a documented extension, `ownerOf` remains the entitlement and the fresh read of it is the default MUST.

Each challenge field closes its own hole. The token and action scope the proof, so a proof obtained for one action cannot be presented for another. The single-use nonce makes a captured proof worthless a second time. The expiration makes a leaked proof go stale. The verifier identity keeps a challenge signed for one issuer from being presented to another that gates the same token. Because the nonce is single-use and issued by the verifier, every conforming flow includes a server round trip; a flow that does not adopt the SHOULD serialization avoids parsing a message format, not the round trip.

#### Example challenge

The following is a conforming Sign-In with Ethereum challenge for one action: the feed action on token id 412 of an example ERC-721 contract on chain id 1, issued by `issuer.example`. It carries the token binding as a CAIP-19 asset identifier in the resources list and the action as a second resource, with the statement line naming the action in plain language.

```text
issuer.example wants you to sign in with your Ethereum account:
0x2B7E9A4c1F0d8e63A5b2C4D6E8F0A1b3C5d7E9F2

Authorize the feed action for wallet pass token 412 on issuer.example.

URI: https://issuer.example/wallet-pass/actions
Version: 1
Chain ID: 1
Nonce: Xq3F9kP2mR7tW1Zb
Issued At: 2026-08-07T15:04:05Z
Expiration Time: 2026-08-07T15:09:05Z
Resources:
- eip155:1/erc721:0x5F9B5a1cdED9d6B3f5E8a2C47B0e13d6A8F4c2e1/412
- urn:wallet-pass:action:feed
```

Each floor field maps to a specific place in the message: the token lives in the resources list as the CAIP-19 asset identifier (chain id, contract address, and token id together), the action lives in the resources list as `urn:wallet-pass:action:feed` and in plain language in the statement line, the single-use nonce is the `Nonce` field, the expiration is the `Expiration Time` field, the verifier identity is the `domain` on the first line, and the claimed account is the `address` line. A contract account verified per [ERC-1271](./eip-1271.md) uses the same message, with the claimed account carried in that same address line. The example timestamps omit fractional seconds; RFC 3339 permits them, and a message whose `Issued At` or `Expiration Time` carries them (for example `2026-08-07T15:04:05.000Z`, the form common signing libraries emit) conforms identically. Both resource entries are valid RFC 3986 URIs, which is what [ERC-4361](./eip-4361.md) requires of entries in the resources list.

#### The capability configuration

An installed pass is a static artifact. Its fields are fixed at issuance and re-rendered only by platform push, so a pass cannot carry a single-use nonce or a short expiration. In an email-onboarded custodial or relayer product the signing key is typically held by the server or an embedded signer rather than prompted per action, so no per-action user signature exists at the moment a pass link is followed. The challenge is therefore fetched from the verifier at action time; the link embedded in the pass only reaches the flow, it never carries the proof. The capability configuration is not a third configuration beside public and gated; it is the gated configuration operated so that the capability URL carries the possession role.

In such a deployment the capability URL MAY stand in for check (1). The substitution is explicitly weaker than a per-action signature, and it is permitted only when all of the following hold:

- the deployment operates the gated configuration defined under Acquisition URLs;
- the URL is an unguessable, high-entropy capability;
- the URL is bound to the specific token and action it reaches;
- the URL rotates on transfer per the Acquisition URLs section (upon observation of the transfer or the new owner's first claim, not synchronously); and
- check (2), the fresh entitlement read, remains in force unconditionally.

Check (2) is never substitutable. No configuration, capability or signed, may omit or defer the fresh entitlement read: it is the authoritative control in every case.

What the substitution gives up must be stated plainly: with no per-action signature, forwarding is not closed. Any party holding the capability URL can trigger the bound action while ownership is unchanged. Unguessability does not help once the URL has leaked, rotation does not fire absent a transfer, and the fresh entitlement read refuses a sold token, not a forwarded URL under an unchanged owner. This residual is accepted by the configuration, and the substitution is sound only for actions whose worst-case impact under forwarding the implementation can tolerate. Actions above that tolerance require the signed challenge.

The verifier-identity binding of a signed challenge and the issuer binding of a capability URL are not the same property. The verifier-identity field guards against a captured signature being lifted and presented to a different verifier that gates the same token. A server-held capability URL has no user signature to lift; its binding to the issuer is structural, since the URL resolves only at the issuer's endpoint, rather than signed. The two should not be conflated when reasoning about what the capability configuration gives up.

In the capability configuration the identifier a URL binds MAY be a server-resolved identifier, for example a pass serial, provided it maps deterministically and uniquely to a single on-chain token and cannot be re-bound to another token. The explicit chain id, contract address, and token id triple is RECOMMENDED for capability bindings. That triple remains REQUIRED in the signed challenge; the signed-challenge floor of check (1) is unchanged.

### Lifecycle requirements

- Implementations SHOULD emit `PassUpdate` whenever on-chain state that is rendered on the pass changes, and SHOULD push updated content to installed passes through the platform update mechanism where available.
- On transfer of a token, implementations SHOULD update or invalidate passes issued to the previous owner so that an installed pass does not continue to present itself as current.
- A wallet pass is a projection of the token, not the token itself. Implementations MUST NOT treat possession of a pass file, or the ability to add it to a device wallet, as proof of ownership of the underlying token. Any action reachable from a pass that mutates chain state MUST NOT be authorized by pass possession alone: a possession-independent fresh entitlement read is always required, as defined under Authorization of pass-reachable actions.

## Rationale

**URI indirection instead of on-chain pass data.** Apple Wallet passes are cryptographically signed bundles produced with issuer certificates; Google Wallet passes are objects registered through an issuer account. Neither artifact can be constructed on chain, and both change far more often than token metadata (timers, balances, moods, standings). A `tokenURI`-style endpoint is the only shape that fits every platform.

**A manifest instead of format query parameters.** A single JSON manifest fetched once tells the client everything available for the token and is trivially extensible to future platforms. Query-parameter negotiation was rejected because it makes capabilities undiscoverable without probing.

**A dedicated `PassUpdate` event instead of reusing [ERC-4906](./eip-4906.md).** `MetadataUpdate` signals that `tokenURI` content changed and is consumed by NFT indexers. Pass content routinely changes when metadata does not (for example a countdown rendered on the pass), and its consumers are pass distributors rather than indexers. Implementations that mirror the manifest into metadata MAY emit both events.

**A mandated challenge floor with SIWE as RECOMMENDED serialization.** The security of the control proof lives in the challenge fields, so this standard mandates the fields directly rather than a message format. Sign-In with Ethereum ([ERC-4361](./eip-4361.md)) is the serialization of exactly those fields that wallets and libraries already emit and parse, so recommending it buys interoperability at near zero cost, while a constrained pass flow that cannot parse the format still meets the same floor with the same guarantees.

**Delivery pipeline out of scope.** Device registration, platform push (APNs and the Google Wallet API), HMAC construction of action links, and pass art are platform- and vendor-specific. Standardizing them would freeze implementation detail without improving interoperability; discovery is the interoperable seam.

## Backwards Compatibility

This standard is a pure extension of [ERC-721](./eip-721.md) and introduces no changes to existing behavior. Contracts that do not implement it are unaffected. The metadata mirror is additive and ignored by clients that do not understand it. The interface can be implemented alongside other extensions (enumerable, royalty, token-bound accounts) without interaction. Application to [ERC-1155](./eip-1155.md) is intentionally out of scope: fungible balances and multi-holder semantics require a different binding between holder and pass, and would dilute the minimal interface proposed here. A future extension would bind a specific account alongside the token id and test `balanceOf(account, id)` against a minimum holding in the authorization check, keeping multi-holder semantics out of the pass artifact entirely.

## Reference Implementation

A production implementation exists and has operated on a public test network since July 2026: a fully interactive consumer experience delivered entirely through Apple Wallet and Google Wallet passes bound to ERC-721 tokens, including capability-URL acquisition links, rotation on ownership claim, platform push on state change, and manifest-style delivery to both platforms. The implementation is closed source at the time of writing; an open reference implementation SHOULD accompany this proposal before it advances past Draft.

## Security Considerations

**Passes are bearer artifacts.** A `.pkpass` file can be forwarded and added to any number of devices, and platforms do not enforce uniqueness. This is why the standard requires that pass possession never be treated as ownership, and why action links reachable from a pass must be authorized by the two checks defined in the specification. The checks are not redundant: the fresh on-chain read closes the transfer window (a sold token stops acting immediately, however many installed passes still look valid), the control proof closes forwarding (a leaked pass or URL cannot act while ownership is unchanged, the case rotation never reaches; in the capability configuration there is no per-action signature and forwarding is accordingly not closed, as the specification states), and the challenge binding closes replay and reuse (the token and action scope the proof, the single-use nonce and expiration make a captured proof worthless after first use or expiry, and the verifier identity keeps a proof from being presented to a different issuer gating the same token). Implementations that skip either check create a confused-deputy risk in which any holder of a shared pass file can exercise the owner's privileges. The fresh read bounds the transfer window; it does not eliminate it. That window is the interval between the read and the action, and a read is only as fresh as the chain head it reflects: a read from a lagging node, or one invalidated by a reorganization, is not fresh, so implementations SHOULD read against their best view of the latest safe chain head. The residual window is accepted risk of this design.

**Capability URL leakage.** Acquisition URLs and action links appear in emails, chat messages, and device backups. High entropy limits guessing; rotation on transfer (and RECOMMENDED rotation on explicit owner request) limits the damage window of a leaked URL. Note that URLs published in an ungated manifest are public data regardless of entropy; the Acquisition URLs section defines the only configuration in which a URL may serve as a possession proof. Clients that durably cache acquisition URLs both widen the exposure window and risk surfacing URLs that have expired or rotated; the Acquisition URLs section requires clients not to cache them durably.

**Stale passes after transfer.** Without invalidation or push updates, a previous owner's installed pass continues to display current state and may still render action links. Implementations SHOULD invalidate or visibly mark superseded passes. Rotation of acquisition URLs is likewise not synchronous with the transfer: until the implementation observes it, a previous owner's capability URLs stay valid, and the fresh entitlement read of check (2), not rotation, is what refuses them in that interval.

**Phishing surface.** Pass fields can carry arbitrary links and text under issuer branding. Clients offering add-to-wallet actions for arbitrary compliant tokens SHOULD present the issuing contract address, and pass endpoints SHOULD serve from an origin consistent with the collection's published web presence.

**Manifest is issuer-asserted, not chain-asserted.** The pass manifest is data asserted by the issuer, not by the chain. The only chain-asserted fact is that the token contract designated this endpoint through `passURI`. Pass files are signed platform artifacts produced under the issuer's Apple or Google platform credentials, but nothing in the manifest JSON is cryptographically bound to the chain: a client cannot verify the manifest against on-chain state, only that it was reached through the contract's `passURI`. Clients surfacing add-to-wallet actions therefore rely on the `passURI` indirection and the origin-consistency guidance above, not on any property of the JSON itself.

**Privacy.** Pass delivery involves device push registrations and often email addresses. Pass identifiers and pass-visible fields SHOULD NOT embed holder personal information; platform object identifiers SHOULD be random rather than derived from emails or account identifiers.

**Endpoint availability.** The manifest endpoint is off-chain infrastructure. Its failure affects pass delivery and freshness only; ownership and transferability of the token are never dependent on it.
